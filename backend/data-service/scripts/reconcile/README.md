# 对账（reconcile）

把「服务端实现的行为与本地实现一致」从口号变成证据。

**这是 S3 的准入条件**（迁移计划 §6）。S3 的 63 条接口测试证明的是「不报错」，
而它们测的是**本地实现**；真正有说服力的是**同一份输入、两条链路、逐表比对**。

---

## 现在覆盖到哪

| 阶段 | 步骤 | 表 | 状态 |
|---|---|---|---|
| 结伴 | 家长邀请 → 学生接受（`pending` → `active`） | `relationship` | ✅ 差异 0 |
| 作业闭环 | 建作业 → 提交 → 传照片 → 写错题 | `homework` `homework_image` `review_mistake` | ✅ 差异 0 |
| 复习闭环 | 组卷 → 导出 → 作答 → 批改 → 毕业 → 报告（含重复生成） | `review_paper` `review_paper_item` `review_attempt` `review_summary` | ✅ 差异 0 |
| 打卡 / 积分 / 心愿 | 建计划 → 打卡（含重复打卡）→ 记分（含重试）→ 撤销 → 许愿 → 定价 → 申请 → 兑现 → 扣分 | `study_plan` `study_plan_checkin` `point_ledger` `wish` | ✅ 差异 0 |
| 运动 | 建计划（**含重复新建**）→ 启用 → 记一条记录（**含重试**） | `workout_plan` `workout_record` | ✅ 差异 0 |
| 点评 | 家长发一条每日点评 | `daily_comment` | ✅ 差异 0 |
| 通知 | 标记一条已读（**只在一侧执行**） | `app_notification` `app_notification_read` | ✅ 按声明核对通过 |

整串跑下来：**31 步 / 16 张表逐行一致，另 2 张通知表按声明核对一致。**

**还欠着**：通知「已读」在客户端读路径上的改造（本地模型缺「读者」维度，见下）。
按同一套办法逐步加 —— 每加一步**两侧执行器都要加**，只加一边的后果是
那一步在另一侧静默不执行，而对账仍然「通过」。

### 三张 2026-09-21 补进来的表，各自解决了什么

**`relationship` —— 它原先只是「起点」，于是只被间接验证。**
两侧的种子都自带一条关系行，它躺在 dump 列表外面；而它是**可见集合
（家长看得见哪个孩子）的来源**：状态词写错时，症状是后面某一步 403，
而错误本身在对账报告里一个字都看不到。现在改成「清空 → 由序列头两步
重新产生」，它就和别的表一样被逐行读出来。代价是**起点约定变了**
（见下节），换来的是「词写错」表现为一条看得懂的字段差异。

**`workout_plan` / `workout_record` —— 它们是 R2 的唯一例外。**
全局规则是「id 由服务端生成」，这两张表刻意反过来：**id 由客户端带**，
因为它同时是幂等键，而「今天跑了几次」不能被一次网络重试改成两次
（理由写在 `src/routes/workout.js` 的文件头）。序列因此把 id 写成**字面量**
（`wp_rec_1` / `wr_rec_1`），两侧发同一个值，并把每次插入都**做两遍**。
⚠️ 但这件事**对账本身测不出来** —— 别名是从响应登记的，响应里给什么、
dump 里就是什么，把 id 换成服务端生成的也照样「两侧一致」。所以
`server-run.mjs` 里另有一条直白断言 `assertClientIdKept`。
这一轮它当场撞出一个真问题，见下。

**`daily_comment` —— 它是「一个动作、两处落库」的第二例。**
服务端的 `insertDailyComment` 在同一个事务里既写点评、又生成通知
（本地是 `parent_controller.dart` 里相邻的两句）。所以补它的同时，
`app_notification` 的声明清单里也多了一条「家长点评」—— 少发一条会报错，
多发一条也会，这正是 `behaviorDiff` 与白名单的区别。

### 通知：dump 了，但按**声明**核对而不是逐行比对

它的**产生位置在两条链路上不同**（迁移计划陷阱⑦）：本地是 `NotificationController`
往本机库写（调用点只有「心愿提醒」与「家长点评」），服务端由 `routes/notify.js`
在写端点的同一个事务里生成（提交作业 / 复习批改 / 计划 / 打卡 / 心愿）。

本场景实测：**服务端 6 条，本地 0 条。** 执行器不会去模拟「控制器的通知写入」——
那是让执行器发明行为。

早先的做法是**不 dump 它**，理由是这个差异「已知且设计如此」；但那只解决了一半：
不 dump 之后，「服务端多发了一条通知」「少发了一条」，甚至「客户端自己也发了一条」
全都看不见了。现在的做法是 `scenario.behaviorDiff` —— 把两侧**故意不同**的行为
逐条钉住（通知按**标题多重集**声明，不按 id，因为两侧 id 本来就无对应关系），
比对器**对着清单核**：多一条、少一条、换个标题都会报错。

这不是白名单：白名单是「抹掉一列的值、此后不再看它」，而这里是**核对**。
2026-09-19 做过一次反向验证 —— 故意把声明删掉一条，
比对器立刻报 `✗ 服务端多出「心愿已兑现」×1` 并退出码 1。

## 三层结构

```
scenario.json        操作序列 —— 语言中立的单一真相
   │
   ├── test/reconcile_dump_test.dart            本地链路执行器（真 SQLite, sqflite_common_ffi）
   │        读序列 → 调 DatabaseService → dump
   │
   └── scripts/reconcile/server-run.mjs         服务端链路执行器（真 PG + 完整 HTTP 路由链路）
            读序列 → 打端点 → dump
                        │
                        └── scripts/reconcile/compare.mjs   比对器（唯一一份 diff 逻辑）
```

`scenario.json` 里有四类内容，都是「唯一真相」的一部分：

| 字段 | 作用 |
|---|---|
| `steps` | 操作序列。每步可带 `identity`（`student` / `parent`，决定用谁的 token）与 `sides`（缺省两侧都跑） |
| `dump` / `dumpServerOnly` | 要 dump 的表。后者是本地 schema 里**没有**的表（目前只有 `app_notification_read`） |
| `behaviorDiff` | 两侧**故意不同**的行为，逐条钉住并核对（见上） |
| `vocabDiff` | 两侧**枚举值域不同**的列。照常打印、不算失败，但它解释了「场景里为什么只用 `completed`」 |

**为什么序列只有一份**：两侧各写一份序列，它们会漂；而漂了的对账脚本比没有更坏 ——
它会给出「一致」的假结论。

**为什么比对逻辑只有一份**：同上。执行器只做「执行 + dump」，不做任何判断。
比对器**也读 `scenario.json`**（它唯一读的非 dump 输入）—— 它需要知道
「哪些差异是声明过的」。把台账写在比对器里、把序列写在 scenario 里，
两者会漂；写在同一处时，「序列里加了新动作」与「它的预期差异」是同一份
diff 里的两行，忘不掉。

## 怎么跑

```bash
# ① 本地链路（cwd = 项目根；路径相对项目根）
RECONCILE_OUT=serverless/data-service/out/local-dump.json \
  flutter test test/reconcile_dump_test.dart

# ② 服务端链路（起本机 PG → 迁移 → 执行 → dump）
#    命令末尾**不要接管道**（postgres 是常驻进程，继承了 stdout 的管道
#    永远等不到 EOF，现象是「无输出地被 SIGTERM」）→ 一律 `> 文件 2>&1`。
cd serverless/data-service && npm run reconcile:server

# ③ 比对
cd serverless/data-service && npm run reconcile:compare
```

③ 的退出码：`0` = 差异为 0；`1` = 有差异（或某一侧的 dump 缺失）。

### ② 的三个环境事实（都是踩过之后写下的）

**端口与数据目录：三方错开，别共用。**
它用 `LOCAL_PG.reconcilePort`（55435）+ `.pgdata-rec`，演示栈是 55433 + `.pgdata-dev`，
测试是 55434 + `.pgdata-test`。2026-09-21 之前它**没显式指定端口**，于是落回 55433
—— 也就是**演示栈的端口**：演示栈开着时表现为「对账跑到一半、退出码 1、
什么原因都没说」（postgres 的 `could not bind ... address already in use`
被 `EmbeddedPostgres` 的默认空 `onLog` 一起吃掉了）。
现在 `onLog` / `onError` 会放行 FATAL/PANIC/ERROR 进进度日志，错误处理本身
也对「拒绝理由是 `undefined`」免疫 —— 一个会把原因吞掉的错误处理器比错误更难查。

**被中断过之后，先删掉 `.pgdata-rec/` 再跑。**
`removeDirWithRetry` 只有 4 秒预算，删不干净就放弃，随后 initdb 面对一个非空目录
**直接拒绝**，而现象是**一行输出都没有地卡住**（本轮连撞两次）。
判据是「进度日志停在『场景 … 31 步』超过四五分钟」—— 正常起库只要 1.5–3 分钟。

**「起库很慢」与「已经挂住」只能靠进度日志分开**（见下）。
本轮实测：起 PG 约 1m45s–1m50s，31 步工作本身只要 0.5 秒，收尾再要一两分钟。
收尾（强杀 postgres + 删目录）偶尔会挂住 —— **dump 早就落盘了**，
所以「已写出 xxx.json」一出现就可以停掉进程，判据看的是那份文件（见「产物保护」第 2 条）。

### 怎么确认对账脚本自己没有变松

一个只会说「一致」的对账脚本和一个真的在核对的对账脚本，**平时输出一模一样**。
所以每加一类出口，都要反向验证一次「它被改坏时会响」。做法是造一份改坏的
`scenario.json`，用 `RECONCILE_SCENARIO` 指过去（不必重跑两个执行器）：

```bash
cd serverless/data-service

# ① 造一份被改坏的声明：把 app_notification 的清单删掉最后一条
node -e "const fs=require('fs');const s=JSON.parse(fs.readFileSync('scripts/reconcile/scenario.json','utf8'));s.behaviorDiff.entries.find(e=>e.table==='app_notification').server.pop();fs.writeFileSync('out/scenario-tampered.json',JSON.stringify(s,null,2));"

# ② 用它跑比对 —— 不重跑两侧执行器，因为要验的是「比对器会不会响」
RECONCILE_SCENARIO=out/scenario-tampered.json npm run reconcile:compare
```

已做过的反向验证：删掉一条通知声明 → `✗ 服务端多出「心愿已兑现」×1`、退出码 1。
**2026-09-21 补做了一次「新加的判据是不是真的在比」**：把本地 dump 里
`relationship.status` 的 `active` 改成 `accepted`（只改产物、不重跑两侧执行器），
比对器立刻报出该行的一个字段差异并退出码 1 —— 这条正是补 `relationship` 的全部理由：
**它原先不在这张表里，写错词没有任何一条判据看得见。**

`RECONCILE_SCENARIO` 也是比对器**唯一**读的非 dump 输入（见上文的四类内容）。

`RECONCILE_OUT` 没设时 ①**整组跳过** —— 它要写文件，而 `flutter test` 全套里
不该有「跑一次就往仓库里写东西」的用例。

### 跑得久 ≠ 卡住：先看进度日志

② 会往 `out/server-run.progress.log` **同步追加**每一阶段的完成情况
（起库 / 清表 / 每一步 / dump / 收尾），不受重定向与缓冲影响。

实测耗时分布（本机）：**起 PG 约 2m52s，22 步工作本身只要 20s，收尾再要一两分钟。**
对账的时间几乎全在数据库生命周期上，所以「没输出」是常态 ——
但也正因为如此，**没有进度日志时几乎无法区分「在起库」与「已挂住」**，
这条日志就是为那一次分不清而加的。

### 产物保护的三个约定

这一轮踩过之后加的，每条都对应一类「对账静默给出错误结论」：

1. **执行器开跑前先删掉自己上一轮的 dump。** 不然在写文件之前失败
   （起库失败、某一步报错）时，旧 dump 留在原地，而比对器只认路径不认时间 ——
   它会对一次**从未发生**的运行宣布「一致」。
2. **服务端执行器在 PG 还活着的时候就把 dump 落盘。** 写文件原本在读回
   `withMigratedDatabase` 之后，也就是收尾之后；收尾是整条链路里最慢、也最可能
   被外部超时杀掉的一段 —— 一旦被杀，一次**成功**的运行会变成「什么都没有」。
3. **执行器遇到失败步骤必须抛错，不能静默跳过。** 跳过之后 dump 照样生成。

### 为什么本地链路那一侧必须是真实现

本地执行器走的是 `sqflite_common_ffi` 起的**真 SQLite** + `DatabaseService` 的
真实实现，而不是手写 SQL 重建一遍行为 —— 后者测的是「我理解的本地实现」，
不是本地实现。

也正因为如此，**两侧接口形状不同**的地方会在这里暴露出来，而它们全是只有对账
才看得见的：`updateReviewPaper` 本地是**整体覆盖**而服务端是**掩码**（执行器
于是必须「读回来 → 套掩码 → 整行写回」，这也正是 `ReviewController` 的做法）；
`updateReviewMistakeState` 则两侧都是掩码。详见迁移计划 §6.2。

## 起点对齐：为什么两侧都先清空业务表

两侧的种子**不同源**：本地走 `DatabaseService.seedIfEmpty()`（演示账号 + 关系 + 若干作业），
服务端执行器直接写 SQL 造账号。

所以「比对种子数据」既无意义、也不可能通过。对账的对象是**同一串操作产生的行**，
起点只能是「业务表为空、**账号**在」。

⚠️ **2026-09-21 起，关系也不再是起点的一部分。** 它原先和账号一起躺在种子里
（后面那些「家长身份」的步骤要靠它算出可见的孩子，看着像非有不可）。但那样一来
它就**永远进不了 dump 列表** —— 两侧的种子行不同源、比对必然失败 ——
而它是**可见集合（家长看得见哪个孩子）的来源**：状态词写错只会表现为
「后面某一步 403」，错误本身在报告里一个字都看不见。

现在它被清空、由序列头两步（邀请 → 接受）重新产生。连带的两处调整：
服务端种子**不再插关系行**（会被 `truncate` 一起清掉，留着只会让人以为它有用），
账号补上了 `phone`（邀请是按手机号找人的，这正是 `lookupUserByPhone` 存在的理由）。
**顺序从此有意义**：关系重建必须排在任何依赖「家长可见集合」的步骤之前。

### 顺带撞出来的：本地两张运动表原先**并不幂等**

补 `workout_*` 时，序列把每次插入都做两遍（重试），本地那一侧**直接抛了**
`UNIQUE constraint failed` —— 而服务端那一侧回的是「还是那一行」（`created: false,
reused: true`）。也就是说：**同一个动作，本地报错、云端成功。**

为什么此前没有被任何人看见：两个调用方都把它包在 `_safePersist` 里
（`student_controller.dart` / `parent_controller.dart`），异常被吞掉之后，
**库里都是一行**，列表里也都是一行 —— 界面完全一样。但「id 是幂等键」这条契约
只是**碰巧**成立的：它依赖调用方继续吞异常。换一个不吞的调用方，两边立刻分叉。

修法是把本地那两处 `insert` 加上 `ConflictAlgorithm.ignore`，与服务端的
`on conflict (id) do nothing` 同形（契约注释本来就写着「重试**复用同一个 id**，
重复提交就**撞主键**」—— 撞了之后怎么办，两侧原先各自决定，现在统一成「保留原行」）。
判据是 `test/workout_idempotency_test.dart`（3 条）：

1. 同一条记录提交两次 → 库里一行、且是**原来**那一行（`minutes` 仍是 30，不是重试的 99）；
2. 同一个计划新建两次 → 同上；
3. **不同 id 的两条都在** —— 这条是必需的：前两条只断言「只有一行」，
   一个「什么都不插」的实现同样能通过。幂等与失效必须分开。

**已验可证伪**：把 `ConflictAlgorithm.ignore` 去掉重跑，第 1 条立刻
以 `UNIQUE constraint failed` 失败。

## 归一化：为什么 id 不能直接比

R2 说 ID 由服务端生成，所以两侧的 id **必然不同**，而 22 张表之间有外键引用。
比对器因此按**别名**归一化：序列里写 `$hw1`，两侧执行器各自解析成自己的真实 id，
dump 时带上 `别名 → 真实 id` 的映射，比对器再把它反查回去。

于是配对是**精确**的（用归一化后的 id 配对），差异能落到具体字段。
按索引逐行比是不行的：一侧多一行就会让全表错位，报出一堆「看起来全都不对」的差异，
而真实原因只有一个。

列名也要归一化：本地是 camelCase（Dart `toMap()` 的产物）、服务端是 snake_case。
不归一化的话，每一列都会被报成「仅本地有 `studentId` / 仅服务端有 `student_id`」，
真正的行为差异会被淹没。

**id 会嵌在别的字符串里** —— 所以替换必须发生在字符串**内部**，不能只认整串相等。
幂等键的形态就是 `plan:<planId>:<date>`（`PointController.planKey`）。只认整串的后果是
每一轮都报两条「`idempotency_key` 不同」，而人一旦习惯忽略它，真差异也就没人看了。
按真实 id **长度降序**替换：`L_pt1` 是 `L_pt1_reversal` 的前缀，短的先替换会把长的换坏。

**DATE 列（`study_plan_checkin.date`）不能用「时刻」表达。** 它记的是「打卡记到了
哪一天」，而 PG 的 `date` 经 node-pg 出来是**本地时区午夜的 `Date`** ——
实测 `2026-09-18` 变成 `2026-09-17T16:00:00.000Z`（Asia/Shanghai），
直接 `toISOString()` 会把这个日子说成前一天，正好是这条数据最要紧的那个错。
服务端 dump 侧按列类型（`information_schema.columns.data_type`）输出 `YYYY-MM-DD`，
与本地 SQLite 存的形状对齐；比对器保留一条 `dateOnly` 兜底，
万一某张表漏了处理，它会报一条**看得懂**的差异而不是一句「日期不一样」。

**`reversed_at` 只比「有没有值」。** 它记的是撤销发生在哪一刻，而那一刻在两侧
必然不同（本地设备时钟 / 服务端 `now()`，R3）。但没有把整列加进白名单 ——
`空 ↔ 非空` 正是「这笔到底有没有被撤销」，抹掉它就等于放过「撤销没生效」这个
bug。所以只把值归一成同一个哨兵，空值仍然是空值。

## 白名单：每一条都要能说清「为什么它必然不同」

出口有四种，强度从弱到强，选哪一种本身就是一次判断：

| 类别 | 位置 | 强度 | 含义 |
|---|---|---|---|
| `IGNORE_VALUES` | `compare.mjs`，按列名 | 最弱 | 该列的值**不参与比对**（此后不再看它） |
| `KNOWN_COLUMN_SET_DIFF` | `compare.mjs`，按表 | 弱 | 列集差异的已知项（照常打印，不算失败） |
| `vocabDiff` | `scenario.json` | — | 两侧枚举值域不同。照常打印、不算失败，但它必须交代「场景里为什么只能用交集值」 |
| `behaviorDiff` | `scenario.json` | **最强** | 两侧行为故意不同，**对着清单核**：多一条、少一条都会报错 |

**它们都是报告的出口，不是「悄悄放过」**：命中的条目会照常打印出来。
不写理由的条目应该被视为待查项 —— 白名单一旦开始「顺手加一条」，
它就会慢慢长成「什么都不比」。

一个能用 `behaviorDiff` 表达的差异，**不要**降级成 `IGNORE_VALUES`：
前者会随行为变化报警（那正是我们要的），后者只会安静地不再看那一列。

## 已知差异（每一处都要能说清「为什么」）

| 差异 | 位置 | 为什么 |
|---|---|---|
| `homework.user_role` 仅本地有 | `KNOWN_COLUMN_SET_DIFF` | 服务端既不写也不读它；两侧对任何读者呈现的值相同 |
| 记录时间（`created_at` / `issued_at` / `expires_at`） | `IGNORE_VALUES` | R3：本地是设备时钟、服务端是 `now()`，必然不同且不同是对的 |
| `review_summary.generated_at` | `IGNORE_VALUES` | 同上。⚠️ 这条白名单**掩着一个已知隐患**：`scopeKey` 由客户端按设备日期算，两者可能落在不同的周 |
| 通知（服务端 6 条 / 本地 0 条） | `scenario.behaviorDiff` | 陷阱⑦：通知的产生位置搬到服务端 —— 这正是迁移要做的事 |
