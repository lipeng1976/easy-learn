## 1. 为什么必须分家

改之前学生端「复习」页的第一屏是：

```
[今日概念训练]        ← 每天要做
[英语单词打卡]        ← 每天要做
[掌握率 + 生成错题资料]  ← 针对错题
[待复习 105 / 复习中 3 / …]
```

两块「今日任务」压在错题状态上面，造成两个具体问题：

1. **心智模型互斥**：概念训练是「今天的一组题」，错题复习是「一个闭环走到哪一步」。
   混在一页时，孩子会以为概念训练也是错题派生出来的，于是「做完 6 题」被当成
   「复习完了」。
2. **顺序错了**：复习页的第一屏应该回答「我还有哪些题要复习」。日常打卡抢了位置，
   真正的错题状态被推到下面还要滚一屏。

计划页本来就装着「今天要做的事」（学习计划打卡、专注计时、阅读），把日常打卡并过去之后，
两页各自只有一个主题：**计划 = 今天做什么，复习 = 做错的题怎么办**。

## 2. 学生端概念打卡（`/checkin`）的两半

### 2.1 未完成：一行一份 + 科目色

保持原样（`_TaskTile`），唯一的变化是左边那个 40×40 方块从**主题蓝**改成**本科目的颜色**
（`subjectColor()`，与家长端色块同一套）。理由：同一天家长可能出了数学和英语各一份，
孩子按颜色扫一眼就知道哪份是要动脑算的、哪份是背单词。

### 2.2 已完成：科目大色块 → 记录页

```
已完成                           12 份
┌ 数学 ──────────┐ ┌ 语文 ─────────┐
│ ■ 数学      12 份│ │ ■ 语文      3 份 │
│ 最近 4/5 · 11-10 │ │ 最近 5/5 · 11-09│
│ 看记录 ›         │ │ 看记录 ›        │
└─────────────────┘ └────────────────┘
```

点进去是 `/checkin-subject`（`CheckinSubjectPage`）：

- 顶部：`数学 · 打卡记录`，`共 N 份`；
- 每行：`11-10 · 基础 · 共 5 题` + 右侧得分徽标；
- 点一份 → **页内**展开成绩单与逐题回放（`CheckinResultPaperCard`），
  顶部「记录列表（共 N 套）」回退；
- 列表分页（10 条/页 + 加载更多），下拉可刷新。

为什么详情不再 push 第三层：孩子只是想看一眼那套错在哪，三层返回路径太长；
而「页内两态」在本项目的打卡页已经跑熟（`_openQuizId`）。

### 2.3 家长端不受影响

同一个页面按角色分支：家长看的是「最近孩子做了什么」，保持**时间倒序平铺**（每份直接给分）。
汇总接口对家长也会返回，但页面不用它 —— 少一次点击。

## 3. 数据：为什么新增 `GET /data/checkin/summary`

分组色块要显示每科的**真份数**。三条路只有一条可行：

| 方案 | 问题 |
|---|---|
| 数已加载的 `doneRuns` | 分页 10 条时数字会骗人（12 → 7），且不报错 |
| `limit=0` 拉全量再自己分组 | 每份带题干/答案/解析，几十份就是几百 KB；这条链路被「大响应卡死」坑过 |
| **`group by` 一次算完** | ✅ 只回计数与最近一次成绩，不含题目 |

响应：

```json
{ "studentId": "stu_001",
  "subjects": [
    { "subject": "数学", "done": 11, "lastSubmittedAt": "2026-11-10T10:27:16Z",
      "lastScore": 4, "lastTotal": 8 }
  ] }
```

SQL 要点：

- `join checkin_result` 是**内连接**：没交卷的归「未完成」那半页，两边数字加起来等于总数；
- `coalesce(nullif(trim(subject),''), '其他')`：科目为空的历史行归「其他」，
  否则它们会在分组里**消失**（列表页把它们显示成「综合」）；
- `lastScore` / `lastTotal` 用 `array_agg(... order by submitted_at desc)[1]`，
  且**缺失时回 `null` 而不是 0** —— 0 分是「做过且全错」，null 是「没有这份数据」。

列表接口则新增可选 `subject` 过滤（`GET /data/checkin/quiz?status=done&subject=数学`）。
**不校验白名单**：读接口为了一个拼错的科目名回 400，只会让整块页面报错，什么也修不了。

## 8. 2026-11-12 晚：三张卡合并成「一个大方块」

虫子原话：
> 刚刚生成的题目，在计划标签页里放在每日概念打卡下方，这里和每日概念打卡一样
> 都是花几分钟做的小练习，可以放在一起，例如一个大方块，里面列出这些训练项。
> 数学的蓝色和界面的灰色接近了，不够醒目，可以换一个醒目点的颜色。

### 8.1 版面

```
今日打卡                          每天做一遍 · 每次几分钟
┌──────────────────────────────────────────────┐
│ [✓] 每日概念打卡          待完成 2 份        › │
│  ┃ ● 数学  共 5 题 · 基础 · 11-12      去做  › │
│  ┃ ● 英语  共 3 题 · 11-11            去做  › │
│ [译] 今日概念训练              6 题          › │
│ [ab] 英语单词打卡         10 题              › │
└──────────────────────────────────────────────┘
[英文阅读卡]                ← 仍是独立卡，见 §8.2
```

- **一张卡**（`DailyPracticeBlock`）里逐行列出三件小练。原来各占一张卡，
  每张都带一句说明和一个大按钮，孩子要读三遍才知道「今天有哪几件小事」。
- **刚出的题挂在「每日概念打卡」下面**：一份一行（科目色圆点 + 题量 +
  日期 + 「去做」）。原来只有一个「待完成 N 份」，孩子得点进打卡页
  才知道是哪几科、几道题。
- 最多列 **3 份**，其余折成「还有 N 份 ›」—— 一次出十份时全列出来会把
  「学习计划」整区顶出屏幕，而真要做的往往就是最上面那一两份。
- 行内没有大按钮：这一区是**清单**，点行本身就是动作。

### 8.2 阅读为什么不并进去

阅读是**一本书的长期任务**（没读顺延、一直挂到整本读完），和「今天做完
就没了」的小练不是同一个时间尺度。混进来会让「今天还剩几件事」这个数字
一半按天算、一半按书算。

### 8.3 明细从哪来

`CheckinEntryState` 原来只存两个数（pending / total），`load()` 拉列表时
`limit: 1`。现在多存一份 `pendingByStudent`（`limit: 6`，最多列 3 行），
`applyCounts` 增加可选的 `pendingQuizzes`：

- 带明细 → 覆盖（交卷后那一份要消失）；
- 不带（老调用点只有计数）→ **保留原明细**，硬清空会让计划页那几行
  忽然消失，而孩子什么都没做。

`CheckinController._syncEntryState`（load / 出题 / 交卷三个时点）把
`pendingRuns` 的 quiz 一起推过去 —— 只推计数的话，出完题回到计划页
还是看不到那一行。

### 8.4 配色：数学的蓝不再是「灰」

页面底色是 `#F5F7FF`（淡蓝灰），数学原来是 `#378ADD`（钢蓝）配 12% 浅底
—— **同色系的浅底叠在淡蓝灰上等于没有颜色**，所以看着像灰。

- `kSubjectColors['数学']`：`#378ADD` → `#1F6FEB`（饱和度更高）；
- 色块浅底：家长端 `0.12 → 0.18`、学生端打卡行 `0.12 → 0.18`、
  已完成科目块 `0.10 → 0.16`（边框 `0.35 → 0.45`）。

判据 `checkin_subject_summary_test` 里那条「色块底色 = 语文科目色」
跟着从 0.12 改到 0.18 —— 它断的是「用的是科目色而不是主题蓝」，
不是那个具体数字。

### 8.5 降级

本地模式（没连云）**不画「每日概念打卡」那一行**（题目快照在服务端，
本地库没有），但概念训练与单词打卡全在本机，照常可用。判据里用
`DailyPracticeBlock(isCloud: ...)` 这个只给测试用的注入点验这条 ——
假库里 `DatabaseService.isCloud` 恒 false，没有这个口子就验不了
「云模式那一行在不在」。

## 9. 2026-11-15：已完成列表里把「今天完成」单独框出来

虫子原话：
> 在家长端看计划-》打卡记录与历史里，分为未完成和已完成，需要在已完成列表里，
> 把今天完成的，用一个方框单独框出来，能一眼就能看出当天做了哪些，
> 而不需要去一条条看打卡时间。

拍板口径（AskUserQuestion）：**按交卷时间**判定 / 方框**带标题与份数** /
**两端都改**（家长平铺列表 + 学生汇总取不到时退回的平铺列表）。

### 9.1 版面

```
已完成                            31 份
┌──────────────────────────────────────┐
│ ▦ 今天完成                    7 份  │
│ ┌ 语文  完成 11-15 · 基础 · 共 5 题 ┐ │
│ ┌ 数学  完成 11-15 · 共 8 题      ┐ │
│ └──────────────────────────────────┘ │
└──────────────────────────────────────┘
  英语  完成 11-14 · 共 6 题          ← 更早的照旧平铺，不进框
  [加载更多]
```

### 9.2 口径：交卷日 ≠ 出题日

`quiz.quizDate` 是**出题日**，`checkin_result.submitted_at` 才是**交卷日**。
家长头晚出题、孩子次日做，两者差一天 —— 本机库真库查到 `quiz_date=11-12/11-13`
而 `submitted_at=11-14` 的行；真路由探针 20 条已完成里 **6 条跨天**。
按出题日分组会把「今天刚做完的」漏出框外，而且**不报任何错**。

链路（服务端零改动）：

| 环节 | 改动 |
|---|---|
| `GET /data/checkin/quiz` | 早就在 `result` 里回 `submittedAt`（`r.submitted_at`），无需改 |
| `CheckinSubmitResult` | 新增 `DateTime? submittedAt`；`fromJson` 解析、`judge` 带本机时钟、`copyWith` |
| `CheckinController.submit` | `judge(submittedAt: _clock())` —— 交卷就发生在这一刻 |
| `CheckinController._store` | `POST /data/checkin/submit` **不回**交卷时刻，换成存档真值时用 `copyWith` 保留本机那个；丢掉它，跨天那份就漏框 |
| `checkinDoneDateKey()` | 单点判定：有 `submittedAt` 取**本地日**，老服务端缺字段才退回出题日；**绝不猜成今天**，否则所有历史行一锅端进框里 |
| `_TaskTile` | 已完成行日期改显示**完成日**（避免「今天完成的框里标着 11-14」），未完成仍显示出题日 |

### 9.3 份数不许骗人

已完成是服务端分页（10 条/页）。第一页全是今天且 `doneHasMore` 为真时，
下一页可能还有今天的 —— 写死「10 份」就是 §0 决策 5 反复治过的那个错。
所以框头只在**确定到底**（本页已出现更早记录，或没有下一页）时写 `N 份`，
否则写 `N+ 份`（至少 N 份）。

### 9.4 降级与边界

| 场景 | 表现 |
|---|---|
| 今天一份都没完成 | 不画空框，历史照旧列出 |
| 老服务端不给 `submittedAt` | 退回出题日；不会把历史误判成今天 |
| 学生端汇总接口正常 | 走科目色块，本来就没有逐条列表可框 |
| 学生端汇总取不到 / 家长端 | 平铺列表，框生效 |
| 服务端改动 | **零**，云版 App 只需更新客户端 |

### 9.5 判据（`test/checkin_today_done_test.dart`，11 条）

| 判据 | 盯什么 |
|---|---|
| `submittedAt` 解析 / `judge` 带时钟 / `copyWith` 保留 | 字段真从服务端进来、交卷那一刻真记下 |

## 10. 2026-11-16：交卷后记积分

「每日练习」从这一版起能赚积分。**两项分开定价**，都进家长端「积分 → 每个动作值多少分」：

| 动作 code | 名称 | 默认 | 触发 |
|---|---|---|---|
| `checkinCompleted` | 每日练习完成 | 5 分 | 交卷成功，**不看对错** |
| `checkinAllCorrect` | 每日练习全对 | 5 分 | 同一组题 `score == total`，**额外**再记一笔 |

### 10.1 为什么是两笔而不是「全对给 10 分」

家长要能分别定价。合成一笔的话，「完成」的分值就藏进「全对」里 ——
孩子错一道就一分没有，而「做完」本身是应该被鼓励的。
想只奖励全对的做法是**把「完成」那项关掉**，而不是改代码。

### 10.2 时机：存档成功之后，不是判分之后

```
交卷 → 本机判分（立刻显示）→ 提交服务端存档 → 存档成功 → 记账
```

先记账再存档的话，弱网下孩子会看到「+5」，而库里根本没有这份卷，
家长端账本上也找不到对应的那一次练习。分与卷必须成套。

判据 `test/checkin_points_test.dart` 里那条「存档请求失败时不发分」盯着这一步
（真还原：把记账挪到判分之后 → **恰好 1 条红**）。

### 10.3 幂等：键是 quizId

- `checkin:<quizId>`（完成）
- `checkin_all_correct:<quizId>`（全对）

用 quizId 而不是日期：每次出题都是新的 `ck_<uuid>`，同一份卷反复「重试存档」
只记一次分；按日期做键会把家长同一天出的第二组题吞掉（那组孩子也是真做了的）。

⚠️ 两个键**前缀必须能区分**。共用一个前缀会撞上部分唯一索引，
症状是「完成有分、全对没分」且完全不报错。

### 10.4 降级

- 记账抛错（分值表读不到 / 仓库没接上 / 云端配额）→ **只写一条 debug 日志，
  交卷照常成功**。积分是奖励，不是账目真相。
- 家长把某一项关掉 → 那一项不发，另一项照发。
