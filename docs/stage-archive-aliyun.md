## 1. 结论

阿里云这一阶段**跑通了**，而且是端到端真跑通的（不是"配好了"）：

- 双端 App（家长 / 学生）· 服务端两函数 · 客户端 SQLite → 云端 PostgreSQL · 照片走 OSS
- **四个产物全部在线上且验过**：数据服务 + AI 网关 + APK + Web
- AI 接入走百炼（`AI_MODEL_PROVIDER=bailian`），三档模型（vision / reasoning / light）
- 复习闭环 + 作业识别/批改/编辑 + 错题库 + 家长端联动的完整链路可用

**遗留的一条主缺陷**：B29「做对的题被判错、假错题进错题库」—— 根因已定死并有三轮受控实验证据，**修法未拍板、生产未改**。

## 5. 换云厂商的接口边界（**这一节是给火山用的**）

本项目的架构是**分层**的，换云**不是重写**。分清三圈：

### 5.1 完全不用动的（占绝大部分）

- **客户端全部 Dart 代码**（`lib/`）—— 它只认 `--dart-define` 给的 URL
- **业务逻辑、路由表、RLS 策略、迁移 SQL、词表、DAO 映射**
- **服务端全部业务代码**（`serverless/*/src/`）—— 只要两个入口 URL 不变
- Web 产物（在 WorkBuddy 域名上，与云厂商无关）

### 5.2 只需改配置的

| 要改的 | 现状 | 火山对应 |
|---|---|---|
| **模型厂商** | `AI_MODEL_PROVIDER=bailian` | 改 `ark`（**本来就是默认值**，见 §5.3） |
| **API Key** | `ARK_API_KEY` = 百炼的 key | 换火山方舟的 key（**变量名不用改**） |
| **模型 ID** | `qwen3.5-omni-plus` / `qwen3.8-max` / `qwen3.8-flash` | 换成方舟的（**豆包系列，qwen 在方舟上没有**） |
| **截图/TOS** | `OSS_*` 五个变量 | 换 TOS 端点 / 桶 / 密钥 |
| **数据库** | `PG*` 一堆变量 | 换火山 RDS 的连接信息 |
| **区域** | `s.yaml` `vars.region: cn-hangzhou` | 火山的地域 ID |

### 5.3 ⭐ **大模型这一侧：项目原生就是方舟，几乎是零改动**

这不是推测，是代码事实：

- `config.js:263` → `export const DEFAULT_MODEL_PROVIDER = 'ark';`
- `config.js:189` → `ark` 的注释原文：「**行为完全不变**，是这一次改动前的唯一路径」
- `ark.js:18` → 数据面地址 `https://ark.<region>.volces.com/api/v3/chat/completions`
  —— 与方舟**逐字一致**
- 09-24 才切到百炼，两家差异已经在 `MODEL_PROVIDERS` 这张表里逐条记着（思维链字段、
  `tool_choice` 能否传对象、会不会序列化嵌套结构），且**新增一家厂商只改这张表**

⇒ **换火山 = 把 `AI_MODEL_PROVIDER` 去掉（回落 ark）+ 换 key + 换模型 ID。**
代码路径是**已有的**，不是新写的。

⚠️ **但有三件事必须重测，不能靠"本来就是方舟"推断**：

1. **`tool_choice` 传对象 + 思维链**的交互 —— 表里记的是历史实测，**方舟当前版本要重测**
2. **`stringifiesStructuredArgs`** —— 表里记方舟 `false`。这条如果错了，结构化输出会静默坏掉
3. 🔴 **B29 的模型选型结论全部作废重来**。现有结论（omni-plus 0/6 · max 6/6 · flash 6/6）是
   **在百炼模型上**测的；换到豆包是**换了一批模型**，那些数字一个都不能沿用
   ⇒ `llm-grading-false-positive-triage` 那套探针要**原样重跑一遍**

### 5.4 必须重做的（工程量所在）

| 项 | 说明 |
|---|---|
| **函数服务** | FC3 → **veFaaS**。`s.yaml` 结构兼容（都是 Serverless Devs），但**组件名不同**（`fc3` → 火山组件），ACL / 触发器 / `logConfig` 写法要重写 |
| **数据库** | 见 §5.5 —— **有版本落差要处理** |
| **对象存储** | OSS → **TOS**。`IMAGE_DRIVER` 已有 `oss` / `fs` 两种，要加 **`tos` 驱动**，并复用 `buildStorageKey` 单点（键格式不许第二处定义） |
| **共享 KV** | 生产必须换成真共享 KV（火山 Redis / 表格存储之类），**不能再靠 `AI_ALLOW_EPHEMERAL_KV` 逃生门** |
| **部署工具链** | `tools/build-cloud-*.mjs` 里写死的地址要换；`build-mode.mjs` 的闸门、`walkthrough-live-web.mjs` 的探活地址都要改 |
| **CORS** | B24 那条 OPTIONS 短路是**代码里的**（`app.js` 开头），跟着代码走，不用重做 —— 但要**重新验一遍平台的预检行为**（这是平台差异，不是代码差异） |

### 5.5 ⚠️ 数据库版本落差：**现网 PG 18.4 → 火山最高 PG 17**

- 火山 RDS for PostgreSQL **2025-04-22 才支持 PG 17**（这是当前最高的）
- 但**影响很小**，因为：
  - 迁移脚本注释第一行写的是「**目标：PostgreSQL 17**」，本来就是照 17 写的
  - 全仓扫描 `gen_random_uuid` / `uuidv7` / `identity` / `virtual` generated column /
    `not enforced` 等 PG 18 特性 —— **0 命中**，没有任何依赖
- ⇒ **降到 17 理论上无痛**，但仍要走完整迁移 + **行为判据**
  （⚠️ **别用"迁移成功"推断"隔离生效"** —— RLS 要行为判据，不是"脚本跑完了"）

## 6. 复现线上状态缺什么

要紧的缺口：**线上四个产物对应的代码没提交**。也就是说——

- 今天能重建出一样的 APK / Web / 两个函数，靠的是**工作区的未提交文件**
- 一旦这个工作区丢了，**线上状态无法复现**

⇒ 换云之前，**先提交**（或至少打一个归档 tag / 把工作区打包）。
这一步不做，后面所有"迁移"都建在一份会消失的基础上。
