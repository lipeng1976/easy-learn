# 历史数据：查询、保留与清理方案

> 2026-09-22。起因是虫子报的一条体验问题：「首页作业、运动、计划那里，日历只有当周的，
> 没法查历史」。查下去发现它牵出三件事，而这三件事**必须一起定**，单独做任何一件都会返工。
>
> 结论先给：**加日历是对的，但「永久保留」这个决定会让「怎么查得动」成为真正的工程问题** ——
> 而当前没有任何一处能按月/按年查。本方案的核心是**把「翻得到」变成有判据的能力**，不是加一个按钮。

---

## 一、问题现状（已核实，不是推测）

### 1.1 日历只有本周 —— 而且**同一段代码抄了三份**

| 位置 | 类 | 选中态存放 |
|---|---|---|
| `lib/pages/student/tabs/homework_tab.dart:1391` | `_WeekCalendar` | `static final Rx<DateTime> _selectedDate`（**static**！） |
| `lib/pages/student/tabs/workout_tab.dart:622` | `_WeekCalendar` | `DateTime _selectedDate`（实例字段） |
| `lib/pages/parent/tabs/overview_tab.dart:246` | `_WeekCalendar` | 待核 |

三份的 `build` 逻辑逐字相同：`monday = today.subtract(Duration(days: today.weekday - 1))`
→ `List.generate(7)`。**都没有翻周/翻月的能力**，因为「今天」是硬锚点、只画 7 个格子。

⚠️ 更要紧的是 `homework_tab` 的选中态是 **`static`**：它是**跨实例共享的全局状态**。
这在测试里会串（一个用例改了选中日期，另一个用例看得见），也给「记忆上次查看位置」这类
需求留了个坑。**抽公共控件时顺手改成实例持有。**

### 1.2 计划页根本没有日历

`plan_tab.dart` 只讲「今天」：`'今天没有需要执行的学习计划'`、`_TodayCheckinBanner`。
它的日期语义与其他两页不同 —— 计划是**周期性的**（`weekdays` / `cycleType`），
「某一天做了什么」的载体是 `study_plan_checkin(student_id, date)`，
而 `study_plan` 本身是**跨越一段时间的规则**。所以计划页的「历史」是
**「那一天哪些计划该做、做了没有」**，不是「那一天创建了哪些计划」。见 §2.3。

### 1.3 没有「按月/按年查」的任何入口

- 客户端仓储签名一律无时间参数：`queryHomework(String userRole)`、
  `queryWorkoutRecords()`、`queryStudyPlanCheckins()`、`queryReviewMistakes()`…
- 服务端只有 `limit`，**没有 `from`/`to`**。极端例子：
  `listHomework` 是 `order by due_at desc limit clampLimit(默认 50、上限 200)`。
  也就是说**作业存够 200 条之后，今天之前的历史永远读不出来** ——
  不是慢，是**结构性取不到**。
- `workout.listRecords` 默认 `limit 100`（上限 500），同理。

📌 **这条要单独记住**：`LIMIT` 是**分页**，不是**时间窗**。用 limit 当时间窗的后果是
「数据一多，最近的那部分就把老的全挤掉了」，而且**界面看起来完全正常**（显示 50 条，
只是那 50 条全是最近的）—— 典型的静默失败。

### 1.4 数据规模其实很小（所以「永久保留」是对的）

按演示栈的种子口径估：一个孩子一天约
作业 1–3 条 · 运动记录 1–2 条 · 打卡 1–3 条 · 错题 0–5 条 · 积分 2–5 条 ≈ **十几行/天**，
一年 **五千行量级**，十年五万行。PG 面对这个量级毫无压力。

**所以「永久保留」不需要为了省空间而做任何事 —— 真正的成本在查询路径，不在存储。**

### 1.5 现在没有任何清理机制（这是好事）

全仓扫过：没有 TTL、没有归档任务、没有 `delete from … where created_at <`。
唯一的删除都是**业务删除**（删错题时连带删它的作答/影子比对/练习/讲解，
见 `local_database_service.dart` 的 `deleteReviewMistake`）。**这个状态是干净的，别去破坏它。**

### 1.6 现有的时间索引

```
idx_homework_student_status    (student_id, status)          ← 没有 due_at
idx_study_plan_checkin_student (student_id, date)
idx_workout_record_student     (student_id, start_at DESC)
idx_review_attempt_student     (student_id, created_at DESC)
idx_daily_comment_student      (student_id, created_at DESC)
idx_point_ledger_student       (student_id, created_at)
idx_notification_target        (target_user_id, created_at DESC)
idx_chat_message_relationship  (relationship_id, created_at)
```

**按天/按月查需要的是 `(student_id, <时间列>)` 的复合索引。** 现在 `homework` 缺
`due_at`、`review_mistake` 缺时间列、`study_plan` 缺 `created_at`。
规模小的时候不建也能跑，但§3 会说明**为什么这个索引是「判据的一部分」而不是优化**。

## 二、查询方案

### 2.1 交互：加一个按钮弹完整日历（维持三页一致）

```
┌──────────────────────────────────────┐
│  一  二  三  四  五  六  日      📅  │   ← 右侧一个日历图标
│  16  17  18  19  20  21  22          │      点它弹完整月历
│              ↑今天                    │
└──────────────────────────────────────┘
```

弹层里要有**四样**，少一样就会立刻回来问第二次：

1. **可翻月**（左右箭头 + 年月标题），
2. **有数据的日期打点**（下面 §2.2，这是「能不能翻」的关键），
3. **回到今天** 按钮（翻远了没有回来的路，是最常见的抱怨），
4. **可选范围边界**：不早于「这个孩子第一条数据的那天」，晚于今天不可选。

选中后：关闭弹层 → 周历**跳到那一周**并选中那一天 → 列表按那一天过滤。

**不做「无限翻」**：翻到没有数据的月份要能一眼看出「这个月没有」，
而不是让人一格一格点。所以 §2.2 的月份摘要必须有。

### 2.2 关键设计：**按月摘要 + 按天详情**，不是「按天逐次查」

如果弹层里每点一天发一次请求，会有两个问题：①翻月时日历不知道哪天有数据（打不了点）；
②家长连点几天就是连发几次请求。

所以拆成两个调用：

| 调用 | 语义 | 用途 |
|---|---|---|
| `GET /data/calendar/summary?month=YYYY-MM` | 这个月**每天有几条**（作业/运动/打卡各自计数） | 日历打点、判断「这个月是不是空的」 |
| `GET /data/homework?from=…&to=…`（已有端点加时间窗） | 某天的明细 | 列表 |

**摘要的形状**（一行一天，空的天不返回）：

```json
{ "days": [
  { "date": "2026-09-22", "homework": 3, "workout": 1, "checkin": 2 },
  { "date": "2026-09-20", "homework": 1, "workout": 0, "checkin": 1 }
] }
```

为什么是这个形状而不是「一次返回三张表的并集」：
**日历只需要「有没有、几条」**，明细等真的点进去再取。这既让摘要很便宜
（三个 `group by date` 各扫一个月），又避免把整月明细塞进首屏。

### 2.3 三页的「某一天」语义**不一样**，别硬统一

| 页 | 「这一天」是什么 | 数据来源 | 过滤键 |
|---|---|---|---|
| 作业 | 那天**到期**的作业 | `homework.due_at` | 同一「本地日」 |
| 运动 | 那天**发生**的记录 + 那天**该做**的计划 | `workout_record.start_at` + `workout_plan` 的周期规则 | 记录按本地日；计划按 `weekdays`/`cycleType` 推导 |
| 计划 | 那天**该做**的计划 + **打卡有没有打** | `study_plan` 规则 + `study_plan_checkin.date` | `date` 是**日期列**（无时区），不是 timestamptz |

⚠️ 两个坑：

- **作业按 `due_at`（timestamptz）过滤，必须先转成本地日再比。**
  现在的 `_isSameDay` 是客户端做的（取 `toLocal()`），服务端时间窗也必须落在
  「本地日 → UTC 区间」上，否则跨零点会偏一天。这不是理论问题：
  项目里已经因为「时间上行不带时区 → 服务端按服务端时区解释 → 静默偏一整天」踩过一次（R3）。
  **约定：客户端算好 `[本地日 00:00, 次日 00:00)` 对应的 UTC 瞬时，作为 `from`/`to` 传上去**；
  服务端只做 `due_at >= from and due_at < to`，**不做时区推断**。
- **计划的「那天该做」是一条规则推导，不是一个状态快照。**
  所以「三个月前那天该做哪些计划」是**用今天的规则去回放**推出来的 ——
  如果中途改过计划（停用、改周期），回放结果与当时看到的**不一致**。
  这是**已知且可接受**的（我们不存「每日计划快照」），但要在界面上诚实：
  历史日期展示「按当前计划推算」，不假装是当时的截图。见 §5 待定项 Q1。

### 2.4 服务端改动清单（都做成**可选参数**，不传就维持现状）

| 端点 | 加什么 | 兼容性 |
|---|---|---|
| `GET /data/homework` | `from` / `to`（ISO 瞬时） | 不传 = 现有行为（`order by due_at desc limit 50`） |
| `GET /data/workouts/records` | `from` / `to` | 不传 = 现状（limit 100） |
| `GET /data/study-plan/checkins` | `from` / `to` | 不传 = 现状 |
| `GET /data/calendar/summary` | **新增** | 新端点，风险为零 |

**硬约束（照项目已有的规矩来）**：

- **`limit` 仍然要 clamp**（≤200/≤500）。加了时间窗之后，`limit` 的角色变回
  「防止某一天数据异常多时把响应撑爆」，而不是「取多少条历史」。
  ⚠️ **`from`/`to` 不能有默认值**。给个默认（比如「最近 90 天」）看着友好，
  实际是把「取不到」从**报错/慢**变成**静默的少数据** —— 正是本项目最恨的那类 bug。
- **时间窗一律走 `ctx.students`**，不接受客户端传 `studentId` 来扩大范围
  （`bootstrap.js` 的注释专门写过这个陷阱：`query` 只表达口径，**从来不表达权限**）。
- **`from > to` 要报 400**，不要静默返回空。返回空的后果是「家长以为那段时间没记录」。
- 索引：`homework` 补 `(student_id, due_at)`，`review_mistake` 补 `(student_id, last_wrong_at)`。
  小规模下 PG 走 seq scan 也能跑，**但见 §3.3 —— 这个索引是判据的一部分**。

### 2.5 客户端改动清单

1. **抽公共控件** `lib/widgets/day_calendar.dart`（或 `lib/pages/shared/`）：
   - `WeekStrip`：7 格，接受 `selectedDate` / `today` / `onDateSelected`，**实例持有选中态**；
   - `MonthPickerSheet`：可翻月 + 打点 + 回今天 + 范围钳制；
   - 三处引用一起替换，`grep -rn "class _WeekCalendar"` **必须归零**。
2. 选中态从 `static` 改为实例字段（顺手修掉跨实例串状态的隐患）。
3. 仓储层加可选时间窗参数：`queryHomework(role, {DateTime? from, DateTime? to})` 等。
   **默认不传** → 行为零变化，这条让改动可以分批上。
4. 弹层打开时按**当前选中月**请求一次摘要；翻月再请求那个月。摘要**按 (学生, 月) 缓存**在内存里，
   同月内来回翻不重发。

## 三、保留与清理方案

### 3.1 结论：**永久保留，不清理** —— 但要显式写下来

理由（三条，按重要性排）：

1. **数据量太小，清理省不下东西。** 十年五万行，PG 里也就几十 MB 含索引。
   为了省这个去做归档/搬迁，是拿「复杂度」换「几乎为零的收益」。
2. **删掉的是「孩子的成长记录」。** 两年前的暑假作业、第一次通过的复习卷、
   连续打卡的记录 —— 这是产品价值本身，不是垃圾。**这类数据的默认答案应该是保留。**
3. **清理机制本身会引入新的静默失败面。** 「删了之后界面怎么表现」这个问题比它看起来难得多。

### 3.2 但「永久保留」有三条**必须守住**的前提

| # | 前提 | 为什么 |
|---|---|---|
| P1 | **查询必须有时间窗能力**（§2.4），不能靠 `limit` 兜 | 否则「永久保留」= 「永久取不到」，比删掉更糟 |
| P2 | **必须能看见增长**（§3.4 的月报） | 需求会变；等发现时可能已经有一张表在悄悄膨胀 |
| P3 | **删除只走业务删除，绝不加「按时间批量删」** | 一旦有批量删，某次参数写错就是不可逆的数据丢失 |

### 3.3 有一个地方**必须**现在就想清楚：照片字节

文字数据永久保留没有代价，**照片有**：

- 库里存的是相对键，字节落在 `IMAGE_ROOT_DIR`（默认 `D:/easylearn/image`），
  目录按**月**分片（`imagestore.js` 的 `archiveDirOf`）。
- 每次作业提交 1–3 张图，手机拍的原图几百 KB 到几 MB。
  **一年下来是 GB 量级**，而且**照片是「不可再生」的** —— 删了没法重拍。
- 配额**已实现**（3000 张/学生 + 接近上限的提前提示）；**清理与冷热分层仍未做**，
  见 §3.6。存储后端**两条都有**（文件系统 / OSS，由 `IMAGE_DRIVER` 选）——
  这一节最初写的时候只有文件系统一份实现。

所以保留策略**必须把「文字」和「字节」分开**：

| | 文字数据 | 照片字节 |
|---|---|---|
| 保留 | **永久** | **永久**（同结论），但要加**配额与可见的用量** |
| 依据 | 成本可忽略、价值高 | 不可再生、成本真实、**无法事后补** |
| 需要做 | 时间窗查询 + 索引 | 单学生用量统计 + 配额上限（**已实现**，见下 Q2/Q3） |

⚠️ **在上云之前，这条必须定**：一旦上云，照片走对象存储，**计费从第一天就开始**，
到时候再想「要不要只留两年」就已经花掉钱了。现在定，成本为零。

**已定 Q2（2026-09-23）**：**每学生 3000 张**，上限走 `IMAGE_QUOTA_PER_STUDENT`
（默认 3000，服务端读，写错直接抛）。*同日从 10000 下调。*

口径从「按 2GB」改成「按**张数**」：张数是大人能直接对着孩子解释的单位，GB 不是。
⚠️ 换算成钱是这么算的 —— 单张上限 8MB 时 3000 张的**最坏**是 24GB/学生；
按实拍 1–3MB 估，现实区间约 **3–9GB/学生**。OSS 标准存储约 0.12 元/GB/月
→ **约 4–13 元/年/学生**。这不是「可忽略」，但也不是「值得为它改设计」的量级 ——
关键是它**能算出来**，而不是等账单。

**⚠️ 下调这件事本身就是设计**：按「一天 3–5 张」算，10000 张是 5–9 年、
3000 张是 **1.6–2.7 年**。前者「长到没人碰得到」，于是「照片只增不减」这个问题
永远不会被暴露；后者会让学生**真的撞上它** —— 那时就必须回答 §3.6 的问题
（删哪些、谁来删）。**故意让问题显形**，比等到某天某个学生突然传不上去要好。

**已定 Q3（2026-09-23）**：**达到上限硬拦 + 接近上限提前提示**。两件事都已实现。

- 超出时服务端回 `storage_quota_exceeded`（**409**，`retryable: false`）——
  必须与「网络抖一下」分开，否则客户端只会说一句「保存失败」，
  而学生要做的其实是**删旧照片**。
- 判在**两处**（刻意的重复，不是冗余）：`saveHomeworkImages`（写行，**权威** ——
  行才是「有几张」的定义）与 `uploadHomeworkImage`（写字节**之前**的预检 ——
  超限时不该先把字节灌进桶、再留一个没人引用的孤儿对象，白花存储）。
  ⚠️ 上传那处挡不住「只传字节、从不提交」的绕过，这是**已知且接受**的取舍；
  两处都是「先查后写」，并发下可能超出「一批」的量（上界 = 并发数 × 单批 30 张，
  相对 3000 可忽略）。要精确的账看 `npm run report:storage` 的月报，那里是读完再算。
- **「接近」的定义**：`IMAGE_QUOTA_WARN_REMAINING`，默认 **20 张**。
  **为什么不用百分比** —— 3000 的 10% 是 300 张，按一天 3–5 张算等于**提前两个月**
  开始喊；而这类提示唯一的用处是让人在**这几天内**做点什么。20 张是 4–7 天，
  这才是「这周不处理就会停下来」的量级。
  提示在**写行成功之后**带出（`saveHomeworkImages` 的响应里有 `photoUsage`），
  不是在上传那一步 —— 上传报的是**写之前**的行数，会少算本次这几张。

### 3.4 必须有的可观测性（P2 的落地）

**一个月报**（`scripts/report-storage.mjs`），输出每个学生的：
文字行数（按表）· 照片张数与字节数 · 最老一条数据的日期。判据：
**最老日期必须随月份推进而**不变**（如果它「变新了」，说明有东西在删数据）**。

这条判据的价值在于它**反向**工作：它不检查「有没有删」，而是检查
「最老的那条**还在不在**」。一个误删的清理任务会让它立刻报警，而任何
「统计总数」的报表都不会 —— 因为总数下降可以解释成很多正常原因。

### 3.6 撞上 3000 张之后怎么办（**未定 · 设计思考**）

⚠️ 与 §3.5 不是一回事：那是数据库里的**行**，这一节是对象存储里的**字节**。

3000 张按一天 3–5 张算约 1.6–2.7 年，所以这件事会在**这一代学生的使用周期内**
真实发生。三条路，列在这里是为了**下次讨论时不用从头想**：

**路线 A —— 手工删（学生/家长自己删旧照片）**

- ✅ 删什么由人定，不会误删「这张是孩子第一次写对的字」
- ❌ 学生要在**撞上限那一刻**才发现，而那时作业已经交不了了
- ❌ 不可再生的数据由用户自己丢，且**没有撤销**
- ⚠️ **现状缺口：现在连字节都删不掉。** `RemoteImageStorageService.deleteImage()`
  是空实现，OSS 后端也只有 `put` / `get` —— 也就是行能删（按作业清场），
  **对象还留在桶里继续计费**。选这条路要补三样：① 两条后端加 `delete`
  ② 一个按照片删的端点（现在只有按作业清场）③ 客户端选择与删除的界面
- ⚠️ **顺序必须是「先删行、后删字节」。** 反过来的话，删字节成功、删行失败
  → 行还在、字节没了 → 界面是**照片位置一片空白且不报错**（本项目最贵的一类失败）。
  先删行的话，字节删失败只是留一个没人引用的孤儿对象：用户无感，月报能发现

**路线 B —— 系统按归档期自动清理**

- ✅ 无人值守，额度不会满
- ❌ 要新建一套「删除」逻辑，而这份方案的 §3.5 与「文字数据保留永久」那条口径
  都站在它的对面；误删不可逆
- ❌ 「哪张该删」需要一个策略（最老？最大？按学期？），**每个策略都会被质疑**，
  而质疑一旦成立，删掉的东西就回不来了
- ⚠️ 硬约束：**不能碰「最近还在被读」的照片**。作业照片是作业的证据，
  家长要看、AI 批改要读。删了字节而留下行，界面就是一片空白且不报错
- 判据（真做的话）：清理跑完后，**最近 N 天的作业照片必须逐张能 GET 到**（正面），
  且月报里「**最老一条的日期**」按策略单调推进（而不是乱跳）

**路线 C —— 不删，降质归档（我更倾向这条）**

到某个时间点把旧照片**降分辨率**（例如长边 800px、JPEG 质量 70），
体积通常降到 1/10，而**照片还在**。它绕开了「删 / 不删」的二元对立：

- ✅ 孩子的成长记录不丢 —— 这是整份方案里唯一「不可再生」的东西
- ✅ 成本大降（3–9GB → 几百 MB，每年几毛钱量级）
- ✅ 「归档」的语义变成「**降质保号**」而不是「删除」，误判的代价小得多
- ❌ 要做一次转码（服务端要图像处理能力，或客户端在某个时机本地做）
- ❌ 降质**不可逆** → 要给用户一个「关键照片留原图」的口子

**我的建议：现在不动代码，先把「看得见」做掉。**

理由是**数据不足**：现在没有任何真实用量曲线，凭「一天 3–5 张」的估算是猜。
阶段 5 的月报会给出真实数字（每月新增多少张、最老一条是哪天），那时候再决定
删不删，成本是一样的；而现在就把删除逻辑写出来，等于在**还没有数据**的情况下
引入了一条不可逆的路径。

本轮已经做掉的是「**看得见**」那半边：接近上限时提前提示。没有它，
学生的第一次感知发生在「传不上去」那一刻 —— 那是最坏的时机。

### 3.5 为什么不做归档表 / 冷存储

写在这里是为了**下次有人提这个需求时直接引用**：

- 归档 = 同一份数据两种存放位置 → **每个查询都要写两遍**、每条读路径都要考虑
  「这段落在哪」。项目里最贵的一类 bug 就是「两条路径行为不一致」。
- 规模不支持：五万行用什么存放方式都是毫秒级。
- **什么时候该重估**：单学生文字行数 > 50 万，或单表 > 1000 万行。
  到那一天再谈分区（PG 原生 `partition by range` 比自制归档表干净得多）。

### 阶段 5 的基线（**这条要一直留着**）

`npm run report:storage` 在演示栈（`127.0.0.1:55433`）上跑出的**最老一条数据的日期**：

| 表 | 最老日期 |
|---|---|
| `homework` | **2026-09-22** |
| `review_mistake` | **2026-09-22** |
| `study_plan_checkin` | **2026-09-22** |
| `workout_record` / `homework_image` | （无数据） |

⚠️ **这份基线只对演示栈有效**。测试库（55434）每次跑测试都被 `rm -rf` + `initdb` 重建，
它的最老日期**不构成基线**（`pg-local.js:137`）。

**用法**：下次跑月报时逐个对照 ——
- 一模一样 → 历史完好（期望结果）；
- **任何一行变新 → 有人删了历史**，立刻查（全仓本该没有任何按时间删）；
- 变旧 → 正常（用户补录了更早的记录）。

这就是方案 §3 缺的那条**反向判据**：它查的是「最老那条还在不在」。
任何「统计总数」的报表都做不到这件事 —— 总数下降可以解释成很多正常原因。

### 实施中值得记住的两件事

1. **`pg` 把 `count(*)`（bigint）当字符串返回**：
   `count(*)` → `"14"`（string），`count(*)::int` → `14`（number）。
   `total += n` 会**拼字符串**。本脚本每一处 count/sum 都 `::int` 或 `Number(...)` 包了一层。
2. **月报数字会随 `dev-stack` 重启而增长**（它每次起栈都会重新灌演示数据，
   多出一行作业）。所以「两次跑结果不同」**不代表漏数** ——
   要验「同一栈内是否稳定」，必须在**一次 `--run` 里连跑两次**。实测两次完全一致（16 / 合计 34）。
