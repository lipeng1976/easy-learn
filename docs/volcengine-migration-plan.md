### 3.5 ⭐ **三档选型的实测结果**（2026-09-30，同判据跨厂商对照）

**做法**：把 B29 那套探针（逐字复用生产的 `prompts.js` / `schema.js` / `buildRequestBody`）
换一个 provider 原样重跑。**两个厂商在同一天、用同一份判据跑的**，所以可比。

| 模型 | 厂商 | 算式核对<br>（已验证全对，15 发） | 含真错<br>（必须报出，6 发） | 空白页<br>（必须拒绝，3 发） | `no_parse` | 429/异常 |
|---|---|---|---|---|---|---|
| `qwen3.5-omni-plus` | 百炼 | 9/15 | 6/6 | **0/3** | 0 | 0 |
| `qwen3.8-flash` | 百炼 | 11/15 | 6/6 | 3/3 | 0 | 0 |
| `doubao-seed-2-1-pro-260628` | 方舟 | — | — | — | — | **33/33 被限流** |
| `doubao-seed-2-1-pro-260915` | 方舟 | — | — | — | — | **33/33 被限流** |
| ⭐ **`doubao-seed-2-1-lite-260915`** | 方舟 | **15/15** | 6/6 | 2/3 | 2 | 0 |
| `doubao-seed-2-0-mini-260428` | 方舟 | 9/15 | 6/6 | **0/3** | 4 | 0 |
| 🔴 `deepseek-v4-pro-ga-260813` | 方舟 | 2/2 ⚠️**是幻觉** | **0/2** | **0/2** | 0 | 0 |

⚠️ `deepseek` 那一行的样本量与其余行**不同**（3 素材 × 2 发 = 6 发），
且它那个 2/2 是**假的满分** —— 原因见 §3.6，**不能与上面的 15 发那列直接比**。

**结论**：

1. **豆包能干活，而且比现网那只更好。** `doubao-seed-2-1-lite-260915` 在 15 发已验证全对
   的素材上 **15/15**，而现网正在用的 `qwen3.5-omni-plus` 只有 **9/15**（六成作答会被判错）。
2. **`lite` 是唯一没有 `no_parse` 的方舟模型**（它那 2 发 `no_parse` 全落在已撤标的 `ex1_block` 上）。
3. **两只 `pro` 根本没法评** —— 不是它们不行，是**账号侧被限死**（见下方行动项）。
4. **空白页那一关谁都没过。** 现网 `omni-plus` **0/3**、方舟 `mini` **0/3** 会在纯白页上回
   `score:100 items:[]`（= **一次批改清空错题库**）；`lite` 是 **2/3** —— 它每次都在 `summary` 里
   正确写出「这张照片是全白的…无法批改」，但**三次里有一次仍把 `score` 填成 100**。
   ⇒ 这是**偶发**，比稳定发作更难发现。**是代码侧缺一道闸，换任何模型都不解决。**
   （2026-09-30 复跑时 `lite` 在空白页上又出过一次 `no_parse` —— 同一族：它**不报错**，
   只是没交出结构化结果，而调用方若把「没结果」当「没问题」就又是一次静默失败。）
5. **「已开通 3 只」≠「3 只都能用」** —— 真正能做作业批改的只有 **2 只**（`lite` / `mini`）。
   第三只 `deepseek-v4-pro` 是**纯文本模型**，它那 2/2 是幻觉碰巧（§3.6）。
   ⇒ **模型清单要按能力筛，不能按「开通了」筛。**

**⚠️ 必须做的一件事（否则 `pro` 档用不了）**：

429 的原文不是限流，是账号级开关：

```
SetLimitExceeded — Your account [2109706933] has reached the set usage limit for the
[doubao-seed-2-1-pro] model, and the model service has been paused. To continue using
this model, please visit the Model Activation page to adjust or close the "Safe Experience Mode".
```

⇒ **方舟控制台 → 开通管理 → 调整或关闭「安全体验模式」的用量上限**。
不关的话，`pro` 两只每次调用都会被挡（重试 5 次也一样），而错误码 `429` 会让人以为是自己并发太高。

### 3.6 🔴 **`deepseek-v4-pro` 根本没有视觉能力，而且它会「编」**（2026-09-30 新增判据）

控制台显示已开通的三只里，`deepseek-v4-pro-ga-260813` 在批改矩阵上出现了一个
**可以有两种解释**的现象：它在「学生全对」的素材上判对（2/2），
但在含真错、空白页上都回 `score:100 items:[]`「本次作业全部正确」。

- **解释 A**：它**看不到图**，每次都在编一个「全部正确」
- **解释 B**：它**看得到图**，但从不做实质核对

**这两种解释的处置完全不同**（A ⇒ 只能去纯文本档；B ⇒ 连纯文本档都要防漏判），
而光看批改结果**分不开** —— 输出一模一样。所以换一个**不用批改**的问法。

**探针**：`probe_volc_vision_capability.mjs`（在工作区，与 `grading_matrix_probe.mjs` 同目录）。
同一个提示词（「逐字读出图中的所有算式」），
发「纯文本」与「+一张图」两次比 `usage.prompt_tokens`；再用**复述**验证。

| 模型 | 纯文本 prompt_tokens | +图 prompt_tokens | Δ | 能否复述出图中算式 |
|---|---|---|---|---|
| `doubao-seed-2-1-lite-260915` | 93 | 1355 | **+1262** | （本次空回复，但 B29 矩阵已证它能读图） |
| `doubao-seed-2-0-mini-260428` | 93 | 1355 | **+1262** | ⭐ **逐字读出 `(11/12 − 7/6 + 3/4 − 13/24) × (−48) = 2`** |
| 🔴 `deepseek-v4-pro-ga-260813` | 62 | 158 | **+96** | ❌ **编了一串乘法口诀表** |

**结论：解释 A 成立 —— `deepseek-v4-pro` 是纯文本模型。**

两条**独立**判据指向同一方向：

1. **token 抬升**：两只豆包对同一张图的增量**完全一致**（1262 —— 同一张图、同样切块），
   而 deepseek 只有 **96**。差一个数量级，不是「图片小」能解释的。
2. **复述**：mini 读出了图里**真实存在**的算式，且与探针注释里人工核对过的
   「例1(3) 末行 =2」**逐字对上** —— 这条**交叉验证**说明探针本身是有效的。
   而 deepseek 在**同一张图**上输出 `7+2=9 | 8+1=9 | 6+3=9 | …`，
   **一串和这张图毫无关系的乘法口诀**。

⚠️ **因此 `deepseek-v4-pro` 在批改矩阵上那 2/2 是「幻觉碰巧」**，不是能力：
它看不到图，被要求批改时随机说「全部正确」，恰好撞上「这张图确实全对」。
⇒ 这正是本文件反复强调的那类失败：**它把错题判成对，而且没有任何报错。**
真把它填进 `ARK_MODEL_VISION`，**错题库会永远为空**。

⚠️ **它现在也不能当 reasoning 档的默认答案。** reasoning 档做的是 `reviewJudge`
（决定错题能不能毕业），一个会**编造内容**的模型放那里同样危险 —— 要放，
得先单独跑一套 judge 判据。**它目前没有经过任何判据，等于未知。**

### 3.7 ⭐ **端到端链路实测：环境已打通，三条链路各测本义**（2026-09-30）

§3.5 / §3.6 都是**直连模型**（import 生产模块自己拼请求）。这一节是**打真实网关**：
`HTTP → router → guard → handler → model-client → ark` —— 把「环境打通」这件事本身验掉。
两者不可互替：直连全绿而网关 500 是很常见的一种状态。

**怎么跑起来的**（可复现）：

```bash
cd serverless/ai-gateway
export ARK_API_KEY="$(grep -E '^ARK_API_KEY=' ../../.env.volc.local | cut -d= -f2- | tr -d '\r\n')"
export AI_MODEL_PROVIDER=ark ARK_REGION=cn-beijing
export ARK_MODEL_VISION=<被测模型> ARK_MODEL_REASONING=<…> ARK_MODEL_LIGHT=<…>
export AI_THINKING_DISABLED_KINDS=homeworkOcr,homeworkCheck,answerOcr
export AI_UPLOAD_URL_BASE=http://127.0.0.1:8787 AI_UPLOAD_SIGNING_SECRET=dev-secret PORT=8787
node src/dev-server.js
```

### 4.6 🔴 **火山的错误可以是 HTTP 200**（判据必须看 body，不能看状态码）

验 AK/SK 时实测：请求回 **HTTP 200**，而错误装在
`ResponseMetadata.Error = { Code: 'AccessDenied', Message: '...' }` 里。

⇒ **只判 `res.ok` 或 `status === 200` 的代码，会把失败读成成功。**
这条与 §4.3 是同一族（「成功信号不构成判据」），但更容易中招：
`fetch` 的 `ok` 字段在这里会说谎。**火山的判据是 `ResponseMetadata.Error` 是否存在。**

### 4.7 🔴 **SDK 的老依赖会让「网络错误」冒充「配置错误」**

`@volcengine/openapi@1.36.2` 依赖 **axios 0.21.4**（2021 年版本）。
在 Node 22 下用它的 `Service` 调 `iam:ListUsers` 会报
`connect ECONNREFUSED ::1:80` —— **根本没连到 `iam.volcengineapi.com`，连的是本机 80 端口。**

而 `svc.options.host` 打印出来**是对的**。⇒ 症状（连接被拒）指向网络/配置，
真因（SDK 依赖太老）在别处。用「检查配置对不对」的思路会一直查不出来。

**处置**：只用它的 `Signer`（纯 crypto-js，不含 axios），HTTP 自己用原生 `fetch` 发。
见 `probe_volc_iam.mjs`。**别用它的 `Service`/`Service.fetchOpenAPI` 类。**

### 4.8 🔴 **自己的探针也会说谎：`--only` 把「样本」伪装成「全量」**

`probe-ark-catalog.mjs --only=pro` 会把候选过滤到只剩 3 个，然后**照样**打印
「本账号已开通 N 个可走 chat 的模型」与档位建议，其中包括：

```
ARK_MODEL_VISION=      # ← 已开通的模型都读不了图，留空
```

**而能读图的那两只（`lite` / `mini`）根本没被探到** —— 它们名字里没有 `pro`。
这是一个**由过滤造成的假结论**：格式规整、还贴心地给出了「留空」的理由，
比一句空白更危险 —— 空白你会去查，这个你会直接信。

⇒ **凡是带「过滤/采样」参数的工具，都必须把生效范围打印出来。** 已修：
`--only` 生效时先声明「这不是全账号结论」。

⚠️ 这一节与 §4.6 / §4.7 同族，都是「**判据本身不可信**」——
区别是前两条来自平台，这条来自**我自己的工具**。

---

### 4.9 ⚠️ **网关缓存会把「这次的结果」变成「上次的结果」**

同一进程内重复发**同一个 body**，第二次根本不到模型 —— 响应里 `meta.model` 是 `cache`、耗时掉到 **10ms 量级**。

判据（一眼可辨）：`meta.model === 'cache'` **或** 耗时比同类请求低两个数量级。本轮 `dx_q4 answerOcr` 就是
先被冒烟测试跑过一次，正式矩阵里那条 10ms 的结果是**冒烟的**，不是 lite 的。

处置：让 payload **实质变化**（探针里是 `--suffix` 改 title / fileName）。
MEMORY 里那条「探针量到的耗时只有几十毫秒 = 命中缓存」说的就是这件事。

### 4.10 🔴 **喂进去的上下文，能把「假能力」做成真结果**（本轮我自己踩的）

`answerOcr` 的请求体里有一个 `questionContent`（题干，给模型的上下文）。
我第一版探针把**带答案的定标真值**填了进去：

```js
// ❌ 错：truth 里写着答案
{ images, questionContent: c.truth }   // '450÷3=150；150−85=65（相遇问题，学生解对）'
```

于是**一个根本看不到图的纯文本模型**照样"转录"出了学生的手写：

| 用例 | 学生实际写的 | deepseek 首轮「转录」 | 修正题干后 |
|---|---|---|---|
| dx_q3 | `450÷3=150 / 150−85=65` | `450÷3=150 / 150−85=65` ⚠️ | `text=""` |
| dx_q4 | `设钢笔x元 / 5×6+3x=54 / x=8` | `text=""` | `text=""` |
| dx_q5 | `设这个数是x / 3x+2x=45 / x=9` | `3x+2x=45 / **5x=45** / x=9` ⚠️ | `text=""` |

`dx_q5` 是铁证：学生**没写过** `5x=45` 这一步（那是合并同类项，是**算出来的**）。
一个看不到图的模型不可能抄到没写的东西 —— 它只能自己算。而它算得出来，是因为答案就在题干里。

⇒ 修正成「图上印刷的题干原文、**绝不含答案**」之后，deepseek **3/3 全空**。
⚠️ **任何「输入里已经含答案」的对照都不构成能力判据** —— 它测的是文本推理，不是看图。

### 4.11 ⚠️ `/ai/health` 的 `capabilities` 是**配置汇报，不是能力证明**

`capabilityReport()` 的判据只有一条：`有没有 Key && 模型 ID 是不是空串`。
所以把 `deepseek-v4-pro`（纯文本）填进 `ARK_MODEL_VISION` 时，health 照回：

```json
"capabilities": { "vision": true, "reasoning": true, "light": true }
```

客户端**据此决定「要不要把 3MB 照片发上来」** ⇒ 配错模型时照片照发、而结果是一条静默的
`score:100 items:[]`（§3.7 链路 2）。**这个方法永远测不出「模型能不能看图」**，
换模型后必须跑一次真图，不能看 health 变绿就收工。
