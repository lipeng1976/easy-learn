# 多设备架构：为什么现在是两台孤岛，以及怎么打通

> 本文回答一个具体问题：**学生用一台手机、家长用另一台手机，怎么看到同一份数据。**
>
> 结论先说：**当前架构做不到。** 这不是「预留没启用」，是架构级缺口 ——
> 代码里没有任何一行业务数据同步，两台手机上的两个 SQLite 文件互相不知道对方存在。
>
> 相关文档：`open-items.md` §C1（清单口径）、`android-deploy-guide.md` §3（部署口径）、
> `auth-extension-seams.md`（登录/短信侧的预留设计）。

---

## 1 现状：一台设备 = 一个数据库

### 1.1 三条代码证据（可自行复核）

**证据一：结伴邀请要求对方账号已经在本机库里。**

`lib/services/database_service.dart` 的 `createRelationshipInvitation`：

```dart
final sender = await findUserById(senderId);
final target = await findUserByPhone(targetPhone.trim());
if (sender == null || target == null) throw StateError('手机号对应的用户不存在');
```

家长在自己手机上输入孩子手机号，`findUserByPhone` 查的是**本机库** ——
孩子的账号在孩子的手机里，所以这里**必然**抛 `手机号对应的用户不存在`。

**证据二：登录是本地比对密码的。**

`lib/services/auth_service.dart` 的 `loginByPhone` 从本机 `app_user` 表取记录，
直接比 `user['password'] != password`。服务端**没有账号概念**，
同一个手机号在两台手机上登录，结果只是两个各自本地的账号，彼此无关。

**证据三：没有任何业务数据同步层。**

`lib/services/` 下 30 个文件里，网络相关只有 AI 网关那几支
（`ai_api_client.dart` / `http_ocr_data_source.dart` / `ai_image_transport.dart`），
**没有一行**业务数据的推送或拉取。`lib/` 全局也没有硬编码的 http 地址。

### 1.2 演示里为什么看着像通的

因为 `seedIfEmpty()` 把 `stu_001`、`stu_002`、`par_001` **三个账号塞进了同一个 SQLite 文件**，
家长端首页再用 `ParentController._belongsToBound` 按 `studentId` 在**同一张本地表**里过滤。

```
同一台设备：  stu_001 的作业 ─┐
                             ├─→ 同一个 .db 文件 ─→ 家长按 studentId 过滤 → 「看得到」
              par_001 的账号 ─┘
```

**换了设备，这个前提就没了。** 过滤本身没问题，问题是**待过滤的数据压根不在这台机器上**。

> 一句话记住：**`relationship` 表把学生和家长绑在「同一个本地库」里，
> 而不是绑在「同一个账号体系」里。**

## 2 为什么不能「把 SQLite 放到云上」

这是最容易走错的一步，值得单独说清。SQLite 不是「能在云上跑的服务」，
它是**被链接进 App 进程的库** —— 没有服务端形态、没有网络协议、没有用户权限概念。

常见想法是「把 `.db` 文件放网盘 / NAS / 对象存储，两台设备都读写它」。这条路有三个坑：

| 坑 | 后果 |
|---|---|
| **文件锁失效** | SQLite 靠 POSIX advisory lock 做并发控制，这类锁在 NFS / SMB / 对象存储上**不生效或不可靠**。两台设备同时写 = 互相整体覆盖，**而且不报错** —— 静默丢数据。SQLite 官方文档专门有一条「不要跑在网络文件系统上」的警告 |
| **整库搬运** | 即使只允许一台写，每次同步也要整库下载再上传；断网、写到一半失败都可能留下半个损坏文件 |
| **没有权限隔离** | 文件给谁读就是**全部**读。家长端会拿到整库，包含别人孩子的数据 —— 这在有真实用户后是合规问题，不只是技术问题 |

**正确做法**：云上用**服务端数据库**（MySQL / PostgreSQL / 托管 NoSQL），
经 **HTTP API** 访问，鉴权在服务端做。本地 SQLite 保留，但角色改变 ——
从「唯一的家」降级为「离线缓存 + 待同步队列」。

## 3 目标架构

```
                 云端服务 · 唯一权威数据源
              账号 · 结伴关系 · 作业 · 积分 · 复习状态
                              ↕  HTTP API（增量拉取与推送）
        ┌─────────────────────┴─────────────────────┐
   学生手机                                        家长手机
   本地 SQLite（缓存 + 待同步队列）        本地 SQLite（只缓存已结伴孩子的数据）
```

三条原则：

1. **服务端权威**。所有「事实」由服务端裁定，客户端不再直接决定对错
   （现在连密码都是在客户端本地比的）。
2. **离线优先保留**。本地库不删。孩子用手机的场景（家里网络不稳、学校没 WiFi）
   必须能离线写，联网后再推。这是这个产品的真实使用场景，不能退化成「必须联网才能用」。
3. **鉴权在服务端**。客户端只带 token，不再自己声明自己是谁 ——
   顺带解决 `open-items.md` §C5 里「`X-Student-Id` 可伪造，`AI_REQUIRE_AUTH` 不敢开」的问题。

## 4 迁移路径（四阶段，每阶段可独立交付）

关键判断：**打通家长看孩子数据，不需要等完整的双向同步。**
把「读」和「写」拆开做，第二阶段就能解决本文开头那个问题，成本远低于全量同步。

> **前置工程见 `architecture-refactor-plan.md`**：在动下面的阶段 1 之前，先做「抽 Repository 接口」和「规则归口」两步 ——
> 否则阶段 3/4 接服务端数据时会一次性波及 111 处调用点。那两步与云选型无关、零行为变化，可以立刻开始。

### 阶段 1 · 服务端登录（= `open-items.md` §A2）

- 网关加 `/auth/register`、`/auth/login`，签发会话 token。
- 客户端 `AuthService` 从「查本地库比对密码」改为「调网关换 token」；
  本地只缓存用户信息，**密码不再在本地比对**。
- **独立交付价值**：换手机能登进同一个账号；AI 网关的 `X-Student-Id` 变成真 token，
  `AI_REQUIRE_AUTH` 终于可以打开。

> 必须先做这一步。没有身份，讨论「这是谁的数据」没有意义 ——
> 服务端数据库只会把「数据在谁的手机里」变成「数据在谁都没管的表里」。

### 阶段 2 · 关系与只读数据上云（**解决本文问题的关键阶段**）

- 云端建 `app_user`、`relationship`；结伴邀请走服务端：
  家长 A 手机发起 → 学生 B 手机能收到并确认。
- 家长端首页改为**从服务端拉**已结伴孩子的作业 / 积分（**只读**）。
- 写入仍全部发生在学生设备本地，再由学生端定期推送到服务端。

**为什么这一阶段最划算**：只需要「单向读 + 单向推」，**完全不需要冲突解决** ——
因为同一份数据同时只有一个写入方。家长看到孩子数据这个需求，到这里就通了。

### 阶段 3 · 学生端写入上云

- 学生设备上的写操作进本地队列，联网后推送到服务端；
- 服务端按 `id` 幂等去重（账本类表天生支持，见 §5）；
- 客户端拉取增量更新本地缓存。

### 阶段 4 · 多端写入与冲突解决

- 家长批改、愿望兑现等**在家长设备上发起的写**开始上云；
- 到这一步才真正需要冲突解决 —— 只在这一阶段引入版本号 / 操作日志。

**顺序理由**：阶段 2 和 3 里「谁写」是明确的，冲突根本不会发生。
把冲突解决留到最后，是为了避免在还没有真实冲突时就引入复杂度 ——
过早引入版本号会让每个写入点都要维护版本，收益却是零。

## 5 各表的同步难度（阶段 3 起参考）

**真正难的不是「存」，是「合」。** 现有 22 张表按合并策略分四类：

| 类型 | 表 | 策略 |
|---|---|---|
| **纯 append**（最好合） | `point_ledger`、`review_attempt`、`workout_record`、`study_plan_checkin`、`explain_record`、`chat_message`、`daily_comment`、`app_notification` | 按 `id` 去重后**求并集**。丢包重发的天然解 |
| **状态机**（最难合） | `review_mistake`、`wish`、`homework`（批改状态） | **不能比时间戳**。要带版本号或操作日志 |
| **快照**（跟父实体走） | `review_paper_item`、`homework_image` | 父实体定了就从属同步，不做独立合并 |
| **配置**（最后写入赢可接受） | `point_rule`、`study_plan`、`workout_plan` | 两端同时改会丢一边，但代价可接受 —— 要提示用户 |

**`point_ledger` 天生好同步**，这是意外收获：它是 append-only 的，
每笔带 `idempotencyKey`，撤销靠 `reversalOf` 冲正而不是删记录 ——
所以合并就是求并集，既不丢也不重复计分。**这套设计本来是为防刷做的，顺带让同步变简单了。**

**最需要小心的是 `review_mistake` 的状态机**：
`pending → reviewing → verifying → mastered` 这四个态，**中间态不能省**
（省了会导致组卷重复收录同一道题）。两端同步若丢中间态，
症状是「错题莫名其妙被收录两次」—— 而且不会报错。
所以它属于**必须带操作日志**的那一类，不能按时间戳覆盖。

**图片建议另走一条路**：`imageBlobs` 现在是 base64 存在库里，
同步起来会把数据库撑爆。应该改存**对象存储**（网关已预留 TOS 图片外链模式，
见 `open-items.md` §B2），库里只留 URL。

## 6 现在就该定下的两件事

1. **包名与签名要在有真实用户之前改**（`open-items.md` §C2 / §C3）。
   现在 `applicationId` 是模板占位 `com.example.easy_learn_app`、release 包用 debug key 签名。
   **改包名 = 换应用身份**，已装的机器必须卸载重装、数据一起没。
   这件事拖到有用户之后做，代价会大得多。

2. **阶段 2 之前不要动 `DatabaseService` 的接口形状**。
   它现在被当作「唯一数据入口」设计，查询内置 `studentId` 过滤 ——
   这个形状在阶段 2（改数据来源）时正好用得上：把「本地查」换成「本地缓存查」，
   调用方不用改。若在此之前把 `DatabaseService` 拆开或让页面直连数据库，
   阶段 2 的改造面会翻倍。

## 7 微信小程序场景（讨论记录）

**问题**：将来若改成微信小程序，数据还放本地吗？

**结论**：小程序里「数据放本地」**不是设计选项，是平台不允许**。
这不是取舍问题 —— 所以小程序反而让架构选择变简单：只能走云端权威。

### 7.1 查证到的硬约束

| 事实 | 出处 |
|---|---|
| 本地缓存单 key **1MB**、总计 **10MB**，且**以微信用户维度隔离** | 官方存储策略文档 |
| 清理时机是「**只有代码包被清理的时候本地缓存才会被清理**」—— 即**不保证持久** | 同上 |
| **没有官方 SQLite API** | 官方 API 索引中无此条目 |

⚠️ 网上有文章声称 `wx.sqlite` 在基础库 2.28.0+ 可用，
但**在官方文档里找不到任何依据**，另有来源明确写「微信小程序并没有原生提供一个名为 wx.sqlite 的 API」。
**不要按前者做规划。** 真要用 SQLite 只有两条路，都有代价：

- **WASM 版 sql.js**：数据库整个在内存里，**必须手动写回文件**。
  写回逻辑没处理好，「数据会在用户关闭小程序的一瞬间消失得无影无踪」；
- **第三方插件**：依赖供应商，有审核与付费风险。

### 7.2 对这个应用是致命的，不是「有点紧」

核心数据是**作业照片**，现在以 base64 存在 `imageBlobs` 表里。
**一张手机照片 2–4MB，10MB 连三张都放不下** —— 而且没有 SQLite、没有 JOIN，装不下 22 张表的关系结构。

**图片必须改走对象存储**（网关已预留 TOS 图片外链模式，见 `open-items.md` §B2）。
这一点无论做不做小程序都成立，做小程序只是把它从「应该」变成「必须」。

### 7.3 这条约束对「现在」的真正影响

**关键不是小程序本身，而是：现在的架构决定将来加小程序是「接入」还是「重做」。**

- 现在按 **云端权威** 做 → 将来加小程序是**新增一个客户端**；
- 现在继续按 **本地权威** 做 → 将来做小程序要**重做整个数据层**，还得补一个后端。

这也是把数据访问收敛到 Repository 接口后面的价值所在（见 §6 第 2 条）。

### 7.4 小程序带来的两个额外收益

1. **账号体系可以更简单**。`wx.login()` 拿 code 换 openid，**不需要手机号密码**。
   而 `LoginMethod.wechat` 与 `app_user.wechatOpenId` **已经预留好了**
   （见 `auth-extension-seams.md`）—— 这个预留正好用得上。
2. **不用自己管服务器与数据库**。微信云开发（CloudBase）直接给云数据库 + 云函数 + 云存储，
   没有 veFaaS 那套部署与 VPC 连接数的麻烦。

### 7.5 两个必须提前知道的真实成本

1. **云开发的数据库是文档型（类 MongoDB），不是关系型**。
   现在是 23 张关系表 + 外键 + JOIN，迁过去要**重新设计数据模型**。
   这个成本无法避免，但**若数据访问已收在 Repository 接口后面，改动只落在实现层**。
2. **客户端整体要重写**。Flutter 没有小程序 target（三条死路见 `open-items.md`），
   做小程序等于用小程序框架重写 34 个页面。
   另外若自建后端而非用云开发，request 域名要 **https + 备案**。

## 附：一句话版本

**现在是「一台设备一个库」，家长和学生能互通只是因为演示账号被塞进了同一个文件。
要跨设备，必须把权威数据搬到服务端 —— 但先做服务端登录，
再走「家长只读 → 学生写入上云 → 多端写入」三步，
分别在第二、第三、第四阶段各自解决一批问题，不要一步到位做全量双向同步。**

**微信小程序把这件事从「应该做」变成「必须做」**：小程序只有 10MB 键值缓存，
没有官方 SQLite，且本地缓存随代码包被清理 —— 云端权威在那里是唯一可行方案（§7）。
