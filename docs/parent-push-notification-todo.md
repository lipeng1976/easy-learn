## 二、通道选型（结论已定）

| 通道 | 判断 |
|---|---|
| **企业微信自建应用消息** | ✅ **选定**。免费、实时、可定向到每个家长、微信里能收到、纯血鸿蒙原生支持、能带跳转链接 |
| 企业微信群机器人 | 备选。5 分钟能跑，但消息落群、无归属、不好跳回具体作业 |
| 短信 | ❌ 不用。需签名审核（App 未上架，签名归口难），且每条计费，高频会烧 |
| 系统推送（FCM / 华为 Push） | ❌ **技术上不可行**。手机是纯血鸿蒙，APK 跑在卓易通容器里，拿不到 HMS 推送通道；FCM 在国内不可用 |
| 邮件 | 可作每日汇总兜底，不作实时主通道（手机邮件推送极易被忽略） |

出网连通性已实测（本机 → 2026-11-16）：`qyapi.weixin.qq.com` 200 / 0.28s，可达。

**需要虫子一次性提供的**：企微 `corpId`、自建应用 `agentId` / `secret`、家长成员的 `userid`。
配置走 `local.env`（键名待定：`WECOM_CORP_ID` / `WECOM_AGENT_ID` / `WECOM_SECRET`），
**绝不进代码、绝不进客户端**。

## 三、投递架构：outbox，不阻塞业务

🔴 硬约束：**绝不能在业务事务里直接调外部 HTTP**。一次 300ms，会拖慢孩子点「交卷」。

```
交卷 / 提交
  └─ 同一事务：写 app_notification ＋ 写 push_outbox（一行）
  └─ 事务提交，学生端立刻返回
后台 worker（本机：dev-server 定时器；云上：函数计算定时触发器）
  └─ 轮询 outbox where state='pending'
  └─ 调企微 message/send → 标记 sent / failed（最多 3 次，指数退避）
```

不引入 MQ / Redis，PG 就够。`push_outbox` 字段建议：
`id / notification_id / channel / payload / state / attempts / next_attempt_at / sent_at / last_error`。

必须守住的三条：

- **幂等**：`notification_id + channel` 唯一，重试不重复推。
- **降级**：推送失败只写 `last_error` 并记日志，**绝不回滚业务、绝不让学生端报错**。
  （与「可选能力不能拖垮主流程」同一条纪律。）
- **不泄漏内容**：只发「谁 + 什么事 + 结果 + id」，不发题目正文、不发图片。

## 四、频次口径（已定：实时合并）

- 同类事件 **5 分钟内合并**成一条（避免做 3 页打卡收 3 条）。
- **每小时上限 3 条**，超出部分并进下一条。
- **22:00–07:00 静默**，攒到次日 08:00 合并发一条。
- 静默期只对「孩子主动发起的求助 / 心愿申请」豁免（需要家长立即行动的那类）。

## 五、事件范围（已定：全选）

提交作业 · 批改完成 · **每日打卡交卷（需新加钩子）** · 学习计划打卡 · 错题新增 · 心愿 · 家长点评。

⚠️ 错题新增与家长点评信息量偏大，外发时按「合并后只报数量」处理，不逐条推。

## 六、开工时要补的判据

1. `checkin.js` 交卷确实写了 `app_notification`（现在一条都没有——先证伪「现在没有」）。
2. outbox：业务事务成功 ⇔ outbox 有一行；推送 HTTP 失败时**业务行不变**、outbox 记 error。
3. 幂等：同一 `notification_id` 投递两次，只产生一次发送。
4. 合并与静默：5 分钟窗口、每小时 3 条、22–07 静默延后，各一条纯函数判据（可注入 clock）。
5. 收件人：多家长（coparent）时**每个家长各一条**，走 `parentIdsOf`，不从请求体取。
6. 未配置企微时：不抛错、不写 outbox、学生端行为零变化（可选能力纪律）。
