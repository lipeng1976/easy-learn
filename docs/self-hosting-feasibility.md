# 后台自托管可行性分析（把服务端搬到这台 PC）

> 2026-10-13 · 对应归档点 `archive-2026-10-13`（commit `9be9b9b`）
>
> 结论先说：**技术上没有障碍（本地栈已经存在且跑通过），真正的变量是「服务契约」——
> 家里这台机器给不了云上那种「7×24 无人值守、谁都能连」。**

## 🔒 当前决策（2026-10-13）

**暂不切换。** 客户端与手机上的 APK **继续走云服务**，本文只是可行性分析。

- 归档点之后**工作树零改动**，运行时代码**一行没碰**；
- 云端地址**不在源码里** —— 它是构建期 `--dart-define` 烧进产物的
  ⇒ 将来切本机 = **换个构建参数重出包**，业务代码不需要改；
- **触发条件 = 云服务停掉之后**，再回到本文按第五节执行。

## 一、结论

| 方案 | 手机在家 | 手机在外 | 额外成本 | 改动量 | 风险 |
|---|---|---|---|---|---|
| **A. 纯局域网** | ✅ | ❌ | 0 | **0**（今天就能跑） | 极低 |
| **B. 组网/内网穿透**（推荐） | ✅ | ✅ | 0～几十元/年 | 0（装个工具） | 低（不暴露公网） |
| **C. 家宽公网直连** | ✅ | ✅ | 需公网 IP（多数家宽没有） | 域名 + 反代 + 证书 | **高**（暴露面 = 真实账号数据 + 模型 Key） |

关键判断依据：**这台机器当前在路由器 NAT 之后**（WLAN `192.168.3.80`），
所以 C 方案不是「配一下就行」，而是先要确认宽带是否给公网 IP —— 多数家宽给的是 NAT 后的内网地址。

## 二、现状：已经有的东西（实测）

这一节的每一条都是查过的，不是推断。

| 事实 | 证据 |
|---|---|
| **一条命令能起整套后端** | `serverless/data-service/scripts/dev-stack.mjs`：起 PG → 迁移 → 演示数据 → 两个服务 |
| **数据库不用装** | 用 npm 包 `embedded-postgres` 起 PG 17 实例，数据在 `.pgdata-dev`（69 MB，已存在） |
| **依赖极轻** | 数据服务只依赖 `pg`（1 个）；**AI 网关零依赖** |
| **本地跑的就是生产代码** | `index.cjs` 只是五行 ESM 垫片；`src/handler.js` 与 `src/dev-server.js` 共用同一套 `src/app.js` 路由 |
| **云依赖都有本地替代** | 附件存储 `IMAGE_DRIVER` 支持 `fs`（默认）；配额 KV `AI_KV_DRIVER` 支持 `memory`（默认） |
| **已有局域网模式** | `dev-stack.mjs --lan` 会把两个服务绑到所有网卡，并打印手机版构建命令 |
| **已经能在无网卡外的地方跑** | `--run` 把「起服务 → 跑测试 → 收服务」收在同一个进程里 |

### ⭐ 一条容易被误读的约束，在自托管场景下不成立

`config.js` 里写着「生产环境默认**不许**用 `AI_KV_DRIVER=memory`」，理由是
**多实例下配额会成倍放大**（每个 FC 实例各算各的）。

自托管恰恰只有**一个**长期进程 ⇒ **这条约束的前提消失了，`memory` 在此处是正确的选择**。
（但仍要记住：一旦你为了并发起两个进程，配额立刻失真。这个坑会在你「顺手多开一份」的时候出现。）

### 唯一必须出网的依赖

**大模型**。当前 `AI_MODEL_PROVIDER=bailian`，走百炼的 HTTPS API。
这意味着「完全离线的自托管」不成立 —— 断网时 AI 批改、AI 观察这些功能必然不可用，
而数据服务（作业、错题、打卡）仍可用。

## 三、缺什么（要做到「当作后台长期跑」）

现状是**开发/演示栈**，不是**服务**。差距具体是这七条：

### 1. 常驻形态 —— 缺

`dev-stack.mjs` 是**前台交互式脚本**（Ctrl+C 结束，注释里就是这么设计的）。
要长期跑得包一层：Windows 服务（`nssm` / `sc.exe`）或计划任务（开机启动 + 失败重启）。
⚠️ 注意它注释里那句话：**「必须在无沙箱隔离下运行」**，
因为沙箱会把常驻的 postgres 当残留进程回收 —— 现象是「起来几秒后自己没了」。
包成服务时这个坑会以「服务启动后立刻停止」的形式重现。

### 2. 数据库产品化 —— 缺

`embedded-postgres` 是**为测试与开发设计**的组件（每次 `npm test` 会起一个临时实例跑完就删）。
拿它长期扛数据，风险在于：
- 升级路径不明（PG 大版本升级要自己做）
- 崩溃恢复、`pg_dump` 备份、WAL 归档都没有现成机制
- 进程若被强杀，数据目录可能出现需要修复的状态

**建议**：要么装一份真实 PostgreSQL（Windows 服务形式，本机目前**没装**），
要么明确接受「这是演示数据、丢了不心疼」——但**别在两种心态之间摇摆**。

### 3. 数据持久化与备份 —— 缺

`.pgdata-dev` 会随使用增长。附件走 `IMAGE_DRIVER=fs` 时也存在本机（`IMAGE_ROOT_DIR`）。
**没有任何自动备份**。云上 RDS 至少有自动备份，本地这份没有。
至少要有一个「把 `.pgdata-dev` 和附件目录定期复制到别处」的计划任务 —— 同一块硬盘上的备份不算备份。

### 4. 对外可达 —— 缺（见第一节的 A/B/C）

### 5. HTTPS 与域名 —— 缺

当前线上是 `banxue.app.workbuddy.host`（WorkBuddy 托管）。
自托管后手机要填的地址会变成 `http://192.168.3.80:8788` 这类形式 —— 可以工作
（项目里已经有 `network_security_config.xml` 放行明文），但：
- 明文传输，同一 Wi-Fi 下可被嗅探（作业内容、账号口令）
- **手机切到 4G 立刻失效**（除非做了 B/C）

### 6. 安全边界 —— 缺

数据服务里是**真实账号数据**，网关手里攥着**百炼 API Key**。
`dev-stack.mjs` 的注释已经写得很清楚：

> 默认只绑回环，这不是洁癖：数据服务里是真实账号数据，而网关攥着方舟的 Key ——
> 放出去而没人察觉的症状是「同一个 Wi-Fi 下有人在花你的额度」。

自托管 + 公网暴露 = 你需要自己承担：端口扫描、弱口令爆破、API Key 被薅、
以及 Windows 本身的补丁水平。**云上那套 RLS + 签名 URL + 会话令牌之所以能成立，
前提是那条链路上的每一环都还在** —— 搬到本地后这些还在（代码没改），
但**网络层的那道门没了**。

### 7. 客户端要重出包 —— 缺（这条最容易被忽略）

`CLIENT_DATA_BASE_URL` / `CLIENT_AI_BASE_URL` 是**构建期**用 `--dart-define` 烧进 APK 的
（`main.dart` 的 `CloudRuntime.fromEnvironment()`，没配就返回 null ⇒ 退回纯本地模式）。

⇒ **换了后端地址，手机会连不上，必须重新构建 APK。**
除非你能让**域名解析**指到家里（那就不需要重出包）——但那个域名是 WorkBuddy 的，不由你控制。

#### 7.1 一个包带两条网络路径（2026-10-20）

「在家走局域网、出门走 Tailscale」不需要打两个包：

```bash
node tools\build-local-apk.mjs --host 192.168.3.80,100.96.105.11 \
  --instance-id <与服务器 SERVER_INSTANCE_ID 相同>
```

`--host` 逗号分隔：**第一个是首选，其余是备选**。客户端由
`lib/services/endpoint_resolver.dart` 在运行期选一个。

**只在两个时机探测**：冷启动第一次需要发请求之前、某个请求连接失败之后。
日常每个请求都不探测 —— 否则局域网也会平白多一次往返。

**并发探测、第一个成功即返回**（不是 `Future.wait`）。

⭐ 这是这个能力最容易做反的地方：写成 `Future.wait` 之后功能完全正常、
测试也能过，但在家每次冷启动都要等 Tailscale 那条回来 ——
把最快的链路拖成最慢的。`test/endpoint_resolver_test.dart` 第一条判据
就是「慢的永远不返回，也必须立刻拿到快的」。

🔴 **`192.168.3.80` 会撞车**：在别人家 WiFi 里这个地址大概率是另一台设备，
万一那台也跑着同款服务，只判「HTTP 200」就会把数据写到陌生人库里。
所以两个服务的 `/health` 都会回 `instanceId`（`SERVER_INSTANCE_ID`），
客户端比对不上就排除该候选。

⚠️ `config\local.env` 与 `config\ai.env` 里的 `SERVER_INSTANCE_ID`
**必须是同一个值** —— 不一致时数据面能选对、AI 面选不对，
症状是「能登录但批改连不上」。

⚠️ 备选地址必须指向**同一个后端（同一份数据库）**。给两个不同的服务端，
客户端会在它们之间来回切，数据也会分叉。

## 四、成本对比（结构，不是报价）

| 项 | 云上（现在） | 自托管 |
|---|---|---|
| 计算 | FC3 两个函数（0.5c1G/60s、0.25c512M/120s）按量 | 电费。按 60–100 W、0.6 元/度**估算**约 26–43 元/月 ⚠️ 需按实际机型核实 |
| 数据库 | RDS PostgreSQL（规格与费用**未核实**） | 0（嵌入式或本机 PG） |
| 对象存储 | OSS（**未核实**） | 0（本地磁盘，但**无冗余**） |
| 配额 KV | 共享 KV（**未核实**） | 0（进程内存） |
| 域名/HTTPS | WorkBuddy 托管 | 需自备（B 方案可绕过） |
| **隐性成本** | 无 | **你的时间**：断电、重启、系统更新、网络波动、磁盘故障，每一样都得你自己爬起来处理 |

⚠️ 上表里标「未核实」的三项，**请从阿里云账单里看真实数字** —— 我没有查到，不编。

## 五、建议

### 如果你只是想「自己/家人用，不想付云费」

**走 A + B 组合**：

1. 先用 `node scripts/dev-stack.mjs --lan` 把机器跑起来（**今天就能用**，零改动）。
2. 装一个组网工具（Tailscale 之类），手机装同一个客户端加入同一网络。
   这样**出门也能连**，而且**家里不用开任何公网端口** —— 安全模型比 C 好一个量级。
3. 再考虑常驻：包成 Windows 服务 / 计划任务 + 一个每日备份脚本。

### 如果你要「给不特定的人用」

**别搬。** 云上那套的价值不只是「跑得起来」，而是：
静态 IP、自动备份、分钟级扩容、DDoS 兜底、证书自动续期、以及**你睡觉时它还在**。
这些每一条都能自己做，但**加起来就是一个运维岗位**。

### 无论走哪条，先做这三件事

1. **确认宽带是否给公网 IP**（打运营商客服问，或看路由器 WAN 口地址是不是 `100.64.x.x` / `10.x.x.x`）。
   这决定了 C 方案是否存在。
2. **确认这台 PC 的稳定性契约**：会不会休眠？会不会自动重启装更新？晚上关机吗？
   这些直接决定后台是不是「经常连不上」—— 而那个症状会被误读成「程序又坏了」。
3. **把「要用哪份数据」想清楚**：云上库和本地库是**两份互不相通的数据**。
   搬过去不等于迁移，账号、作业、错题都不会自动跟过来（`seed:demo` 只能造演示数据）。
