## 1. 定位、角色与边界

### 1.1 谁在用

| 角色 | 谁 | 手里有什么 | 五件最常做的事 |
|---|---|---|---|
| **学生** | 小学中高年级孩子 | 自己的作业、错题、积分、心愿 | 交作业 / 运动打卡 / 复习错题 / 计划打卡 / 许愿 |
| **家长** | 孩子的父母 | 孩子的一切（只读视角 + 定价与兑现权） | 看概览 / 看作业与错题 / 定计划 / 定分值与兑现 / 写点评 |
| 老师 | 班主任（**未实现**） | 班级 | 建班、发班级号、看全班（§9） |

### 1.2 关系的建立方式

家长 → 输入孩子手机号 → 创建邀请 → 孩子接受 → `relationship.status = active`。
**只有 `active`（关系成立）的关系才有数据可见性**（服务端 RLS 按这个集合判定，见 §4.5）。
这个词就是「要不要隐藏数据」的开关：它**写错不报错**，只是可见集合算成空、
家长看不到自己的孩子（2026-09-20 统一前两侧各用各的词，见 §4.5）。

**基数**：关系表的唯一键是 `(student_id, parent_id)` —— 所以**一个孩子可被多位家长绑定、
一位家长可绑定多个孩子**（演示数据里王老师结伴两个孩子）。

**双方互见名字（2026-09-20 修）**：关系列表会带出 `studentName` / `parentName`。
在此之前它只回 id，客户端模型那两个字段是 `required`、只能填空串 ——
症状是**结伴成功、`status` 也是 `active`、界面上对方那一栏却是空的**，且不报任何错，
而库里两边账号都在。修复要**两件事一起**，缺一不可：

| 改哪 | 文件 | 少了它会怎样 |
|---|---|---|
| 列表 JOIN 出名字 | `routes/relationship.js`（**LEFT** JOIN，`pending` 的邀请不能因此丢行） | 名字字段不存在 |
| 放开「结伴对端」的读 | `sql/008_relationship_peer_name.sql` | JOIN 到了但被 RLS 挡 → 仍是 `null`（**学生视角的可见集合只有自己**，光 JOIN 拿不到家长那一行） |

`pending` 阶段**刻意读不到名字** —— 对方还没同意，不该先把资料给他看。这是设计不是缺口。

**解除结伴（2026-09-26 新增，B22）** —— 口径三条，都是产品拍板的：

| 口径 | 内容 | 为什么这么定 |
|---|---|---|
| 谁能解除 | **仅家长端**（学生端**连按钮都不渲染**，不是渲染出来再报错） | 孩子的数据由家长监管；给一个点了必然 403 的按钮，不如不给 |
| 怎么生效 | **单方、立即**，不需要对方同意 | 解除本就是「收回授权」，再走一次双向确认等于家长要孩子点头才能撤回 |
| 历史数据 | **全部保留、重结伴后全可见**，包括解除期间孩子自己记的 | 见下 |

**实现上是「改状态」而不是「删关系」**：`POST /data/relationship/revoke` 只把
`status` 从 `active` 改成 `removed`（**一行都不删**），可见集合（§4.5）随即算不到这个孩子 ——
这就是「解除」的全部机制。所以重结伴时历史**自动完整恢复**：

- 数据都按 `student_id` 挂在孩子名下，行上**没有**「哪个家长可见」的标记；
- 可见性是每次请求**现算**出来的（`resolveVisibleStudents` 只认 `active`）；
- ⇒ 重新 `active` 的那一刻，包括解除期间产生的记录，一次性全部回来。

⚠️ 这里有两个**必须一起改**才成立的点，缺一个就是「静默的错」：

1. **`invite` 必须允许从 `removed` / `rejected` 复活**（`on conflict … do update … where status in (…)`）。
   不写这个 `where`，重新结伴会走 `ON CONFLICT DO NOTHING` 静默不动 ——
   而接口返回的是「**你们已经结伴**」，**与事实正好相反**。
   （顺带修掉一个既有缺陷：`rejected` 原本是终点，那对被拒绝的关系**永远无法再结伴**。）
2. **解除后要刷两个控制器**（`ProfileController` + `ParentController`）。少刷一个的症状是
   「列表里已解除、首页还看得到那个孩子」—— 数据是旧的，但**看起来像是解除没生效**。

**孩子会收到一条通知**（类型 `relationship`），所以别指望这是悄悄断开。

**判据**：服务端 `test/auth.test.js` 的「解除结伴」整条用例（10 个编号断言：学生 403 **且核对文案** /
家长解除 → `removed` / 重复解除 403 / 家长 403 看不到 / 双方仍见 `removed` 行 / 学生收到通知 /
解除期间插一条孩子自己记的数据 / 重邀回 200 **且是同一行 id** / 那条数据也可见）。
⚠️ **「全绿」不构成判据**：这条实现有**两道独立保护**（角色闸 + SQL 里的 `parent_id = 我`），
所以「把角色闸改成恒不触发」测试**照样全绿** —— 必须**同时断言错误文案**才测得出来。

### 1.3 边界：做什么，不做什么

- 做：**一个家庭 + 一个班**规模的学习闭环。班级级足够覆盖「一个班都在上面」。
- 不做：学校/机构组织树、SaaS 权限矩阵、跨校统计（§9）。
- 做：AI 辅助（识别、批改、判定、讲解、出题）。
- 不做：**AI 替学生做作业**——所有 AI 产出都要求学生有自己的作答证据才计入掌握（§3.2）。

## 3. 端到端操作闭环

这一节是本文最该细读的部分。**每个闭环都写成「谁 → 做什么 → 状态怎么变 → 落哪张表 →
谁看得见 → 怎么验」**，因为交接时最常丢的就是「这一步之后应该发生什么」。

### 3.1 闭环 A：一次作业，从录入到订正

```
学生录入/拍照识别      提交               批改                 订正/重交
      │                │                 │                     │
      ▼                ▼                 ▼                     ▼
  homework 行 ──▶ items 清单(可编辑) ──▶ status=checking ──▶ 有错题→needFix ──▶ finished
                                        (无需批改→finished)   无错题→finished
  （原先还有一个 `timeout`「已超时」状态 —— 2026-09-28 已删除，见 B26）
```

| 步骤 | 细节（含**为什么这么定**） |
|---|---|
| ① 作业从哪来 | **学生自己录入**（「录入作业」按钮，可手动填，也可拍照后核对识别结果批量录入）。家长端**没有布置作业的入口**——家长的权力在计划、分值与兑现，不在往孩子清单里塞任务 |
| ② **拍照识别** | 学生拍 1–4 张照片 → 网关视觉档认字 → 返回任务清单。**「有没有结果」与「有多大把握」是两件事**（2026-09-29 修正，见 B27）：只要认出了条目就**进核对表单**；置信度低于 0.8 时**加醒目核对提示**（「这次偏低，请逐条对着原图核一遍」），**不再整份丢弃**。真正走「认不出来」的是**一条都没产出**的情况，此时如实返回 `success: false` 且**不产生占位任务**——占位任务会变成孩子真照着做的一项作业。多图合并去重、跨科目标「多科目」，认不出的照片**不落库** |
| ③ **识别后归一化** | 由客户端**纯规则**完成（`HomeworkItemNormalizer`）：科目同义收敛、正文科目前缀优先于 `subject` 字段、漏拆兜底、去重时保住 `uncertain` 标记。**不交给模型的唯一理由是「会漂」**——同一张图两次跑出不同条数，而「今天有几项作业」要落库、要被家长端另一个会话读到。**题号连写也在这一层展开**（`1.2.37` → `1、2、3、7`）：实测模型自己改写这串时 **25 次丢 6 次数字**（丢掉那一题，语义还通顺，没有任何机制能发现）。⚠️ 展开后**必须幂等** —— `1、2、3、7` 这种形态不能再被列表切分规则切一遍 |
| ④ 提交 | **不是独立动作**，就是一次 `updateHomework(掩码)`：写 status / submittedAt / submitBatchId / imageCount / needsGrading，并 `clearResult()` 清掉上一次的分数 |
| ⑤ 批改 | 需要批改的走 AI（视觉档），不需要的（朗读/背诵/默写/抄写/字帖）直接完成。**批改来源必须落库**（`gradingSource = cloud \| local \| ''`），否则家长看到「没有批改」分不出「这类作业本来就没有」还是「AI 不可用」 |
| ⑥ 得分 | 提交需批改 **5 分** / 无需批改 **3 分**（动作完成即给，不等批改结果）/ 全对或订正通过再 **5 分** |
| ⑦ **录错了 / 录重了 → 整份删掉**（2026-09-28 新增，B25） | 入口 = 作业卡片右上角 **⋮**。**只有学生端有**（家长端对作业一直只读）。**任何状态都能删**（含已提交、已批改）—— 真实触发场景都在识别环节（认错字、同一份被认两遍），而后者常常是**提交之后**才发现。⚠️ **不可逆**，且**连带删掉**照片行 · 批改结果 · 它带出来的错题（含 4 张从属表）；原因是 `homework` 表**没有任何外键指向它** ⇒ 只删作业行会留下**查不出来的孤儿**（照片配额照算、错题指着一份不存在的作业）。已发积分**不追回**。两道权限闸（角色 + 可见集合），`checking` 中禁用 |

| ⑧ **作业上不再有「超时」**（2026-09-28 删除，B26） | 原先有个 `timeout`（已超时）状态，触发条件是 `now > dueAt` —— 而 `dueAt` 取的是**打开作业页那一刻**（录入表单里**没有时间输入框**）⇒ **每一条刚录入的作业当场就算「已超时」**，卡片挂红「截止 22:56」、家长端报「已超时 N 项」。它想说的是「还没做」，不是「没按时做」⇒ **枚举值 · 扫描逻辑 · 学生端红字与 chip · 家长端统计与日报文案全部删除**。家长端的信息由「已提交（含提交时间）/ 尚未提交」承担（本来就有）。老库里残留的 `'timeout'` 由 `HomeworkStatus.parse` 归一到「待完成」（**不迁移、不改库版本**）。⚠️ `dueAt` 字段**保留**（它实际是「这份作业属于哪一天」）—— 但**不许再拿它算超时** |

**学生能看到**：我的作业列表 + 批改结果 + 错题。**学生在卡片上不会被提示「超时」**（2026-09-28 起）。
**家长能看到**：概览的作业卡、作业详情（分数、错题、照片）、**孩子交了没有 / 什么时候交的**。**看到的是同一份数据**（上云后跨会话）。

**照片是跨设备的**（2026-09-20）：字节存在服务端（落盘根目录由 `IMAGE_ROOT_DIR` 配置），
库里只存**相对路径**，家长端按 `id` 取回。在此之前 `storageKey` 是一个**设备本地标识**，
字节从未离开学生那台设备 —— 换成家长的手机必然读不到，而且**静默返回 null**
（用户只看到照片位置一片空白，没有任何报错）。
判据：`serverless/data-service/test/images.test.js`（字节逐字节相同 + 权限正反对照）、
`test/image_key_test.dart`（与服务端 `imagestore.js` 的正则跨栈对照）。
**怎么验**：`test/homework_submission_flow_test.dart`、`homework_grading_test.dart`、
`homework_ocr_test.dart`、`homework_item_normalizer_test.dart`、
`homework_delete_test.dart`（B25：协议 + 「先落库后清内存」+ 失败原因透传 + id 早退，**5 条，含一次组合证伪**）、
`homework_overdue_test.dart`（B26：录入后不再变超时 + 老数据 `'timeout'` 归一到「待完成」，**2 条，含一次两处组合证伪**）；
服务端 `serverless/data-service/test/data.test.js`（B25：7 张表级联归零 + 两道权限闸，**两处逐个证伪**）；
真浏览器走查里的「学生首页看得到服务端种子作业」。

**已知边界（不要当成 bug）**：手写体的真实失败模式是**「错误不可见」**而不是识别率低 ——
最潦草一档会把「静夜思」认成「静在恩」，而自报置信度仍有 0.90（门槛 0.8），
结构上抓不住。对策是提示词写死「认不准就标出来、**不要换成通顺的词**」+ 结果带**可选** `uncertain`
标记，但实测两个错字只标出一个 —— **它不能替代对着原图核对**（§7.5）。

### 3.2 闭环 B：一次复习，从错题到毕业

这是全系统最复杂的一条，也是唯一有**状态机 + 双人协作 + 线下动作**的闭环。

```
        ┌──────────── 一池：review_mistake ────────────┐
        │  pending 待复习   reviewing 复习中   verifying 待批改   mastered 已掌握（出池）
        └──────────────────────┬───────────────────────┘
                               │  三路（都可产生作答证据）
        ┌──────────────────────┼───────────────────────┐
        ▼                      ▼                       ▼
  review_paper(_item)    explain_record        ai_practice_question
  组卷 → 导出打印 →      讲解（AI 或自看）      举一反三练习
  作答回传 → AI 判定
```

| 关键规则 | 内容与理由 |
|---|---|
| **中间态不能省** | `pending → reviewing → verifying → mastered` 四态。把 `reviewing` 去掉（「已入卷」直接算「待批改」）会让**同一道题被重复组卷** |
| **一池三路一个出口** | 三条路都写进同一张 `review_mistake` 的状态与计数，而不是各自记一份「掌握情况」——否则「这题到底掌握没有」会有三个答案 |
| **卷内题目是快照** | `review_paper_item` 存题面副本；**在卷的题不许删**（删了会导致判卷对不上号） |
| **毕业分档** | 错 ≤ 2 次：通过一**轮**即毕业；错 ≥ 3 次：需**连续两轮**通过。理由：一次做对可能是蒙的，而反复错的题需要更长的确认 |
| **什么不算毕业** | 讲解**不构成**毕业（看懂了 ≠ 会做）；**自评**（只标对错不写答案，`paperSelf`）不算掌握证据，不参与掌握率与给分 |
| 判卷 | 剥掉「（括号说明）」再比对答案，**两侧同时剥**、反复剥最内层；判不出来的记 `inconclusive`，**按未通过**处理（保守） |
| 周期报告 | 窗口是**自然周/月**；**通过率分母 = 期内作答次数**（不是题数）；周期键取 **ISO 周年**，落库按 `scopeKey` **覆盖**而不是追加 |
| 导出 | `ReviewExporter` 端口（`printHtml` / `downloadHtml` / `shareText`）是唯一出口；卷子是 **HTML A4**。**失败或用户取消，一律不写 `exportedAt`、不转 `printed`** ——否则卷子会显示「已导出」而实际上没导 |
| 得分 | 完成一轮复习 **10 分**（本轮至少一道题写了答案）；错题毕业 **10 分**（逐题，自评不算） |

**怎么验**：`test/review_closed_loop_test.dart`、`review_p1_test.dart`、`review_export_ui_test.dart`、
`judgement_ab_test.dart`。对账侧见 §7.2（复习闭环是三个已对平闭环之一）。

### 3.3 闭环 C：运动打卡 → 积分

学生建运动计划（家长端也有同一个动作，可替孩子建）→ 按项目打卡（跑步/跳绳/…）→ 落 `workout_record`。
**同项目同一天只记一次**（防重复点击），一次 **5 分**。家长在概览里看到运动数据。

### 3.4 闭环 D：学习计划

```
家长布置 → pendingStudentConfirm ──学生确认──▶ active ──每日打卡──▶ 累计
                    │                                  │
                    └─ 学生拒绝 → rejected              └─ 家长撤回 → withdrawn ⚠️ 服务端无此词（§4.5）
                                                        完成 → completed
```
打卡落 `study_plan_checkin`，唯一键 `(planId, date)`，**date 是「学生所在时区的今天」**——
服务端按 UTC 算会错一天（晚上 8 点后打卡记到明天，这正是服务端必须由客户端给纯日期的原因）。
每次打卡 **5 分**；**撤销打卡不删记录**：原记录打 `reversedAt` + 补一笔负数冲正分录。

### 3.5 闭环 E：积分与心愿（全系统最需要小心的一条）

```
        ┌── 唯一真相：point_ledger（流水） ──┐        余额 = 流水求和（没有任何地方存 balance）
        │  幂等键 + 部分唯一索引             │
        └────────────────┬──────────────────┘
                         │
   攒分 ◀──── 作业/复习/运动/计划/家长奖励 ────▶ 花分 = 心愿兑现
```

| 环节 | 规则 |
|---|---|
| 学生许愿 | 只登记愿望，`pointCost` 由**家长确认时定价**（**0 表示不消耗积分**，即纯奖励） |
| 学生申请兑换 | **一分不扣**，只写 `redeemRequestedAt` |
| 家长确认兑现 | **扣分发生在这里**。理由：不可逆的损失应由掌握兑现权的一方触发。若申请时就扣、家长又没兑现，就成了「分没了、愿望也没实现」 |
| 家长拒绝 | **一分不动**，`redeemRejectedAt` 只留痕、不是封禁，孩子可以再申请 |
| 一个愿望只兑一次 | 幂等键 `wish_redeem:{wishId}`，`redeemedAt` 非空即不可再兑 |
| 为什么是三个时间戳 | 申请/兑现/拒绝各一个，而不是一个状态字段——压成一个就得再定一套「谁覆盖谁」的规则，而那正是扯皮的来源 |
| 分值设置 | 家长可改 7 项动作的分值、可开关，**按孩子独立**；家长额外奖励**不做防重**（点两次就该给 10 分，那是他的本意） |

### 3.6 闭环 F：家长监管

概览（孩子概况 + 作业/错题/积分/打卡）→ 作业详情（分数、错题、照片，以及「这次批了没有」）→
每日点评（`daily_comment`，学生端可见）→ 聊天（`chat_message`，**与孩子本人**）→
通知（**8 类**，带未读计数）。
**通知由服务端生成**：作业提交/批改、打卡、点评、心愿状态都会推给对方（§4.5）。
第 8 类是 `relationship`（**只有一种：家长解除结伴**）—— 它**刻意不参与**通知页那两个
「类型 → 页签」跳转，只标已读：学生端没有「结伴」tab，硬塞一个最接近的落点
（比如心愿）会让人点进去看到一堆无关的东西。

### 3.7 闭环 G：换设备登录与离线

```
另一台设备打开 → 登录（服务端签发 token）→ bootstrap（用户 + 关系 + 未读）→ 首屏
                                              │
                        ┌─────────────────────┴─────────────────────┐
                    在线：读服务端 + 后台回填缓存            离线：读缓存 + 横幅告知「这是上次同步的」
                                                                       写：必须在线（离线写如实失败，不排队）
```

**这是本期最值钱的一条**：它把「我昨天做的作业全没了」这个**用户能看见的灾难**消掉了。
代价是旧数据与实时数据长得一样，所以**陈旧读必须可见**（§4.6 方案 B）。

### 3.8 闭环 H：解除结伴 → 重连（2026-09-26，B22）

```
家长解除（仅家长端、单方、立即生效）
      │
      ▼
relationship.status: active → removed        ← 只改状态，一行都不删
      │
      ├─▶ 可见集合当场算空 ⇒ 家长端所有页都看不到这个孩子
      ├─▶ 孩子收到一条「结伴已解除」通知（不是悄悄断开）
      └─▶ 历史数据原地不动（挂在 student_id 下，行上没有「哪个家长可见」的标记）
      │
      ▼
重新邀请 → 孩子接受 → active 恢复
      │
      ▼
全部历史一次回来，**包括解除期间孩子自己记的**
```

| 步骤 | 细节与理由 |
|---|---|
| 为什么是 `removed` 而不是删行 | 唯一键 `(student_id, parent_id)` 决定删了就得重建新行，「同一对关系的历史」会被切成两段；而且删行不可逆 |
| 为什么「解除」不收回已看过的数据 | 数据不在家长名下，它是**孩子的**。收回等于让第三方动作删掉孩子自己记的东西 |
| 为什么重连必须能复活 | 否则「解除」= 永久拉黑：接口会回「你们已经结伴」，而**事实正好相反**（§1.2 里那两个必须一起改的点） |

**怎么验**：§1.2 的判据清单（服务端 10 条编号断言 + 客户端 3 条 + 三次证伪）。

## 4. 架构

### 4.1 总体

```
┌─ Flutter 客户端（Android / iOS / Web）
│   只依赖 lib/repositories/ 的 9 个接口 / 75 个方法
│   本地 SQLite 与 Web 版内存库：降级为**读缓存**，不再是权威副本
└──────────────┬──────────────────────────────────────────
               │ HTTPS + Bearer session token
    ┌──────────┴───────────┐
    ▼                      ▼
┌─ 数据服务 /data/* ─┐  ┌─ AI 网关 /ai/* ──────────────┐
│ 账号·关系·作业·复习 │  │ 识别·批改·判定·讲解·出题      │
│ 积分·心愿·计划·运动 │  │ 鉴权·配额·缓存·审计·看板·降级 │
│ 通知                │  │ 零 runtime 依赖               │
└─────────┬──────────┘  └───────────┬──────────────────┘
          │ 连接池                    │ ARK_API_KEY（槽位名，实为百炼）
          ▼                          ▼
   PostgreSQL（云 RDS）          百炼（模型：qwen3.5-omni-plus /
   25 张表 + RLS 多家庭隔离        qwen3.8-max / qwen3.8-flash）
```

⚠️ **Web 版只是多了一个静态入口，没有多一层服务**：`site/` 里的 HTML/JS/wasm 由
分享链接托管（§10.3），浏览器直接调上面那两个域名 —— 所以 **CORS 预检是它唯一的
新增前置条件**（§4.5）。⚠️ 视觉档模型名以 **`.env.prod` 的实测值**为准
（`qwen3.5-omni-plus`）；本文 v1.0 在 §4 与 §7 里还写着上一档 `qwen3-vl-plus`，
属于「同一事实多处副本、只改了一处」。

**两块服务刻意分开**，不是随手拆的：零依赖约束（网关零 runtime 依赖、数据服务必须带 PG 驱动）、
冷启动敏感度（数据 API 是打开页面就要等的，AI 本来就要等 10–30s）、流量特征相反、
故障隔离（AI 挂了不该影响登录与查作业）。
共享的是 `serverless/shared/`（错误码 + token）——**不复制粘贴**，错误码分叉是最难查的一类 bug。

### 4.2 客户端四层

| 层 | 位置 | 职责 | 硬约束 |
|---|---|---|---|
| L1 控制器 | `lib/controllers/`（11 个） | 业务动作与规则 | **上云改造不碰这一层**——这是「行为零变化」的基准面 |
| L2 仓库接口 | `lib/repositories/`（9 接口 / 75 方法） | 数据访问面 | 一次冻结成接口，上云变成「多实现一份」而不是「重写」 |
| L3 实现 | `lib/services/http_*_repository.dart`（10 个）+ `local_database_service.dart`（唯一本地实现） | HTTP ↔ 服务端 / SQLite ↔ 本地 | 编译期开关切换（`cloud_runtime.dart`），每一步可回退 |
| 横切 | `data_api_client`（信封/鉴权/缓存/重试）、`session_store`、`read_cache`、`ai_api_client` | 与业务无关 | 每个都是 ``*_io`` / ``*_html`` / ``*_stub`` 三份，条件导入 |

### 4.3 数据模型

**25 张表**（22 张业务表 + 3 张横切表），按域分五组（PG 侧 DDL：`serverless/data-service/sql/`）：

| 域 | 表 |
|---|---|
| 账号与关系 | `app_user`、`relationship`、`user_session`*、`app_user_credential`* |
| 作业 | `homework`、`homework_image` |
| 复习 | `review_mistake`、`review_paper`、`review_paper_item`、`review_attempt`、`explain_record`、`ai_practice_question`、`review_summary`、`judgement_ab` |
| 激励 | `point_rule`、`point_ledger`、`wish`、`workout_plan`、`workout_record`、`study_plan`、`study_plan_checkin` |
| 沟通 | `chat_message`、`app_notification`、`app_notification_read`、`daily_comment` |

（`*` = 横切表，共 3 张。`app_notification_read` 是**已读表**，
**不碰通知行上的 `is_read`**——通知是广播的，一行被多人读，行级字段表达不了「谁读了」）

⚠️ **RLS 对这 25 张表是全覆盖的**（25/25，`ENABLE` + `FORCE` 都开）。别因为某张表「看着是横切的」
就以为它不设防 —— 实测 `comm` 求差为空，**没有表在 RLS 名单之外**。

### 4.4 服务端 7 条权威规则

这 7 条**每一条都靠「单机 + 只有一个客户端」侥幸成立过**，上云后会以不同方式坏掉。先定规则再写代码。

| # | 规则 | 一句话 |
|---|---|---|
| R1 | 身份只能由 token 给出，且**必须带角色** | `{sub: userId, role, studentId}`；body 里的 role 一律忽略；配额按 `sub`（谁花的钱占谁的额度） |
| R2 | ID 必须服务端生成 | 客户端造 ID 既可伪造（拿别人的 ID 覆盖数据）、又会因多设备时钟不同步而撞 |
| R3 | 时间戳服务端生成，**但要分两类** | **记录时间**（createdAt 等）服务端 `now()`；**业务时间**（打卡日期、运动开始时刻）客户端给，服务端只校验范围 |
| R4 | 归属字段服务端填 | body 里的 `studentId` 只当「申请访问哪个孩子」，绝不直接落库 |
| R5 | 关系鉴权必须服务端判定 | 家长访问孩子数据一律过 `requireBound(studentId)` 中间件；**不允许端点各自实现**（散落实现早晚有人忘，忘了的那个就是越权口子） |
| R6 | 幂等在 HTTP 下重做一遍 | 重试命中已存在记录 = **返回原结果**，不是报错（`ON CONFLICT ... DO NOTHING RETURNING`，没返回行就回查） |
| R7 | 隔离必须是**数据库机制**，不是约定 | PostgreSQL RLS。一个家庭时漏写 where 无所谓；**一个班 40 人时一次漏写 = 全班数据泄露** |

### 4.5 接口契约（跨端最容易漂的部分）

| 约定 | 内容 |
|---|---|
| 统一信封 | `{ok, data, meta}` / `{ok, error}`，数据服务与 AI 网关一致，客户端解析逻辑共用 |
| **掩码写入** | 请求体里**键出现 = 这次写它**，值为 `null` = 写成 NULL/空，**没出现的键一个字都不动**。这一条保住了「重新提交后清掉上一次分数」（清空必须能表达） |
| 端点按 Repository 接口列，**不按业务动作** | 「提交作业」在 L1 就是一次 `updateHomework(patch)`；照动作建端点会让服务端把 L1 规则抄一遍，两份实现一定漂（症状：家长端分数与学生端不一致） |
| 关系可见性 | 服务端把「本次会话能看哪些学生」算成一个集合，再由 RLS policy 认这个集合；**不按角色写 policy** |
| 账号行可见性 | `app_user` 的读策略 = **自己 + 可见学生 + 结伴对端**（`sql/008_relationship_peer_name.sql`）。最后一项是 2026-09-20 加的：**学生的「可见学生」只有自己**，不加它就读不到家长的账号行 —— 表现为关系里对方名字恒为空串，而不是报错 |
| 通知 | 只读 + 标记已读；**没有 `POST /data/notifications`**——让接口*不存在*比「存在但返回 403」少一个将来被误用的口子 |
| 错误码 | 单一来源 `serverless/shared/errors.js`；`quota_exhausted`（天，不可重试）与 `rate_limited`（分钟，可重试）**必须是两个码** |
| **跨域预检** | 浏览器发**带自定义头**（`authorization` / `content-type: json`）的请求之前**必发 `OPTIONS`**；而平台只对**简单请求**补 CORS 头 ⇒ **函数必须自己接住 OPTIONS**（`app.js` 最前面短路回 **204**）。⚠️ **不要自己再加 CORS 头** —— 平台会给 204 补一整套，重复的头是浏览器直接报错的形态 |
| **解除结伴** | `POST /data/relationship/revoke`，body 只有 `{id}`。⚠️ 它是一个**独立端点**，不是「状态端点多取一个值」：前置状态（`active` vs `pending`）、权限（仅家长 vs 被邀请方）、语义三样都不同（§1.2） |

⚠️ **CORS 这条的判据极易搞错（2026-09-26 记）**：`curl -X OPTIONS <url>` 能拿到
**整套 CORS 头**，看起来「跨域早就配好了」—— 但判据必须是**预检本身的状态码**：
修之前函数把 OPTIONS 当成「路径存在、方法不存在」回 **405**，非 2xx ⇒ 浏览器判预检失败
⇒ **真实请求根本不发出去**。它的招牌症状是「**原生 App 一切正常，网页连登录都发不出去**」，
因为预检只发生在浏览器里。已修（B24）：云上 405 → 204，单元测试 + 两次**互不重叠**的证伪
（删掉短路 ⇒ 恰好 3 条红；让函数自己加头 ⇒ 恰好 1 条红），真浏览器探针 `EXIT=1 → 0`。

⚠️ 另外两条现状（都别按字面理解）：平台 Default CORS **不限来源、反射任意 Origin 且允许凭证**
⇒ **别把 Cookie 当会话载体**（现在用 Bearer 票，所以这个组合没被放大）；
`.env.prod` 里的 `CORS_ALLOW_ORIGIN` 在云上是**死配置** —— 只有本机的 `dev-server.js` 读它。

✅ **已统一（2026-09-20，P1-3）**：`relationship.status` 两侧现在**逐字相同** ——
服务端由 `accepted` 改成 `active`（与客户端枚举名、与本地 SQLite 里存的值一致）。
改的是服务端那一侧，理由不是「服务端好改」：客户端那份词已经落进**每台已装设备的库**
（`RelationshipStatus.active.name` 直接写库），改它要动客户端 DB 迁移；服务端只有演示数据。
词的单一来源是 `serverless/data-service/src/vocab.js`，数据侧的另一半是
`sql/007_status_vocab_active.sql`（幂等）。**没有为兼容留别名** —— 当前没有真实用户，
留一个「accepted 也收」的口子等于把「同一个语义两个词」永久留在系统里。

⚠️ **`study_plan.status` 仍未统一，而且剩下的差异不是命名风格**：
服务端 `pending / active / rejected / completed / expired`，客户端
`pendingStudentConfirm / active / rejected / withdrawn / completed`。三处差异各有原因：
① `pending` ↔ `pendingStudentConfirm` 是同一个语义两个词，合并要动客户端的落库值；
② 服务端 `expired`（到期自动失效）与客户端 `withdrawn`（家长撤回）在对面**都没有对应值** ——
它们是两个不同的动作，凑成一个词会丢掉「谁把它结束的」；③ 所以客户端上行仍需一层翻译
（`lib/services/wire_status.dart`，判据在 `test/wire_status_test.dart`，含**跨栈对照**：
它会读 `vocab.js`，服务端改词而客户端没跟上就红）。
**这类不一致会持续产生 bug** —— 历史上真漏过一个词，症状是家长端永远显示「尚未与任何学生结伴」，
且**不报任何错**。

### 4.6 离线策略：方案 B（读缓存优先 + 写必须在线）

```
读：命中新鲜缓存(≤15s) ──▶ 直接返回            写：必须在线
    └ 过期/未命中 ──▶ 先返回缓存 + 后台刷新         └ 离线 → 如实失败 + 上报 writeDropped
                      └ 网络失败 → 用缓存 + 亮横幅      （不落本地、不排队）
```

| 约定 | 理由 |
|---|---|
| 缓存只对 `/data/`，且 **key 带身份** | 否则换账号会读到上一个人的数据 |
| `lookup` **同步** | 首屏不能等 I/O；落盘是 200ms 防抖的后台动作 |
| 世代校验 + 容量上限 + 坏数据自愈 | 缓存是加速器，不能变成新的故障源 |
| **陈旧读必须可见** | 旧数据与实时数据长得一样，是本方案引入的**新风险**。横幅是这条方案的必需品，不是装饰 |
| 写成功即 `invalidateAll()` | 否则用户看不到自己刚写的东西 |
| 横幅 20s 自动隐藏 | 时长是产品决定；**但它有后果**：验收必须在这个窗口内探它（§7.3） |

|---|---|

| **重试切两半** | 传输失败 → 网关重试（≤2）；**schema 违约 → 客户端带 `retryHint` 重试**（上限 2×2 = 4）。解包以服务端 `retryable` 为准 |

## 5. 关键设计约定（交接时的「不许删」清单）

这些看起来都「多余」，删掉都不报错，只在某天出事。

| 约定 | 删掉的后果 |
|---|---|
| 余额是**求出来的**，不存 `balance` 字段 | 撤销打卡/改分值/兑心愿任一处漏更新，孩子看到的数字就再也解释不清 |
| 撤销 = 标记 + 反向分录，**不删记录** | 反复开关打卡就能无限刷分 |
| 幂等键 + **部分唯一索引** | Dart 侧查一遍拦不住连点（查与插之间永远有缝），唯一索引才是保证 |
| `PointAccount.fromLedger` **跳过已撤销的记录连同它的冲正笔** | 让一正一负抵消虽然余额对，但「累计获得」会凭空多 5 分 |
| 复习**中间态不能省** | 组卷会重复收录同一道题 |
| `review_paper_item` 是**快照** | 判卷对不上号 |
| 导出失败/取消**不写 `exportedAt`** | 卷子显示「已导出」而实际没导 |
| `updateHomework` 的 `null` = 「本次不改」；清空用 `clearResult: true` | 「重新提交后家长仍看到上一次的旧分数」 |
| **DB 版本三处同步**（`_initDatabase` / `_onCreate` / `_onUpgrade`） | 漏在 `_onCreate`：老库升级没事、**全新安装直接炸** |
| 受保护页面挂 `AuthGuard` 且在**路由层**拦 | 页面内自查拦不住已经装出来的界面 |
| 无效身份由客户端在上行前拦（`AiIdentity.usable`） | 发占位符学号 = 网关把配额记到一个不存在的学生头上 |
| `SimulatedAiDataSource` **不是脚手架，不要删** | 它是本地/离线模式的行为基准（FNV-1a 确定性） |
| 演示种子与真实数据**必须分开** | 否则用户第一次打开就看到别人的孩子（§8 P1） |
| 部分唯一索引上的 `ON CONFLICT` **必须带 `WHERE`** | 漏了当场 `42P10`——PG 推断不出该索引 |
| 建 policy 后**必须** `ENABLE ROW LEVEL SECURITY` | 隔离**静默失效**（policy 建成功、无任何报错），某天变成「一个班互相看得见」 |
| 应用必须用**普通角色**连库 | superuser 绕过 RLS，连 `FORCE ROW LEVEL SECURITY` 也拦不住 |
| `invite` 的 `ON CONFLICT` **必须带 `WHERE status IN (…)`** | 漏了则「重新结伴」**静默不动**，而接口回的是「你们已经结伴」——**与事实正好相反**（§1.2） |
| 解除结伴**只改状态、不删行** | 删行会把同一对关系的历史切成两段，而且不可逆；「重结伴后全可见」正是靠它才成立 |
| 通知里的 `relationship` **不参与页签跳转** | 学生端没有「结伴」tab，硬塞一个最接近的落点（比如心愿）会让人点进去看到一堆无关内容 |

## 6. 非功能需求

### 6.1 安全

| 项 | 要求 | 现状 |
|---|---|---|
| 模型 Key | **绝不进客户端** | ✅ 只在网关环境变量 |
| 身份 | 服务端签发、可吊销的会话 token（HMAC） | ✅ 会话表（S2）+ 客户端逐请求带票（P0-2，2026-09-20）；⚠️ 旧的 `X-Student-Id` 通道仍在，网关侧由 `AI_REQUIRE_AUTH` 收口（演示栈默认开） |
| 多家庭隔离 | 数据库机制（RLS），不是「记得写 where」 | ✅ 逐表 policy + 启动自检 |
| 越权 | 家长访问孩子数据一律过关系鉴权 | ✅ 中间件 |
| 审计 | 记录「谁调的、花了多少、有没有异常」 | ✅ **刻意不含学生答案与作业照片**（照片里有姓名、班级、住址） |
| 口令 | scrypt 哈希 | ✅ |
| 跨域来源 | **不限来源**（平台 Default CORS 会反射任意 `Origin`，且允许凭证） | ⚠️ **已知现状、没收窄**。之所以没被放大：会话是 **Bearer 票**而不是 Cookie。⚠️ **别把它改成 Cookie 会话** —— 那个组合会当场变成「任意网站都能带着用户身份打你的接口」（§4.5） |
| 云凭证 | 全部轮换 | 🔴 **未做**：AK/SK、数据库口令、`AI_SESSION_SECRET` **都进过对话记录**；OSS 子账号带着 `AliyunRAMFullAccess`（能自己给自己挂权限）**该撤**；RDS 白名单**未收窄** |

### 6.2 性能与时延

- 数据 API 目标 **10–50ms/次**（无外呼）；AI 端点本来就要等 10–30s，前端必须能等。
- 首屏读**一次往返**：`GET /data/bootstrap` 把 18 条按场景 1:1 的读聚成 1 条 —— 服务端完成度是
  `bootstrap`（**已落地，2026-09-21，P2-2**）；`home/*` / `review/board` 仍是 1:1（见 §8）。
  客户端的用法是「读缓存优先 + 聚合预热」：任一条读未命中缓存时顺手打一次聚合，把 20 个段灌进缓存。
  **聚合是加速手段，不是数据通路** —— 它 404 / 超时 / 段名不符时一律退回逐条读，行为不变。
  判据在端到端走查里（首屏业务读 ≤3 次）。
- AI 侧真正的瓶颈是**输出长度**而非速度：12s 窗口 ≈ 只够 500 输出 token。

### 6.3 成本与配额

- 配额按**成本单位**分桶（视觉 8 / 强推理 2 / 轻量 1），按**人**（`sub`）计，不按班。
- ⚠️ 默认配额与缓存是**进程内存**（多实例各算一份、重启即丢）→ 拦得住「一分钟猛打」，
  **拦不住「刻意拉开间隔刷」**。要真正有效必须配共享 KV（抽象已就位，默认配置不会自动变安全）。
- 看板从**审计事件**聚合；没配单价时 `cost: null`（不是 0），含义是「成本未知，仅有用量」。
- ⚠️ **云上 `AI_KV_URL` 是空的**（2026-09-27 读 `.env.prod` 确认）⇒ 上面那条「进程内存口径」
  就是**生产现状**，不是「默认值可能不安全」的假设。要真管住刷量，才轮到配共享 KV。
- ⚠️ 云上 `CORS_ALLOW_ORIGIN` 也是空的 —— 它是**死配置**（只有本机 `dev-server.js` 读它）。
- ⚠️ **别只看 FC 的算力账单**：上次全站挂掉的直接原因是**账户余额为 0**，
  触发它的是 **2 分钱**的计算费用。`余额 > 0` 与「费用预警」比任何优化都优先。

### 6.4 可靠性与降级

- AI 不可用/未开通/超预算时：**如实失败并降级**，降级结果落库留痕；
- 断网时：读走缓存且**可见地**标记为旧数据；写**必须在线**且如实失败；
- 通知失败不阻断主流程。⚠️ 这里有一个**已解决但很贵**的坑值得记住：跨用户写通知在 RLS 下，
  `INSERT … RETURNING` 要求新行能被**读**策略看见，否则报错、
  而报错文案指向的是**写**策略（`42501 new row violates row-level security policy`）——
  看起来像五六个互不相关的 bug，实际是同一个。处置是写完不读回来，返回值由 JS 侧组装。
  详见 `cloud-migration-plan.md` §5「S3 落地情况」②。

### 6.5 可观测与可诊断

- 网关：审计日志 + `/ai/metrics` 看板 + `scopeNote`（声明口径，避免被当全局数字）。
- 客户端：`AiStatusController` / `AiObserveController`（家长端看板）、`DataStatusController`（陈旧读横幅）、`AiDegradationLog`。
- 排障入口：业务说「AI 没生效」时**先查身份**（`verify-ocr-identity.mjs` 一次跑完四种情形）。

### 6.6 可部署性

- 网关：零 runtime 依赖、单入口（veFaaS / SCF / FC 事件形状一致，不改代码）。
- 数据服务：独立部署；**Serverless + PG 必须解决连接数**（PgBouncer / RDS Proxy / HTTP 驱动），这条要在 S1 就定。
- 区域必须与函数在一起（跨区延迟会吃掉首屏预算）。
- ⚠️ **Web 版的落点不在阿里云**（2026-09-26 定）：OSS 静态网站托管的**默认域名**访问 HTML
  会被浏览器**强制下载而不是打开网页**，要正常浏览必须绑**已备案**的自定义域名
  （中国内地 Bucket 绑域名强制 ICP 备案）⇒ **云空间里没有现成的静态入口**。
  现在用的是**分享链接**（免备案、自带 HTTPS），见 §10.3。
- Web 版的发布前校验是**六道闸门**（`tools/build-cloud-web.mjs`）：地址必须 https 且非本机 ·
  两个地址探活 · **flutter 真能跑** · 构建 · 产物不许残留 `127.0.0.1` · 产物必须字面含两个生产域名。
  ⚠️ 最后一道是有原因的：`build-mode.mjs --expect cloud` 的判据是「产物里**有没有**服务端地址」，
  不是「是不是**生产**地址」—— 它对一份**指向 `127.0.0.1`** 的产物照样打印
  「✓ 模式：云端」，单靠它会放行一份「点了没反应」的 Web 版。

⚠️ **脚本名里的 `ark` 是历史遗留**（厂商已换百炼，槽位名没改）。**别按名字判断当前厂商。**

**真凭证第一次跑就抓出两个本地怎么测都测不出来的问题**（都发生在 2026-09-20）：

| 问题 | 为什么本地看不见 | 修法 |
|---|---|---|
| **讲解超客户端窗口**：客户端文本窗口 12s，讲解实测 14–41.6s（出参 60%+ 是思维链） | 超窗口**不报错** —— 客户端安静地退回本地模板，看起来只是「AI 好像没生效」。而判定的耗时只有 3–4s，拿它代表整条链路会得到「模型够快」的错误结论 | `AI_THINKING_DISABLED_KINDS`：关掉讲解/出题/批量的思维链后 2.1–6.8s 全部落进窗口，且全部通过 schema 校验。**判定不关** |

⚠️ **这两条的性质是同一类**：失败都不报错，只表现为「某个功能安静地不对」。
所以真凭证验收的价值不在「确认接得上」，而在**把这类静默失败逼出来**。

⚠️ 两个「像功能坏了、其实是判据坏了」的坑，写在这里因为下次还会踩：
**① 会自动隐藏的元素（横幅 20s）必须在窗口内断言**——先花 10s 找作业再探横幅，
结论就是「横幅没实现」，而同一张截图里横幅清清楚楚；
**② 用 CDP 改客户端 localStorage 必须在新文档启动前注入**——`evaluate` 当场改是竞态，
客户端卸载时用内存快照整份覆盖回去（改 3600s、新文档读到 48s），
后果是**反向**的：「构造出了新鲜缓存」，要验的场景根本没发生。

**③ 演示栈里最难查的一条是「PG 自己崩了」**，它长得像三件别的坏事：
客户端报「数据库暂时无法连接」、网关侧 0 请求、走查在第 4/5 步断掉。
真相在 PG 自己的日志里，而那份日志原来被 `onLog: () => {}` **整份吞掉**。
放行 FATAL/PANIC 之后一眼可见（2026-09-20 实测两份）：

```
PANIC:  could not open file "global/pg_control": Permission denied
LOG:    server process (PID 49840) was terminated by exception 0xC0000409
FATAL:  the database system is in recovery mode
```

`0xC0000409`（Windows 快速失败）是被 `pg_control` 读不到触发的 —— 数据目录里的文件
**对 PG 自己间歇性不可访问**（典型是杀软实时扫描 / 文件锁）。它不是应用逻辑问题，
但那一段时间的代价全落在功能头上。两条对策都已落地：
① 数据服务**不许因为一条空闲连接出错就退出**（`pool.on('error')`）；
② 借连接遇到**已知瞬时**的失败会等到一个预算（默认 5s），而永久失败（口令错等）
立刻报且**不许说成「暂时无法连接」**。两份实测里 PG 崩了两次并自行恢复，
走查仍全绿 —— 这就是那两条对策在起作用。

## 9. 刻意不做的事

写在这里是为了防止「下一个人以为是漏了」。

| 不做 | 原因 |
|---|---|
| 多学校 / 机构层 | 只做到**班级**级；再往上抽象会做错 |
| 老师角色（本期） | **同时也不做班级**：班级号由老师建班时生成，没有建班角色就没有真实班级号，「申请加入班级号」没有服务对象。设计已定死，实现与老师角色同一提交落地 |
| 实时推送 | 先轮询，够用再上 WebSocket |
| 离线写队列 | 方案 B 下写必须在线（选 C 才需要） |
| 自动合并存量本地数据 | 需要冲突解决；演示数据本来不重要 → 给显式入口 |
| 服务端 SQLite | 「一个班」直接否决：SQLite 没有 RLS，隔离只能靠应用层记得写 where |
| 动包名/签名/图标 | 与数据上云无关，是独立的一件事（P1-2） |
| **微信登录（本期不接）** | **不是「差个开关」，是从来没接过**：`POST /auth/login-wechat` 恒返 **501**（**刻意**占位 —— 返 404 会让人去查「是不是这次部署漏了代码」）。卡在三层：① 代码（`pubspec.yaml` 里没有任何微信 SDK 依赖）② 资质（开放平台开发者认证 **300 元/年**）③ **域名**（网站应用的授权回调域**必须已备案**，而 Web 版挂在分享链接的域名下 ⇒ **结构上接不了**）。⚠️ **App 版是另一回事**：移动应用绑的是**包名 + 签名**，不依赖域名备案。建议等「自有备案域名」这一步真要走时一起做 —— 详见 `open-items.md` **C7** |
| **短信验证码 / 找回密码（本期不接）** | 结构全就位（三态结果、冷却秒数、用途分离），**只差一个服务商账号**；客户端 `UnconfiguredSmsGateway.isConfigured` 恒为 `false` ⇒ **如实失败、不伪造成功路径**。伪造的后果不是「演示不好看」，而是接入之后没人知道哪一段代码其实是假的 |

### 10.3 怎么打开应用（三种方式）· 本机怎么演示

| 方式 | 状态 | 怎么做 |
|---|---|---|
| **网页版** | ✅ **已上线**（2026-09-26） | 浏览器打开 **`https://banxue.app.workbuddy.host/`** —— 零安装、免备案、自带 HTTPS。首次要下约 5MB 的 wasm 运行库（首帧约 3s），之后走缓存 |
| **安卓** | ✅ 可用 | `node tools/build-cloud-apk.mjs --out apk`。⚠️ **别装同目录里那份 `app-debug.apk`**（那是本地模式的旧产物） |
| **苹果（iOS）** | ⏳ 未构建 | 配置齐，本机是 Windows 做不出来（§7.5） |

⚠️ **发布目录是 `site/`，刻意不叫 `build`/`dist`**：发布工具有「排除构建产物」的规则，
万一按目录名匹配，整个目录会被**静默跳过** —— 上传成功、页面空白、零报错。
`.gitignore` 已加 `/site/`。

**重建 Web 版**：`node tools/build-cloud-web.mjs` —— 构建 + **六道闸门**校验 + 整理出 `site/`，
最后一道会检查产物里**同时**有「两个生产域名」和「零个本机地址」。

⚠️ **别拿 `build/web` 里现成那份去发**：它是 **09-21 的本机模式**产物
（`main.dart.js` 里 `127.0.0.1:8788` 命中 1 次、`fcapp.run` 命中 0 次），
发出去的症状正是「能打开首页，点了连不上后端」。**要发就必须重新构建。**

```bash
# 一条命令：起 PG + 迁移 + 演示数据 + 数据服务，跑完走查自动收栈
cd serverless/data-service && node scripts/dev-stack.mjs --no-ai \
  --run "node tools/walkthrough-cloud.mjs"

# 客户端要指向本机服务构建，否则点进去走的是本地模式
flutter build web --dart-define=DATA_API_BASE_URL=http://127.0.0.1:8788
```

> ⚠️ **要不要带 `SEED_DEMO_DATA=true`，看构建走哪一侧**（别照抄错的那条）：
> 上面这条带了 `DATA_API_BASE_URL` → **云端模式**，数据由服务端 `seed-demo.mjs` 灌，
> 客户端那份种子本来是空操作，**不需要也不该加**；
> **纯本地模式**（不加 `DATA_API_BASE_URL`：README 里的 web 演示构建、
> `android-deploy-guide` §1.1 的演示 APK）**必须**加 `--dart-define=SEED_DEMO_DATA=true`，
> 否则首屏是空的 —— 从 2026-09-21 起客户端默认不灌演示数据（理由见 `lib/services/demo_seed.dart`）。

⚠️ **演示数据按天刷新**：种子作业的 `dueAt` 落在「当天 23:00」，客户端按天过滤，
所以种子脚本判重时带「今天有没有」，换一天会自动补一份（否则第二天演示首页是空的）。
⚠️ 走查的截图与断言日志落在 `build/demo-evidence/`（`06_offline_reload.png` 是断网读缓存那一步的证据）。
