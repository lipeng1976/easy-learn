# 架构改造方案：从「单机本地库」到「云端权威」

> 目标（虫子定调）：**数据最终在云端；后端逻辑保持不变；差异只出现在前端。**
> 本文把这个目标翻译成可执行的分层与迁移顺序，并标出**几个只在"上云"时才会暴露的陷阱**。

---

## 0. 一处必须精确化的地方

「后端逻辑不变」这句话方向对，但**今天它还不成立——因为"后端逻辑"目前不存在**。

现状是：业务规则**没有归口**。它散在两处：
- 一部分在 `lib/controllers/*.dart`（4 个控制器共 4483 行，其中 96 处直接调库）
- 一部分在 `lib/services/review_service.dart`（**这一块建对了**，见 §2）

所以如果只是"把 SQL 换成 HTTP"，规则会**留在客户端**，后果是：

1. **三端各自实现一遍 → 必然漂移**。这个项目已经踩过一次同形状的坑：作业识别后的归一化之所以不交给模型，唯一理由就是"会漂"——同一张图重跑结果不同。规则散在三个客户端里的漂移比模型更严重，因为它不会报错，只会让三端显示不同结果。
2. **规则在客户端 = 可绕过**。积分发放、毕业判定、鉴权跑在客户端，改包即可刷分。
3. 小程序端要**重写一遍**规则（Flutter 无小程序 target，是另一个语言栈）。

**正确的表述**：不是"前端有差异"，而是——

> **最上面那层（UI + 平台能力）有差异；它以下的全部共享。**

## 1. 目标分层（三段）

```
┌──────────────────────────────────────────────────────────┐
│ L3 平台适配层        UI / 相机 / 文件 / 分享 / 网络 / 登录 │  ← 唯一因平台而异
├──────────────────────────────────────────────────────────┤
│ L2 数据访问层        Repository 接口 + 多实现              │  ← 本地 / 远端，按平台注册
├──────────────────────────────────────────────────────────┤
│ L1 领域层            纯规则，零 IO，无平台依赖              │  ← 唯一真相，可原样搬到云函数
└──────────────────────────────────────────────────────────┘
```

L1 是这次改造的**重点**，不是 L2。理由：L2 换实现是机械工作（审计显示 73/107 个方法是纯数据访问），而 L1 决定了"将来加一个客户端是**接入**还是**重做**"。

### L1 还要再切一刀

| 子层 | 内容 | 放哪 | 为什么 |
|---|---|---|---|
| **L1a 权威规则** | 计分发分、毕业判定、批改口径、鉴权、配额 | **服务端** | 涉及公平与数据完整性，客户端可被绕过；且它在定义上就不可能三端漂移 |
| **L1b 只读派生** | "还差 1 次毕业"、"本周掌握率 67%" 这类**提示性**计算 | 客户端可算 | 避免每次点一下就往返一次网络；但**只作展示，不作数** |

这条区分是为了避免两个极端：既不要把每个 UI 提示都做成一次网络请求，也不要让客户端算出"毕业了"这种结论。

### 平台差异边界（真实的，不含 UI 风格）

| | iOS | Android | 鸿蒙 | 微信小程序 |
|---|---|---|---|---|
| **L1 领域层** | 共享 | 共享 | 共享 | ⚠️ **唯一真差异点**：有归口可移植，散着写就得重写 |
| **L2 数据访问** | SQLite + 远端 | 同 | 同 | ⚠️ **没有 SQLite**，只有远端 + 10MB 缓存 |
| **L3 平台能力** | 相机/相册/分享/文件 | 同 | 同 | `wx.chooseMedia`/`wx.login`/`wx.shareAppMessage` |

**注意 L2 那一行**：小程序端不是"本地实现差一点"，是**没有本地实现可选**。所以 Repository 接口必须设计成「**允许某个平台不注册本地实现**」——否则接口会隐含假设本地库一定存在，而那个假设在小程序上不成立。

## 2. 现状对照（方法级审计结果）

审计 `lib/services/database_service.dart`（4172 行 / 107 个方法）：

| 类别 | 数量 | 处置 |
|---|---|---|
| **纯数据访问** | **73** | 机械替换，低风险 |
| **混了业务规则** | **22** | 需逐条判断规则归属（§4 列了最难的 5 个） |
| **纯规则（无 IO）** | 2 | 只是格式解析（`_parseWeekdayList` / `_parseNullableTime`） |

**这里有一个反直觉的好消息**：真正"不碰存储的业务规则"在本文件里**几乎是 0 个**。毕业判定、掌握率、毕业分档、周期报告都在 `review_service.dart` ——

### ✅ 已经建对的那一块：`review_service.dart`

866 行，**零 SQL、只依赖 model**，全静态纯函数：`compose`（组卷）、`judge`（判卷）、`masteryRate`、`buildPeriodReport`、`nextRound`、`periodStart`。

**这就是 L1 的标准形态，也是本次改造的模板**。它可以直接搬到云函数（Dart 写的话用 Dart Server，或按测试用例重写为 JS）。

### ⚠️ 已经内嵌的第二套实现：77 个 `_webStore` 分支

77 个业务方法里含 `if (kIsWeb)`，即**同一个类里挤了两套实现**（SQLite 版 + 内存版）。

这是**可复用的既有资产**：抽 Repository 接口时，把 `if (kIsWeb)` 的两支拆成两个实现类即可，不用从零设计第二实现——它已经被验证过（Web 一直在跑）。

### ❌ 缺的是

- **Repository 接口**（不存在；111 处调用点直接绑着 `DatabaseService` 具体类）
- **其他领域的 L1**：作业、积分、关系、通知的规则目前**住在 controller 里**，且 controller 直接调库——规则与数据访问缠在一起，无法单独上移。

## 3. 五个「本地永远不炸、上云才会炸」的陷阱

这五个是我逐个核对代码找出来的，**它们的共同特征是：在单机单进程下被掩盖，换成多端并发后立刻暴露**。改造时必须逐个处置，不能等出事。

### ① 积分幂等：最后防线在数据库引擎里 ⚠️ 最危险

```dart
// database_service.dart:4141
final rowId = await db.insert('point_ledger', entry.toMap(),
    conflictAlgorithm: ConflictAlgorithm.ignore);   // ← 撞上唯一索引就静默跳过
return rowId > 0;                                    // ← 靠 rowId 判断"这次真的写进去了"
```

防线是 `CREATE UNIQUE INDEX idx_point_ledger_active_key`（在 `reversedAt IS NULL` 上唯一）。**这条约束是"不重复发分"的最终保证**，业务代码只是"先查一次（`findActivePointEntry`）避免白跑"。

**修正一处我原来的判断（核代码后发现写错了）**：`PointController._write` 的注释里已经写明「真正的保证是数据库那道部分唯一索引，下面的 insert 返回值才是最终裁决」—— **作者知道这件事，现有代码没有竞态**：正确性押在 `insertPointLedger` 的返回值上，而本地实现（部分唯一索引 + `ConflictAlgorithm.ignore` + `rowId > 0`）确实提供了这个原子保证。Web 端那套内存实现也是同步完成的（`any` 与 `add` 之间没有 `await`），在 Dart 单线程模型下同样成立。

**所以真正的隐患不在实现，在契约**：这条「返回值即最终裁决」的约定**此前只存在于代码注释里，没有写在接口上**。换实现的人看不见它，很容易写一个「尽力而为」的版本（先查再插，或者忽略返回值）—— 症状就是**静默重复发分**。**已在第 0 步把它写进 `PointRepository.insertPointLedger` 的文档注释**：服务端实现必须提供同等强度的原子保证。

**上云后**：两个端同时提交同一份作业 → 两边都查到"没有"→ 两边都写入 → **重复发分且不报错**。

**处置**：客户端那条"先查"降级为**乐观预检**（只为省一次往返，不承担正确性）；正确性**必须由服务端的唯一约束承担**（云端库里建同样语义的唯一索引，或写入走一个原子的「若不存在则插入」）。

### ② `updateHomework` 的 null = 「本次不改」在 HTTP/JSON 下会坏 ✅ 已定

当前签名有**四态**：`null` = 不改、具体值 = 改成它、`bool? false` = 显式写成 false（注释里专门写明了原因）、`clearResult: true` = 清空一批字段。

在 Dart 里这能工作，因为「没传」与「传了 null」由**调用方语法**决定，编译期就分开了。但**这份区分活不过一次序列化**：云端接口要发 JSON，而 `{"score": null}` 与「`score` 这个键不存在」在标准 JSON 库里是**同一个东西**。偏偏「把 `score` 写成 null」**正是清除批改结果要表达的意思** —— 于是 `clearResult` 的意图会在网络边界上被静默抹掉，症状是**重新提交后家长仍看到上一次的旧分数**（不报错、不崩，只是数字不对）。

**处置（已落地）**：改为 `HomeworkPatch` 的**显式字段掩码** —— 掩码由「被 setter 写过」这个事实给出，而不是由「值是不是 null」推断。`toMap()` 就是可直接上行的字段集合，调用方**无法**表达出歧义。见 `lib/repositories/homework_repository.dart`。

**同一族的残留**：`updateReviewMistakeState` 仍是「`null` = 本次不改」的可选参数签名，尚未收敛成掩码 —— 属**待定项**，需与上云改造一起定死（已写在该接口的文档注释里）。

**同一族的正面对照（已合规，不用动）**：`updateWishRedeemState` 用**显式的
`clearRedeemRequest` / `clearRedeemRejected` 标志**表达「清空」，而不是靠「传了 null」
推断 —— 序列化后语义不变。写新接口时照它抄。它唯一的不对称是 `redeemedAt` 只能设不能清
（没有对应标志），将来要支持「撤销兑现」得补一个，**不要**改用 `null`。

### ③ 5 表级联删除需要服务端事务

`deleteReviewMistake` 一次删 5 张表（`review_mistake` + `review_attempt` + `judgement_ab` + `ai_practice_question` + `explain_record`）。本地是 SQLite 事务；改成多次 HTTP 调用会**中断在中间**，留下孤儿记录（`review_attempt` 是毕业判定的唯一依据，残留会让判定错乱）。

**处置**：服务端提供**单个**「删除错题及其全部证据」的端点，内部用服务端事务。**不要**让客户端编排 5 次调用。

#### ⚠️ 顺带发现一处同族缺陷（2026-09-18 核代码时发现，本期**刻意不改**）

`deleteReviewMistakesByHomeworkId`（重新提交时清掉旧错题）**只删 `review_mistake` 一张表**，而它的兄弟方法删 5 张 —— 两者不对称，从属行会留成孤儿，正是本节的注释里明确说要避免的情况。

触发路径真实存在：批改写出错题与影子比对记录 → 学生重新提交 → 删旧错题（孤儿留下）→ 新错题再写一批 → **同一道题的判定被重复计入一致率**。

已核代码确认孤儿行真的会进分母：`queryJudgementAB(studentId: X)` 只按 `studentId` 过滤，**不与 `review_mistake` 关联**（`database_service.dart:2211`）。

**为什么不在第 0 步顺手修**：第 0 步的承诺是零行为变化，而"要不要级联"其实是一个**产品判断** —— 一致率衡量的是"模型判定 vs 本地规则判定"的质量，它未必要跟着错题的生死走。两种口径都讲得通，得先定口径再改代码。已记入两个接口的文档注释。

### ④ 客户端鉴权 = 没有鉴权

`_requireActiveRelationship`（`database_service.dart:2893`）在本地校验"请求方是关系成员且关系 active"。它是**数据访问方法里的鉴权**，用的是客户端自己库里的数据。

上云后，这段若留在客户端，等于**让请求方自己声称自己有权限**。同理 `X-Student-Id` 目前是客户端自报的，所以 `AI_REQUIRE_AUTH` 至今不敢开。

**处置**：鉴权随服务端登录一起上移。**顺序上这决定了「服务端登录」必须先于「数据上云」**——没有真身份的数据上云，只是把"数据在谁的手机里"换成"数据在谁都没管的表里"。

### ⑤ 图片的 `storageKey` 是设备本地标识 ✅ 已改正

> ⚠️ **本节原先写的是「`imageBlobs` 表存 base64」，这是错的。** 全库**没有** `image_blobs` 表（22 张表里没有它）。

真实形态：

- `homework_image` 表只存 `storageKey`（外加 `fileName` / `fileSize` / `mimeType` / `ocrStatus` 等元数据），**不存字节**；
- **原生端**：`storageKey` 是**绝对文件路径**。`image_file_writer_io.dart` 把字节写到**文稿目录**（`easy_learn/homework/<studentId>/`）—— 刻意不用临时目录，因为临时目录会被系统在空间紧张或重启后清理，症状是"家长端图片不可用"；
- **Web 端**才用 base64：`storageKey` 是 localStorage 的键（`_persistWebImage`，带 `maxWebImageBytes` 上限，超限会 `debugPrint` 警告并放弃持久化）。

**真正的陷阱**：`storageKey` 是**设备本地标识**，只在那一台设备上有意义。上云后它必须换成**任何设备都能解析的全球标识**（对象存储 key / URL），否则换手机后 `storageKey` 指向一个不存在的路径 —— 而读取失败是**静默返回 null**（`readImageFile` 与 `_loadWebImage` 都把异常吞掉），症状是**照片位置一片空白，没有任何报错**。

**处置**：图片字节走对象存储（网关已预留 TOS 外链模式），库里存对象 key。本地可继续缓存副本供离线查看，但**权威副本在对象存储**，且 `storageKey` 的语义要一并改掉。

### ⑥ 「先取全表，再在客户端过滤」= 越权点，且有一批 ⚠️

第 0 步收尾时把最后 4 个领域（心愿 / 学习计划 / 运动 / 通知）的调用点过了一遍，
发现它们**共用同一个形态**：

```dart
// 数据访问层：无任何过滤
final all = await db.query('daily_comment', orderBy: 'createdAt DESC');

// 控制器：拿到全表之后，在内存里挑「我结对的孩子」
final mine = all.where((c) => _belongsToBound(ids, c.studentId)).toList();
```

`ParentController` 里这样的内存过滤有 **8 处**（作业图 / 作答 / 错题 / 卷子 /
打卡 / 点评 ……），另有 3 处把 `userRole` 直接当 SQL 条件用
（`wish.userRole`、`study_plan.userRole` —— 这两个字段是**由客户端传进来的身份**，
写进了表）。

单机单库下这两件事都不会炸：库里只有这一台设备的数据，「全表」本来就等于
「我应该看的那部分」。上云后则同时坏两个方向：

| | 症状 |
|---|---|
| **性能** | 每个客户端都拉走全库数据（全部学生的点评、打卡、通知……） |
| **安全** | 过滤发生在一个**可被改包的客户端**里 —— 等于没有隔离；`userRole` 由调用方自报，写成对方就能读对方的心愿 |

**处置**：第 2 步（服务端登录）落地时，把「我能看谁的数据」从
「客户端传进来的 `userRole` / 内存 where」改成**服务端按 token 推导**；
接口上保留 `userRole` 参数只是为了让本地实现继续可用，**它不进契约**
（已分别写进 `WishRepository` / `StudyPlanRepository` / `WorkoutRepository` /
`NotificationRepository` 的类注释）。

**顺带说明 `StudyPlanRepository` 里藏了一条规则**：`queryStudyPlans` 的
`userRole == 'student'` 分支是**全表返回**，家长分支才过滤 ——
「学生能看到家长发来的全部计划」这条可见性规则**写在数据访问方法内部**。
这是第 1 步要剥离的对象之一；在此之前，谁换实现都得知道那个「全表」不是笔误。

### ⑦ 通知的**产生位置**错了 —— 照现在的形态上云，功能直接不成立 ⚠️ 最结构性

其余陷阱都是「实现要改」，这一个是**结构不对**：

```dart
// NotificationController.addNotification
await _database.insertNotification(notification);   // 写进「自己这台设备」的库
```

通知是**哪台设备显示、就由哪台设备生成**。单机演示下它是通的 ——
学生提交作业后家长确实能看到，**因为两个角色共用同一个库**。
换成两台手机后，学生手机写进的通知在家长手机上**根本不存在**，
`targetUserId` 填得再准也换不来一条记录。这不是配置问题，也不是同步延迟问题。

**处置**：上云后通知必须**由服务端在事件发生时生成**（提交作业 / 批改完成 /
打卡 / 心愿申请…），客户端只读。到那时 `insertNotification` 退化成服务端内部调用，
客户端侧不该暴露这个能力。

#### 同族发现：广播通知的已读状态是**全角色共享**的（本期刻意不改）

`app_notification` 只有一列 `isRead`，而广播行（`targetUserId == ''`）
是**所有角色共用的同一行**。所以 **学生点掉一条广播，家长端的未读数也一起消失**。

触发路径真实存在：演示数据里的通知大量是广播（`targetUserId` 为空，
见 `_ensureWebSeed`），点一下「全部已读」就全清了。

正解是**每用户一份已读状态**（`notification_read(userId, notificationId)` 关联表），
而不是把 `isRead` 放在通知行上。之所以不在第 0 步顺手改：它需要一张新表 + 一次
DB 版本升级，超出了「纯重构、零行为变化」的范围。已写进
`NotificationRepository.markNotificationRead` 的文档注释。

## 4. 迁移顺序（每步行为可验证）

原则：**每一步做完，App 都能正常跑、325 个测试全绿**。不允许出现"改到一半不能用"的中间态。

| 步 | 做什么 | 风险 | 做完能验证什么 |
|---|---|---|---|
| **0** | **抽 Repository 接口**：按领域切 9 个接口，`DatabaseService` 退化成实现；拆开 77 个 `kIsWeb` 分支 | **零**（纯重构） | 325 测试全绿；111 处调用点收成 1 处；**行为一行没变** |
| **1** | **规则归口**：把 4 个 controller 里的业务判断剥成 L1 领域服务（照 `review_service.dart` 的样子） | 低 | 控制器变薄；规则可被独立测试；**这是"后端逻辑"真正诞生的时刻** |
| **2** | **服务端登录**：网关发 token，客户端不再本地比密码；鉴权上移 | 中 | **换手机登同一账号成立**；`AI_REQUIRE_AUTH` 可以打开了 |
| **3** | **只读上云**：结伴关系走服务端，家长端从服务端读孩子数据 | 中 | **"两台手机"这个用例到这里就通了**，且不需要冲突解决（写入仍只有一处） |

### 第三批新发现：`LocalSeedService` 是**抽象层的实际漏洞**（需定夺）

前三批的接口注入有个被 `LocalSeedService` 绕过去的洞，收尾核代码时才看全：

```dart
class LocalSeedService {
  static Future<List<HomeworkItem>> studentHomework() async {
    await init();                                                   // ← seedIfEmpty()
    return DatabaseService.instance.queryHomework('student');       // ← 绑死具体类
  }
}
```

它**不是**「只用来造演示数据」的：它是**三个控制器的初始列表加载路径**，
共 19 个调用点（`ParentController` 7、`StudentController` 6、`ReviewController` 6）。
后果很具体：

1. **给控制器注入假仓库，这些读取不会跟着变** —— 注入只覆盖了写路径和少数读路径，
   测试里换不掉真实数据库，接口冻结在**读**这一侧是名义上的；
2. 上云那天，这 19 处是**漏网的直连点**（不在任何接口后面）；
3. `init()` 把「首次运行灌演示数据」这个副作用**藏进了每一次读取**里 ——
   数据上云后，本地灌演示数据这件事本身就不该发生。

**为什么这次不顺手改**：它**不是**零风险的机械替换。`await init()` 目前是
load-bearing 的（Web 端 `_ensureWebSeed` 依赖它在首次读之前跑完），
把它从读路径上摘下来需要先定「seed 到底该在哪一步跑」，
否则症状是首次启动列表空白 —— 属于行为变化，超出第 0 步的承诺。

**待定夺（两个选项）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 现在收口** | `LocalSeedService` 去 static、改持 6 个接口；或直接删掉这层，控制器调 `_homework.queryHomework('student')` 等，`init()` 提到应用启动处调用一次 | 中：需先定 seed 时机，19 个调用点 + 启动流程一起动 |
| **B. 保持现状** | 只在文档里标为「上云前必清的漏网点」 | 低：但接口冻结在读侧继续是名义上的 |

我的倾向是 **A**，但要先定 seed 时机——它其实是「本地演示数据从哪来」这个问题的一部分，
和「上云后演示数据是否还由客户端灌」是同一个决定。

## 5. 本期刻意不做的事

- **不做离线队列与冲突解决**：第 4 步之前不存在并发写入，先做等于给不存在的冲突付费。
- **不删本地 SQLite**：它从"唯一的家"降级为"离线缓存"。孩子在学校网络不稳是常态，而且拍照识别本身就是大上传，网络本来就差。删掉它的结果是一个"在校门口打不开的作业 App"。
- **不追求"客户端代码变少"**：删掉本地库后同步层反而更大。变轻的不是客户端代码，是**设备之间的耦合**。
- **不动包名/签名**：`com.example.*` 与 debug key 是发布问题，不是架构问题，分开处理。

## 6. 结论

**"后端逻辑不变、只有前端有差异"的可执行版本是：把规则从"散在客户端控制器里"变成"有唯一归口（L1）"，数据访问收在 Repository 接口后面（L2），平台差异全部挤压到 L3。**

这么做的直接收益不是"能上云"，而是：
1. 将来加小程序是**接入**，不是重做；
2. §3 那五个陷阱会在**结构上被消除**，而不是等出事再补；
3. 规则终于**可被测试**——它现在是藏在 4172 行文件的 `if` 里。

顺序上不急：第 0、1 步零风险且与云选型无关，可以现在开始；第 2 步之后才需要云账号。

## 7. 云数据库选型（2026-09-18 补）

> 起因：虫子问「现在数据库是用的什么？以后要部署在云上的」。这里把**现状**和**选型的真正决定因素**记下来。

### 7.1 现状：三处存数据的地方，没有一处是云库

| 位置 | 用的什么 | 规模 |
|---|---|---|
| 客户端（App） | **sqflite = SQLite 本地文件库** | DB `version: 23`，**22 张表** |
| 客户端（Web） | 内存 `_webStore` + localStorage | 同一个类里的第二套实现，77 个 `kIsWeb` 分支 |
| 网关 `serverless/ai-gateway` | **没有数据库** | 配额计数默认进程内存（可选 HTTP 共享 KV）；上传对象在内存或 TOS；token 无状态自包含 |

**AI 那条链路已经上云了，数据那条链路完全还在设备里。**这是两件独立的事，别混在一起排期。

### 7.2 SQLite 为什么不能直接搬到云上

它不是一个"弱一点的数据库"，而是**结构上不同**：嵌入式、跑在**同一个进程里**、
**单写者**、一致性靠**文件锁**。把 `.db` 放共享盘/网盘上，文件锁失效 →
两个客户端并发写会**静默互相覆盖**（不报错）。论证见 `doc/multi-device-architecture.md`。

### 7.3 选型的真正决定因素：三件 SQLite 给了、别的库未必给的东西

我在代码里逐个核对过，这三条比"谁更流行"重要得多：

**① 部分唯一索引 —— 它直接淘汰 MySQL** ⚠️ 最硬的一条

```sql
CREATE UNIQUE INDEX idx_point_ledger_active_key
  ON point_ledger(idempotencyKey)
  WHERE idempotencyKey <> '' AND reversedAt IS NULL   -- ← 带 WHERE 的唯一索引
```

这是「同一个动作不会重复发分」的**最终保证**，代码注释写得很清楚：
「只靠 Dart 侧查一次再插是不牢的 —— 查与插之间永远有缝」（陷阱①）。

- **PostgreSQL：原生支持**（partial index）→ 这条 DDL **原样搬过去**；
- **SQLite：原生支持** → 所以今天它能工作；
- **MySQL / MariaDB：不支持** filtered index，只能改成
  「生成列 + 唯一索引」绕过（`active_key = IF(reversedAt IS NULL AND idempotencyKey<>'', idempotencyKey, NULL)`，
  利用 MySQL 唯一索引允许多个 NULL）。**能做，但那是重写，不是迁移。**

**② 7 处事务，其中两处跨表**

- `deleteReviewMistake` 一次删 **5 张表**（陷阱③），必须原子；
- `insertReviewPaperWithItems` 卷 + 题目一起写；
- 另有 `insertJudgementABRecords` / `saveHomeworkImages` / `insertReviewMistakes` /
  `insertReviewAttempts` / `replacePracticeQuestions`。

→ 排除「最终一致的 KV / 对象存储 / 单纯 key-value」当**主库**。

**③ 三个 upsert 唯一键 + 冲突策略**

`UNIQUE(planId, date)`（打卡）、`UNIQUE(studentId, action)`（积分规则）、
`UNIQUE(studentId, parentId)`（结伴关系），配合 `ConflictAlgorithm.replace / ignore`。
需要 `INSERT ... ON CONFLICT DO UPDATE / DO NOTHING` 这一级语义。

### ✅ 一个好消息：**0 个 JOIN**

全库 `JOIN` 出现次数是 **0** —— 所有查询都是单表 + 在 Dart 里拼装
（只有 3 处 `rawQuery`，两个是 `COUNT(*)`）。所以**迁移的工作量几乎不在 SQL 改写上**，
而在把「取全表再内存过滤」和「客户端自报的 `userRole`」下推到服务端（陷阱⑥）。

### 7.4 建议

**首选 PostgreSQL 系**，理由就是 §7.3① ——部分唯一索引能 1:1 搬，schema 几乎是原样，
事务与 upsert 全都现成：

| 选项 | 说明 |
|---|---|
| **火山引擎 RDS PostgreSQL** | 与方舟（AI 网关已在用）同生态，一台机器办完两件事，账单和网络都省 |
| **Supabase** | PG + 登录 + 对象存储 + RLS **一次到位**，正好覆盖第 2/3 步要的东西；缺点是数据出境，且国内访问要测延迟 |
| **腾讯云 PostgreSQL** | 若最终偏向腾讯/微信生态，这个更顺 |

**不建议的两条路**：

- **微信云开发的文档型数据库当主库**：它支持 partial index，但关系约束与事务要按 NoSQL 重设计，
  等于把 §7.3②③ 重新做一遍，还会削弱「同一套规则三端共享」这个最大优势。
  **将来真做小程序，也让它连同一个 PG 后端。**
- **Cloudflare D1**：它确实是 SQLite（schema 能搬），但用户在国内，延迟不合适，
  且单写者模型撑不住多端写入。

### 7.5 顺序不变：登录先于上云

第 2 步（服务端登录 + 鉴权上移）**必须早于**第 3 步（数据上云）。
理由在陷阱④：`_requireActiveRelationship` 这类客户端鉴权如果留着，
数据上云只是把「数据在谁的手机里」换成「**数据在谁都没管的表里**」。

### 7.6 顺带两条

- **图片字节走对象存储**（网关已预留 TOS 外链模式），库里只存对象 key ——
  因为 `storageKey` 现在是**设备本地绝对路径**，换手机后指向不存在的文件，且读取失败**静默返回 null**（陷阱⑤）。
- **网关的共享 KV**：现在默认进程内存，单实例够用；**多实例上配额会成倍放大**，
  上线前把 `AI_KV_URL` 指到 Redis / 表格存储即可（协议见 `serverless/ai-gateway/README.md`）。

### 7.7 一个必须排除的选项：服务端也跑 SQLite

这个选项容易被忽略，但**它在技术上成立**，所以必须正面排除，而不是不提。

§7.2 说 SQLite 不能上云的真正原因是「**多写者 + 文件锁**」。而**服务端独占时写者只剩一个** ——
客户端的并发写被 HTTP 请求串行化了，文件锁退化成进程内锁，问题消失。
迁移成本还接近于零：schema 完全一样，`DatabaseService` 的 SQL 几乎能原样搬
（部分唯一索引、`ON CONFLICT` upsert、事务，SQLite 与 PostgreSQL 两边都支持）。

**但它和 Serverless 部署形态互斥：**

| 部署形态 | 服务端 SQLite | 原因 |
|---|---|---|
| 单台常驻服务器 | ✅ 可行 | 一个进程写一个文件，写者唯一 |
| **Serverless（多实例、无状态）** | ❌ 不行 | 实例本地文件重启即失；多实例各写一个文件 = **数据分叉** |
| Serverless + 网络盘（NAS/CFS） | ❌ 不建议 | 又回到「文件锁在多写者下不可靠」，且延迟不可控 |

**所以真正的选择不是「PG vs SQLite」，而是「部署形态」。**

- 要 Serverless（不运维、按需伸缩、与 AI 网关同形态）→ **PG 是硬性要求**
- 接受一台常驻云服务器 → 服务端 SQLite 可行

**建议仍是 PG**，理由不是「SQLite 不够用」——一个家庭的数据量它绰绰有余。而是：
选 SQLite 省下的**只是「申请一个数据库」这一步**，换来三样代价：

1. 部署被绑死在单台机器上（不能伸缩、不能多实例容灾）；
2. 运维自己做（进程守护、备份、磁盘满了、机器到期续费）；
3. 用户变多时要**再做一次数据迁移** —— 而那时的迁移比现在难，因为库里已经是**真实用户数据**了。

再加上 AI 网关已经是 Serverless，数据服务用常驻服务器意味着**两套运维方式**。

> 反过来说：如果这个应用的目标就是「自己家用 + 演示」，从不想扩容，
> 那服务端 SQLite 是个**诚实的低成本选项**。但既然方向是多家庭、多端（含小程序），
> 一步到位更省事。

**开发阶段不受影响**：本机 Docker 起一个 PG 就能开工，**S1/S2 全程不需要云账号**。
