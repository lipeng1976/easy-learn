## 2 服务端怎么部署

### 2.1 路 A：函数计算 FC（推荐，改动最小）

现在两个服务的形态**就是** serverless：`index.cjs` 导出 `handler`。搬到 FC 要做的：

| 项 | 现在（火山/本机） | 阿里云 FC |
|---|---|---|
| 入口 | `index.cjs` → `exports.handler` | ✅ 同样支持（`handler` 是 FC 的标准入口名） |
| 运行时 | Node 20+ | Node 20 / 22，选 20 最稳 |
| 触发器 | 路径 `/data/*`、`/ai/*` | FC3 HTTP 触发器**默认透传完整路径** → 不用配；见下面那条 ⚠️ |
| 超时 | ≥30s / ≥60s | 函数配置里改（`s.yaml` 用 60s / 120s） |
| CPU / 内存 | — | **数据服务 0.5 vCPU / 1024MB；网关 0.25 / 512MB**。⚠️ FC3 要求 `cpu : 内存(GB)` 在 1:1~1:4 之间，**随手填 256MB + 0.5 核会直接 `InvalidArgument`** |
| 请求体上限 | ≥12MB（照片） | FC3 的**函数配置里没有这一项**（不是可调参数）→ 只能**实测**：发一张接近上限的原图，看收到的是本服务的响应还是平台的 413 |

**⚠️ 路径重写是老问题，但要分两种情形**：FC3 的 HTTP 触发器**默认把完整路径透传**
（事件里 `requestContext.http.path` 就是 `/data/bootstrap`），所以 `s.yaml` 那条路不用配路径。
**风险只在你前面又挂了 API 网关 / 自定义域名并且做了路径重写时出现** ——
一旦前缀被剥掉，`handler.js` 里「找 `/data/` 那一段」就无从下手 → 线上每个请求都 404，
**而响应体是本服务的标准错误信封、看起来完全正常**。部署后**第一件事**就是验这条。

### 2.2 路 B：ECS（如果没申请 FC）

那么现在的 serverless 代码要加一层常驻外壳 —— 本机那个 `src/dev-server.js` 就是现成的
参考实现（它把 `handler` 挂到 `http` 上）。需要：

- 一个进程管理器（`systemd` 或 `pm2`）保持常驻
- Nginx 反代 + TLS（两条路径 `/data/*`、`/ai/*` 分别转到两个端口）
- **`.env` 真的放在磁盘上** → 权限必须收紧（`chmod 600`），别用 root 跑

⚠️ 路 B 下「函数实例弹性伸缩」不存在了，**连接池算式退化成固定值**（§5.2）；
但**也**就没有「多实例配额计数翻倍」的问题了。

## 3 大模型：用开关选厂商（**已实现，无需改代码**）

> **2026-09-23 更新**：原先这一节写的是「换百炼必须改代码」，列了三处要动的地方。
> 那三处现在**已经收敛进一个开关**：`AI_MODEL_PROVIDER`。
> 下面保留原始分析，因为它解释了**为什么需要一个开关**（那些差异确实存在，
> 只是现在由适配层扛着，不由你手工扛）。
>
> **2026-09-30 晚再更新**：开关存在 ≠ 「只改一个配置」。两家原先**共用一组槽位**
> （`ARK_API_KEY` / `ARK_MODEL_*` / `AI_PRICE_*`），切换时要覆盖掉上一家的值、
> 切回来还得再改一遍。现在改成**两套配置并存**（`ARK_*` 与 `BAILIAN_*`），
> 切换才真的只动这一个变量。见 §3.3。

### 3.1 怎么用

```bash
AI_MODEL_PROVIDER=ark        # 火山引擎方舟（**默认**，不配就是这个）
AI_MODEL_PROVIDER=bailian    # 阿里云百炼
```

**不配 = 方舟**，所以既有部署零行为变化（已由 150 条原有测试保证）。

开关管的是**协议差异** —— 也就是那些「照抄过去不会报错、只会静默做错」的地方：

| | 方舟 | 百炼 |
|---|---|---|
| baseUrl 默认值 | 按 `ARK_REGION` 拼 `ark.<region>.volces.com/api/v3` | 固定 `dashscope.aliyuncs.com/compatible-mode/v1` |
| 思维链字段 | `thinking: { type: 'disabled' }` | `enable_thinking: false` |
| `tool_choice` 能否传对象 | 始终可以 | **思维链开着时不行**（会 400） |
| 嵌套结构会不会被**序列化成字符串** | 不会 | **会**（实测 4/4） |

`ARK_BASE_URL` 仍然可以盖掉默认值（自建网关 / 本机 Ollama 的退路都在）。

### 3.3 两套配置并存（2026-09-30 晚）

**切换 = 改 `AI_MODEL_PROVIDER` + 重新部署**，不需要再动任何值：

```
方舟那一组   ARK_API_KEY · ARK_REGION · ARK_MODEL_* · ARK_PRICE_* · ARK_THINKING_DISABLED_KINDS
百炼那一组   BAILIAN_API_KEY          · BAILIAN_MODEL_* · BAILIAN_PRICE_* · BAILIAN_THINKING_DISABLED_KINDS
```

**为什么**：共用一个槽位时，「换厂商」= 把上一家的值覆盖掉 —— 漏改一项就是
**用甲家的 Key 打乙家的地址**（401，看着像 Key 没开通，没人会怀疑变量名）。
切回来还得再改一遍。这不是运维不小心，是数据结构不对。

**三样东西必须跟着厂商走，而它们都不会报错**（所以必须在**读取时**就分好）：

| 跟着走的东西 | 分错了的症状 |
|---|---|
| 模型名 | 调用时才 `invalid_parameter_error`，且**未必带模型名**。自检在**两个方向**都拦 |
| 思维链名单 | 百炼用短名单 → 硬约束悄悄降级、偶发 502；方舟用长名单 → 白关思维链、推理质量下降 |
| 单价 | 接口全通、日志全绿，**看板给出一个格式完整、数值错误的成本数字** |

⚠️ 单价那条是**本次真查出来的**：`.env.prod` 里六个 `AI_PRICE_*` 一直是百炼的价，
2026-09-30 切到方舟后没更新 ⇒ 看板当时正在拿百炼的价算豆包的账。

**兼容**：旧的单套写法仍然有效（本家那组为空时回退到 `ARK_*` / `AI_PRICE_*` /
`AI_THINKING_DISABLED_KINDS`）。是否发生了回退看 `/ai/health` 的
`modelProviderEnvFallbacks`（正常是 `[]`）。

**验证**（都跑过，不是推的）：
- `test/provider-switch.test.js` 新增 9 条；四次证伪每次**恰好**命中目标用例
- 真实 `.env.prod` 在**两种开关位置**下自检都通过、回退都为空数组
- 两家模型链路**各真调通一次**（真凭据）：方舟 1069ms、百炼 793ms，都会回合法结构
- `deploy-check --env-file .env.prod`：**零孤儿变量**、AI 网关自检无致命问题

### 3.2 为什么当初以为「必须改代码」

`src/ark.js` 请求形态本来就是 OpenAI 兼容的（`POST {baseUrl}/chat/completions` +
Bearer），`baseUrl` 也早就是环境变量 —— 所以**大多数东西确实只是换配置**。
真正不兼容的是上面表格后两行，而它们**藏在协议之外**：

**① 思维链字段名与语义都不同。** 方舟的「关掉」是一个**对象**，
百炼的是一个**布尔**。字段名不认识时，多数服务端**选择静默忽略**（而不是 400）。
后果是「思维链根本没关掉」→ 讲解悄悄超时 → 客户端安静退回本地模板，
从外部看就是那句「讲解功能好像没用上 AI」——本项目最典型的静默失败。

**② `tool_choice` 与思维链的交点是个陷阱。** 本项目用 `tool_choice` 传对象来
**硬约束结构化输出**（代码注释：*「结构化输出靠 function calling 硬约束，
而不是在提示词里求模型返回 JSON」*）。而百炼在思维链开启时只接受 `"none"`/`"auto"`。
**单看每一处都对，合起来就 400。**

触发面很窄，但**正中核心闭环**：

| 路由 | 默认是否关思维链 | 百炼下会不会 400 |
|---|---|---|
| `reviewExplain` / `reviewPractice` / `reviewReferenceBatch` | 是 | 否 |
| **`reviewJudge`（判定）** | **否（刻意不关）** | ⚠️ **会** |

默认名单唯独没关判定，而代码注释写明这是有意的：

> 判定（`reviewJudge`）**不建议**关 —— 它本来只花 21–84 个思维链 token，
> 关掉省不下时间，而它的准确率直接决定错题是否毕业。

### 3.3 现在由适配层怎么处理

分叉只有一处，且是**纯函数**（`src/ark.js` 的 `buildRequestBody` / `shouldSendToolChoiceObject`）：

- **思维链**：按厂商查表取字段名与值（`MODEL_PROVIDERS[provider].thinkingOff`）。
- **`tool_choice`**：**只在「百炼 + 思维链开着」这一种组合下退成 `'auto'`**。
  其余情况**照旧传对象**，结构化输出的硬约束不丢 ——
  这个区分很重要：不做的话会把本来能拿到的结构保证也一起丢掉。
- **兜底**：`provider` 缺失时回落方舟字段，且**绝不静默不发**思维链开关
  （「没关掉」是不报错的，很难归因）。

⚠️ **没有**用「把判定也加进关闭名单」来绕这个 400 —— 那是拿准确率换兼容性。

### 3.4 开关管不到、仍要手工确认的三件事

1. **模型 ID 换厂商就要换**。方舟形如 `doubao-seed-2-1-pro-260628`（带 `-YYMMDD` 后缀），
   百炼形如 `qwen3-max` / `qwen3-vl-plus`。
   ⚠️ 选百炼却填了方舟名字时，**配置自检会拦下来**（启动即失败）——
   这类错误在调用时才报，且报错信息里未必带模型名，很难定位。
   判据刻意宽松：只拦「明显像方舟的」（日期后缀 / `doubao-` / `ep-`），
   不写死百炼白名单（否则新模型一上线，老配置就拦下来了）。
2. **百炼对非流式调用思考模式模型有限制**：
   `enable_thinking must be set to false for non-streaming calls`。
   网关正是**非流式**调用 —— 所以百炼下要么让思维链关着，
   要么改用流式。默认名单下 `reviewJudge` 会自动退成 `tool_choice: 'auto'`，
   所以**不会 400**（代价是那一条的结构约束变软）。
3. **真凭证探活**（本地测不出来）：`node scripts/probe-ark-catalog.mjs`。

### 3.5 怎么验证开关真的生效

```bash
curl -s https://<网关域名>/ai/health | grep modelProvider
```

它会如实回显当前厂商。**这条比看配置可靠** ——
「改了环境变量但实例缓存没重建」时，配置看着是新的、实际调用还是旧的。
所以实例缓存签名里已经带上了厂商（这一条有专门的测试盯着）。

生产环境**特意不回显 `baseUrl`**（避免带出内网地址）。

**没有了。** 照片存储后端（§4）与照片配额（§4.4）都已落地并测过。

### 3.7 ⭐ 跨云调用方舟：**阿里云侧一行配置都不用加**（2026-09-30 实测）

选定形态是**混云**：基础设施全在阿里云，只有大模型出公网调方舟。
这一节回答「这做得到吗、要配什么」。**逐层给判据，不是从方案推的：**

| 层 | 结论 | 判据 |
|---|---|---|
| 协议 | 网关本就是 OpenAI 兼容（`{baseUrl}/chat/completions` + Bearer）；方舟的字段差异**已建表** | `ai-gateway/src/ark.js:240` · `src/config.js:188` |
| 开关 | `AI_MODEL_PROVIDER=ark` **本来就是默认值**；切换有断言盯着请求体形态 | `src/config.js:263` · `test/provider-switch.test.js` |
| 网络 | **需要调模型的只有 `ai-gateway`，而它恰好是唯一「不配 VPC + `internetAccess: true`」的函数** | `s.yaml:291` 与 `:293-299` |
| 出口 IP | 方舟的 IP 白名单是**可选**能力，**不启用就不限制** ⇒ FC 的动态出口 IP 无影响 | 方舟官方「管理 API Key」 |
| 端点 | **北京 / 上海都实测 200**，且 `tool_choice` 传对象**真生效** | 探针 `probe_ark_dual_region.mjs`（工作区）· 真凭证 |

⚠️ **两件不要做**：

1. **不要给 `ai-gateway` 补 `vpcConfig`** —— 哪怕「为了保持一致」。`s.yaml:293-299` 那段注释
   就是为这件事写的：配 VPC 只增加冷启时间，对出网没有帮助。
2. **不要给方舟 Key 开 IP 白名单** —— 一旦启用就必须上 **NAT 网关 + EIP**（官方口径），
   而那条路**会同时断掉 OSS 的公网域名**（同一条出网路径），且 NAT/EIP 是额外计费项。

**延迟不是问题，理由是量级**：网络代价是「杭州 → 北京」的几十毫秒，而模型推理是**秒级**
（本次探针实测 1s ~ 35s），**差三个数量级**。本文开头那句「跨地域几十毫秒会逐次叠加」
说的是**同区内反复查库**，**模型调用不适用**（一次批改调模型的次数是个位数）。

**上海端点已实测可用，但不建议切**（`ark.cn-shanghai.volces.com` 同一把 Key 可调）：
收益几十毫秒被推理耗时淹没，成本是引入一个官方未主推、本账号只有一条证据的地域。
⚠️ 真到「模型延迟成为体感瓶颈」那天，再做一次对照测量。

🔴 **唯一的缺口**：**「从阿里云 FC 出去调方舟」这条路径从来没跑过**。
上面五层把缺口收窄成一条，但**没有填上** —— 按本项目纪律，没跑过就不算通过。
补法两条（一次性探针函数 / 直接把网关部署掉）、以及**代价清单**
（`AI_PRICE_*` 会**静默**算错成本、两笔账单、跨云故障域、学生照片出阿里云、逃生门 = 改回 `bailian`）
→ `doc/volcengine-decloud-plan.md` **§13**。

## 4 照片存哪：OSS 与共享目录的区别

这是你反问的那个问题。**核心区别是「有没有一台机器持有一份你可以挂载的磁盘」**：

| | 共享存储目录（NAS / 云盘挂载） | 对象存储 OSS |
|---|---|---|
| 代码改动 | **零** —— 只需把挂载点填进 `IMAGE_ROOT_DIR` | 一个后端模块（**已实现**，见 §4.1） |
| 适用的部署形态 | **必须**是 ECS（有磁盘可挂） | FC 与 ECS 都行 |
| 读写的语义 | POSIX 文件：`mkdir` / `rename` / `readFile` | HTTP 语义：`PutObject` / `GetObject` |
| 多实例 | 靠 NAS 共享，**没问题** | 天然共享，**没问题** |
| 计量与扩容 | 按容量买，闲置也付费 | 按量付费，存储 + 请求 + 流量分别计 |
| 原子性 | 依赖 `rename`（NAS 支持） | 每个对象 PUT 本身原子，但**没有目录概念** |
| 生命周期策略 | 要自己写清理脚本 | 有现成的生命周期规则（转低频/删过期） |
| 权限模型 | 文件系统 UID/GID + 挂载点权限 | RAM 策略 + STS 临时凭证 |

**判断方法一句话**：**跑 FC，就只能选 OSS**（函数没有可挂的持久磁盘）；
**跑 ECS，两条都行** —— 想省事（零代码改动）就挂 NAS，
想省运维（自动扩容、生命周期、按量计费）就写 OSS 后端。

**你的选择是 OSS。** 下面是落地时要知道的事。

### 4.1 两条后端都已实现，由 `IMAGE_DRIVER` 选

| 值 | 实现 | 配置项 |
|---|---|---|
| `fs`（默认） | `data-service/src/imagestore.js` | `IMAGE_ROOT_DIR` |
| `oss` | `data-service/src/ossimagestore.js` | `OSS_BUCKET` / `OSS_REGION` / `OSS_ACCESS_KEY_ID` / `OSS_ACCESS_KEY_SECRET`（+ 可选 `OSS_ENDPOINT` / `OSS_PREFIX`） |

默认值仍是 `fs`，所以这个改动**不改变任何既有部署的行为**。
⚠️ 但 `IMAGE_DRIVER` 写错（比如 `Oss`）会**直接起不来** —— 不会静默退回 `fs`。
静默退回的后果是把照片写进一个你以为不是那里的地方（函数实例的本地磁盘）：
上传回 200、库里也有记录，文件却随实例回收消失。

**接口与文件系统版逐字相同**，所以业务路由（`routes/homework.js`）与冷启动自检一行都没改。

写这个后端时**必须继续保证**的几条（前两条现在由共享函数单点保证）：

- **键格式只有一处定义**：`buildStorageKey()` 产出 `YYYYMMDD/<studentId>/<uuid><ext>`，
  两条后端共用。两处各写一份的话，切后端等于让老照片**全部失联** ——
  而失联的表现是「照片位置一片空白」，没有一处会报错。
- **写入原子性**：文件系统版先写 `.tmp` 再 `rename`，理由是家长端可能**恰好**在
  写入过程中来读 → 直接写目标文件会读到**半截的图**，在浏览器里表现为「图裂」，
  **没有任何一处会报错**。OSS 的 PUT 本身是原子的，这条天然满足。
- **读图的 404 分三种**（不是两种）：
  - `not_on_server` —— 旧版设备本地标识 → 客户端**回退本地读**
  - `file_missing` —— 服务端确实没了 → 只能如实报不可用
  - `storage_backend_error` —— **配置错**（桶名 / 区域 / 凭证 / 权限）
  ⚠️ 前两种是「照片的问题」，第三种是「你配错了」。而 OSS 侧 `NoSuchKey` 与
  `NoSuchBucket` **都是 404** —— 只看状态码的话，「环境变量填错」会被读成
  「照片被清理了」，于是所有人去查清理策略，而真实原因在环境变量里。
- **启动自检** `assertReady()`：OSS 版换成「GET 一个必然不存在的键，期望 404 NoSuchKey」。
  这个「期望失败」的判据比 HEAD 强：HEAD 没有响应体、读不到错误码，
  两种 404 又分不开了。它顺带把**签名算法写对没有**一起验了 ——
  这是唯一能在本地暴露签名错误的时机。

### 4.2 ⚠️ 必须用 V4 签名（V1 已经不能用了）

这是本节最要紧的一条。OSS 的 V1 签名（`Authorization: OSS <AK>:<sig>`，HMAC-SHA1）：

- **2025-03-01 起，新注册用户无法使用 V1 签名**
- **2025-09-01 起，新创建的 Bucket 无法使用 V1 签名**

**你的账号是新申请的、桶也是新建的** —— 所以任何按老文档写的 V1 实现都会 100% 失败，
而失败信息是 `SignatureDoesNotMatch`，看起来像 AccessKey 填错了，
排查方向会先跑到控制台去重新生成密钥。

本仓用的是 V4，**零依赖自写**（只用 `node:crypto`，不引 `ali-oss` SDK ——
避免为两个操作拖进一整棵依赖树）。正确性靠三层判据：

1. `test/oss-imagestore.test.js` 对齐官方文档算例的**规范请求哈希**
   （`c46d9639…`，逐字节一致 —— 差一个空格都会变）；
2. 同文件里「用文档印出的 SigningKey 能签出文档印出的 Signature」，
   一次验证 StringToSign 的拼接与最终那一步 HMAC；
3. SigningKey 的派生链由 Python 标准库独立复算交叉验证。

⚠️ 但**签名对不对最终只有 OSS 说了算**。上面三层都是「纸上的一致」，
验不到桶 ACL、RAM 权限、区域、内网域名可达性、时钟偏差 ——
而它们失败时给的都是长得一样的 403。上线前必须用真凭证打一次：

```bash
cd serverless/data-service
node --env-file=.env.oss scripts/probe-oss.mjs
```

（探测 + 一次 PUT + 一次 GET + 逐字节比对。会留下一个几十字节的探针对象，
脚本会把键打出来让你自己删 —— 刻意不自动删：这是照片桶，
「脚本自己会删东西」不值得引入。）

### 4.3 几个具体的选择

- **桶设成私有**，不要公共读。图片是学生作业本，键里含 `studentId`；
  公共读等于把「猜别人家孩子的照片」变成只需知道一个 uuid 的事，与多家庭隔离冲突。
  本后端**总是带签名读**，不依赖公开访问。
- **生产用 RAM 子账号**，只授予该桶的 `PutObject` / `GetObject`，别用主账号 AccessKey。
- **同区域就走内网域名**（`oss-<region>-internal.aliyuncs.com`）：省流量费，也少一跳。
- **多套环境共用一个桶时设 `OSS_PREFIX`**，否则开发环境和线上互相看得见。
  注意前缀只在存储层生效，**写进数据库的键仍是不带前缀的相对键** ——
  所以将来改前缀会让老照片失联，别随便改。
- 照片配额的**数**要在开通前确认（见 §4.4）—— 对象存储从第一天开始计费，
  等账单来了才发现「3000 张其实也不小」就晚了。

### 4.4 照片配额（Q2/Q3 已定并已实现，2026-09-23）

- **每学生 3000 张**（同日从 10000 下调），走 `IMAGE_QUOTA_PER_STUDENT`，
  两条后端共用同一个数。下调的理由不是省钱，是**让问题显形**：
  10000 张约 5–9 年、3000 张约 1.6–2.7 年，前者长到没人碰得到，
  「照片只增不减」这件事就永远不会被摆到桌面上。
- 达到上限时写照片回 **`storage_quota_exceeded`（409，`retryable:false`）**。
  刻意**不复用** AI 的 `quota_exhausted` —— 客户端对两者的处置不同
  （一个是「今天的 AI 额度用完了」，一个是「去删旧照片」），共用一个码
  等于把两句处置相反的话对调给用户看。
- **接近上限时提前提示**：`IMAGE_QUOTA_WARN_REMAINING`（默认 **20 张**），
  写行成功后由响应里的 `photoUsage` 带出，客户端在提交结果里补一句
  「照片已存 x / y 张，只剩 N 张，删掉一些旧照片可以腾出名额」。
  写 `0` = 不提前提示（与配额那条不同：`0` 在这里只有一个读法）。
  ⚠️ 判据必须在**两侧**：剩 21 张不说、剩 20 张说 —— 只测一侧的话，
  把阈值实现成「永不提示」也会全绿。
- 判在**两处**：写行（**权威**，行才是「有几张」的定义）+ 上传字节**之前**
  （预检 —— 超限时不该先把字节灌进桶、再留一个没人引用的孤儿对象）。
- 配错**直接起不来**（配额：0 / 负数 / 非数字；阈值：负数 / 非数字）。
  静默当成「没有上限」的代价是账单，不是报错。
- ⚠️ **这个数在计费上是有含义的**：单张上限 8MB，按实拍 1–3MB 估，
  一个学生约 **3–9GB**；OSS 标准存储约 0.12 元/GB/月 → **每学生每年 4–13 元**。
  改小是安全的（已有照片不会因此被删，只是不再收新的）。
- ⚠️ 3000 张按一天 3–5 张算约 **1.6–2.7 年** —— 学生是**真的会撞到它**的。
  撞上之后怎么办（手工删旧照片 / 系统按归档期清理 / 降质归档）
  **还没定**，三条路与我的倾向见 `doc/historical-data-plan.md` §3.6。
  **这是上云前该回答的问题之一**：配额只让写入停下，不让空间能被重新使用。
- **改这个数要动哪几处**：改**生产**配额只需一处，而且不是代码 —— 函数计算的环境变量
  （`IMAGE_QUOTA_PER_STUDENT`）。仓库里其余提到它的地方分五种角色：定义 / 引用 /
  部署产物 / 断言 / 注释文档 —— 只有前两类之外的才要跟着改。要一次改干净就先跑
  `npm run quota:where`：它列出全部位置、按「要动 / 不用动」分组，并检查注释里写的
  「默认 N」是否与代码一致（不一致 `exit 1`，已挂进 `npm test`）。
  角色划分与「为什么测试里的数字必须手抄」见 `doc/release-guide.md` §2.4。

## 5 环境变量与两个硬约束

### 5.1 与火山版**完全相同**的变量名

`ARK_BASE_URL` / `ARK_API_KEY` / `ARK_MODEL_*` 这些名字**不用改**（名字是历史遗留，
但改名的收益是零、风险是漏改一处）。只是**值**换成百炼的。

完整清单见 `serverless/deploy-prepare.mjs` 的 ⑤ 段（可直接照抄）。

### 5.2 连接池算式（那条最容易打爆的）

```
函数实例上限 × (PG_POOL_MAX + PG_AUTH_POOL_MAX) < RDS max_connections
```

默认 `5 + 3 = 8` 连接/实例。FC 的实例上限设 50 → 400 连接。
RDS PostgreSQL 的 `max_connections` 与规格相关，**买之前先看那个数**。
症状是**高峰期大面积超时**（看着像接口变慢，其实是连不上库）。

⚠️ **RDS 有两个额外注意**：

1. **白名单 —— 已定方案 A：走 VPC 内网（2026-09-24）**。
   FC 的公网出口 IP 是**动态**的 → 靠放行 IP 永远追不上，只能把网段开得很大，
   等于把库敞在公网上。所以改成：**给数据服务配 `vpcConfig`**（`s.yaml` 已加，
   三个值在 `.env.prod` 的 `FC_VPC_*`），函数在 VPC 里拿一张 ENI 走内网连库；
   白名单只需放行**交换机网段 CIDR** —— 一个固定值，一劳永逸。
   具体三个 ID 从哪抄、以及三条不明显的官方口径（**别用安全组授权** /
   **安全组出方向要放行 ICMP** / 交换机要在 FC 支持的可用区），
   都写在 `.env.prod.example` 的 `FC_VPC_*` 那一段，照抄即可。
   ⚠️ **只给需要连库的函数配**：AI 网关刻意不配（它不碰库，且配了会拖慢冷启动）。
   ⚠️ `internetAccess: true` 要**留着**（数据服务还要连 OSS 的公网域名）——
   FC3 支持「VPC + 公网」并存，两者不是二选一。

2. **`PGSSLMODE` —— 这一条被实测推翻过一次，别再照旧记载走。**
   旧说法：「阿里云 RDS 默认强制 TLS，写 `require` 就对了」；后来又有一次实测说
   「那台**根本没开 SSL**（服务端回 `N`），写 `require` 会让函数连不上库」。
   2026-09-24 傍晚的三条独立判据把**后者也推翻**了：SSL **能用** ——
   `pg_stat_ssl` 报 `ssl=true`、`TLSv1.3`、`TLS_AES_256_GCM_SHA384`；
   `show ssl` = `on`；全库 19 条连接里 8 条走在 SSL 上。
   所以 `.env.prod` 现在填的是 **`require`**（代码在 `db.js:78` 映射成
   `{ rejectUnauthorized: false }`，即**不校验证书链** —— 云厂商自签 CA 的常见形态）。
   ⚠️ 换新实例仍要**先问一句**：`probe-db-access.mjs` 说「不接受 SSL」就改回 `disable`。
   好在那个方向的失败是**吵的**（`The server does not support SSL connections`），
   不会静默降级成明文 —— 这也是敢从 `disable` 挪到 `require` 的理由。
   判据见 §6.1。

   ⚠️⚠️ **下面这段原先是「双栈」的说法，2026-09-24 云上实测把它推翻了 —— 保留更正过程，
   因为它是一个「看起来很有道理、而且被数据支撑」的错误结论。**

   当时的推理：`pgm-<实例ID>.pg.rds.aliyuncs.com` 从公网解析到 `8.158.12.86`，
   而 `pg_stat_activity` 里又同时出现过 `172.21.26.x` 的连接 →
   于是判定「同一个名字双栈，`PGHOST` 一个字都不用改」。

   **两处都不成立：**

   1. 那些 `172.21.26.x` 的连接**不是我们的**。用管理员身份把清单看全之后
      （`datname` 一列）可以看清：它们全部落在 **`supabase_db`** 上
      （PostgREST / kong / supabase_mt_realtime）—— 那是**同一台 RDS 实例上的另一个库**。
      `easylearn_db` 上从来没有一条 `172.21.26.x`。
      📌 教训：**「名单里出现了某物」不等于「某物是你的」** —— 判据要先按
      `datname` 收窄到自己那个库，否则会被邻居的连接误导。
   2. 那个名字在 **VPC 内也解析到公网地址**。判据是两次对照实验：
      `s.yaml` 的 `internetAccess` 设 `true` 时，`app_auth` 的源 IP 是三个**来回变**的
      公网地址（FC 共享出口）；设 `false`（=`允许函数默认网卡访问公网` 关闭，
      流量被强制走 VPC 网卡）时，源 IP **稳定为 `120.26.102.18`**（VPC 的 NAT 网关 EIP）。
      **两次都在公网** → 目的地从来就是公网地址 → **这个域名是「外网地址」。**

   → 正确的结论：**必须把 `PGHOST` 换成 RDS 的「内网地址」**（控制台 → 实例 →
   数据库连接 → **内网地址**，与手上这个域名**不是同一个字符串**）。
   而 `internetAccess` 保持 `true`（OSS 的公网域名要靠它），改 `PGHOST` 就够 ——
   目的地是私有 IP 时，VPC 那张 ENI 自然会接手。

   ✅ **2026-09-24 当天已按上面做完并实测验证 —— 下面是实测事实，不是推断：**

   | | 主机名 | 本机解析 | 函数侧连库来源 |
   |---|---|---|---|
   | 外网地址（原先用的） | `pgm-bp18o4i0278o6p9u0o.pg.rds.aliyuncs.com` | `8.158.12.86` | 三个**会变**的公网 IP |
   | **内网地址（现用）** | `pgm-bp18o4i0278o6p9u.pg.rds.aliyuncs.com` | `172.21.26.125` | **`172.21.26.148`（私有 ✓）** |

   ⚠️ 两个名字**只差尾部两个字符**（`...o6p9u0o` vs `...o6p9u`）——
   实测解析结果完全不同，所以**别把它当成复制时被截断的笔误**（我第一反应就是笔误，
   查了才确认是两个真名字）。
   ⚠️ 那个内网名从本机**能解析、但连不上**（实测 TCP 6.1s 超时；外网名 322ms 连上）。
   于是换地址时**本机脚本必须一起改走外网端点** —— 否则「判据自己先坏了」，
   现象是「连不上库」，看起来像白名单没放行或库挂了。
   规则只有一处：`.env.prod` 的 `PGHOST_EXTERNAL` + `scripts/lib/env-file.mjs`
   的 `cloudHost()`（六个本机脚本都从它取址）。

   📌 顺带：函数还有一个**内网专用入口** `https://<函数名>-<id>.cn-hangzhou-vpc.fcapp.run`
   （部署输出里的 `system_intranet_url`），只能在 VPC 内访问 —— 排查时别拿它当公网地址用。

   ⚠️ 判据与**读法陷阱**都写在 §7.1（含「必须用管理员身份读，否则是假阴性」）。

### 5.3 `AI_SESSION_SECRET`

⚠️ **两个函数必须是同一把、≥32 字符**，且**绝不能**是仓库里那把
`dev-stack-secret-not-for-production` —— 它写在仓库里，任何人拿它都能签一张有效票，
**而且校验全过、不留痕**。

生成：

node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

## 6 部署顺序（与火山版同序）

```
① RDS 建实例（PG 17+；实测 18.4 也跑通了全部迁移）→ 记下连接参数
   ⚠️ 库名按你建的填 —— `src/db.js` 的默认值 `easy_learn` 只是**本机**的
   ⚠️ 白名单分两段，别只做一半：
      · **跑迁移那台机器**的出口 IP（本机连的是那个域名的**公网**地址）
      · **交换机网段 CIDR** —— 这是给函数的（走 VPC 内网，见 §5.2 第 1 条）。
        ⚠️ FC 的公网出口 IP 是**动态**的，所以**不要**指望放行它。
② 建角色 + 建表（**顺序不能颠倒**）：
     cd serverless/data-service
     node scripts/provision-app-roles.mjs --env-file .env.prod --yes   # 先建角色（带强口令）
     node scripts/migrate.mjs --env-file .env.prod --dry-run           # 只读，先看
     node scripts/migrate.mjs --env-file .env.prod --yes               # 真跑
   ⚠️ 为什么先建角色：sql 文件里那句 CREATE ROLE 用的是**开发口令**，而它被
      `IF NOT EXISTS` 包着 —— 角色已存在就整句跳过，开发口令**一次都不会落地**。
      反过来（先迁移、再改口令）也能用，但中间有一个窗口：知道源码里那串口令的人就能连上。

## 7 验收（每条都能红，最后一条是**反面判据**）

```bash
curl -i https://<数据服务域名>/health                      # 期望 200
curl -i https://<网关域名>/ai/health                       # 期望 200
curl -i https://<数据服务域名>/data/bootstrap              # 期望 **401**
#   ↑ 返回 200 说明鉴权链断了。「永远 200」从正面看和正常一模一样。
curl -i -X POST https://<数据服务域名>/auth/login \
  -H 'content-type: application/json' \
  -d '{"phone":"<真实测试账号>","password":"<口令>"}'       # 期望 200 带 token
```

### 7.1 上面四条**证明不了**「函数连得上库」（配了 VPC 之后尤其要看这条）

这不是重复，是**判据的适用范围**问题：

- `/health` 是**特殊路径，任何前缀都能命中，压根不碰数据库** —— 它 200 只说明函数活着；
- `/data/bootstrap` 的 **401 是鉴权层拦下来的**，还没走到数据库就返回了。

所以第一条第 4 行（`/auth/login` 用**真账号**拿 200）才是**唯一**能证明「库通了」的判据。
⚠️ 它必须用**服务端库里真实存在的账号** —— 拿本地模式的账号去试会得到 401，
而那**看起来像 VPC 配错了**。

⚠️⚠️ **先说一个 2026-09-24 踩到的、比上面更隐蔽的版本**：
**库里一个账号都没有时，用什么手机号都回 401，而那条 401 证明不了任何事。**
当时的云库里 `app_user` 是**空表**（迁移建了表、没灌数据），于是「401」被读成了
「已查到库、只是账号不对」—— 实际上连接根本没走到查询那一步也无从分辨。
判据：**先列出账号，再挑一个真的去登**。

```bash
node serverless/data-service/scripts/cloud-accounts.mjs   # 列云端库的账号（只读）
# 空的话先注册一个（注册走同一个 app_auth 连接，本身就是一次真实的写库判据）：
curl -s -X POST https://<数据服务域名>/auth/register \
  -H 'content-type: application/json' \
  -d '{"phone":"13800000001","password":"abc123","name":"测试","role":"student"}'
```

再加一条**只有配了 VPC 才需要**的判据，用来区分「走内网」还是「走公网」：

```bash
node serverless/data-service/scripts/probe-vpc-path.mjs
```

它读的是 `pg_stat_activity.client_addr`（每个连接的对端 IP），**决定性的一行是
`usename = app_auth` 那条** —— 那是登录/注册专用身份，只有数据服务会用它，
所以它的来源 IP 就是「函数走内网还是公网」的直接答案，不用改生产代码。

- 私有地址（`10.` / `192.168.` / `172.16-31.`）→ **走了内网 ✓**，白名单那条固定 CIDR 生效了。
  ✅ 2026-09-24 换完内网地址后的实测输出：
  `172.21.26.148/32 app_auth`、`172.21.26.148/32 app_rls` —— 两条都是**私有**。
  ⚠️ 同一份输出里还有一条 `36.148.179.99/32 easylearn_admin`（公网），那**是探针自己**
  （本机在 VPC 外，只能走外网端点）—— 别把它当成「函数还在走公网」。
- **公网地址** → 函数还在走公网。当时用的就是**外网地址**（见 §5.2 的更正），
  修法是把 `PGHOST` 换成控制台里的**内网地址**。

📌 **不用等部署才能发现这件事**：`deploy-check.mjs` 的 ⑥ 节会解析 `PGHOST` 并与 `s.yaml`
的 `vpcConfig` 对照，两个方向的不自洽都会报 ——
① 有 VPC 却解析到**公网**（= **VPC 白配**，就是本节这一条）；
② 解析到**内网**却没配 VPC（= 函数没有到该网段的路由，**连不上库**）。
⚠️ 它**只证明端点配对了，不证明真的走了内网** —— 后者只能在部署后从库侧看（即本节判据）。

> ⚠️⚠️ **读法陷阱：这个判据有「假阴性」，而且非常像真的。**
> `pg_stat_activity` 对**非超级用户**只显示**它自己那条会话**。实测同一个集群：
> 以 `app_rls`（`rolsuper=false` `rolbypassrls=false`）读 → **1 行**；
> 以 `PG_OPS_USER`（`easylearn_admin`，`rolbypassrls=true`）读 → **22 行**。
> 用前者时，`app_auth` 明明开着两条 idle 连接，输出却是「⚠️ 没看到 app_auth 的连接」，
> 并顺手指向「函数可能没连库 / VPC 配错了」—— **方向完全错**。
> 📌 通则：**凡是「看不到某物」的判据，先确认自己有没有资格看到它。**
> 脚本已改用 `PG_OPS_USER`，并会把当前身份的 `rolbypassrls` 打出来。
>
> ⚠️ 还有一条：按 `usename` 区分还不够，**要再按 `datname` 收窄到自己那个库** ——
> 同一台实例上还挂着别的库（实测有 `supabase_db`，它有一堆 `172.21.26.x` 的私有连接），
> 不筛就会把邻居的连接当成自己的证据（这正是「双栈」那个误判的成因）。

> ⚠️ 为什么单列一节：这是「配了 VPC 就以为万事大吉」的典型坑 ——
> 配 VPC 的**动作**成功了（`s deploy` 不报错、`/health` 也是 200、
> 部署日志里 `vpcConfig` 三要素齐全），而 VPC 的**目的**（走内网连库）并没达到。
> **配置正确 ≠ 行为正确；判据必须落在行为上。**

⚠️ **包不能是空的**：`--exclude` 写错会打出 0 KB 的包，而平台**照样部署成功**，
直到线上第一个请求才 500。`deploy-prepare.mjs --zip` 已带两条断言
（体积 ≥20 KB、归档条目 ≥10）。

## 8 一键部署：现状与边界

**已经是「一条命令上传」了**（2026-09-24 补上 `s.yaml`）：

```bash
node serverless/deploy-prepare.mjs                              # 构造暂存目录 + 离线自检
node serverless/scripts/deploy-check.mjs --env-file .env.prod   # 上传前对账（见下）
node serverless/scripts/run-s.mjs deploy                        # 一把上传两个函数
```

> ⚠️ **别手写成 `set -a && . ./.env.prod && set +a && s deploy`。**
> 那样会漏掉「清代理」，而在带本地代理的机器上（本机就有 `http_proxy=http://127.0.0.1:<port>`）
> `s` 拉取 component 时会把完整 https URL 当成路径发给代理，只拿回一句
> `Request failed with status code 400` —— **s 不打印响应体**，看不出是代理。
> 详见 `doc/release-guide.md` §2.0.2。`run-s.mjs` 会载入 `.env.prod`、清代理、
> 确认暂存目录在；真出问题加 `--sniff` 就能看到真实响应体。

`deploy-prepare.mjs --zip` 仍可用（顺手打出两个 zip，给「手工上传」那条路）。

**边界（诚实版）**：

- `deploy-prepare` / `deploy-check` 都**不登录云账号、不上传、不碰生产库** —— 那三件事需要你的账号权限。
- `s deploy` 需要 `npm i -g @serverless-devs/s` 且先 `s config add`（填 AK/SK，别名用 `default`）。
  **本机没装，所以这条命令没被真跑过** —— 格式是按阿里云官方文档写的，第一次跑请留意输出。
- `s.yaml` 的 `code:` 指向 `build/deploy/<服务>-code/`（⑦ 构造的暂存目录），
  所以**必须先 prepare 再 deploy**。原因见 `doc/release-guide.md` §2.0.1。
- `deploy-check.mjs` 补上了原先缺的那一环：**对账 `s.yaml` 与 `.env.prod`**。
  这两份是分开的（一个进版本库、一个不进），漏一边都只会安静地出事 ——
  引用没值 → 平台拿到空串；值没被引用 → 根本没上传。
